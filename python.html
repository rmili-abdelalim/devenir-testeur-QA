Partie 1 · Module 01

Pourquoi Python, et comment l'installer

Python est un langage de programmation généraliste, lisible, et extrêmement répandu dans le test logiciel : c'est le langage principal derrière Playwright, pytest, Selenium et la quasi-totalité des outils d'automatisation de tests actuels. Sa syntaxe proche du langage naturel le rend rapide à apprendre — mais "rapide à apprendre" ne veut pas dire "sans rigueur" : ce cours pose les fondations correctement, parce que c'est ce qui te permettra ensuite d'écrire des tests fiables plutôt que du code qui marche "par chance".

Contrairement à un langage compilé comme Java ou C, Python est interprété : il n'y a pas d'étape de compilation séparée, un programme .py s'exécute directement via l'interpréteur python3. C'est ce qui rend les allers-retours rapides — utile en test, où on modifie et relance du code en continu.

Vérifier l'installation

Sur macOS et sur la plupart des distributions Linux, Python 3 est généralement déjà présent. Sur Windows, il s'installe depuis python.org (cocher "Add python.exe to PATH" pendant l'installation). Dans tous les cas, on vérifie la version installée depuis un terminal :

Terminal — vérifier la version

$ python3 --version
Python 3.12.3

Selon le système, la commande peut s'appeler python3 ou simplement python — ce cours utilise python3 par convention pour lever toute ambiguïté avec d'anciennes installations Python 2, aujourd'hui obsolètes et à éviter.

Le REPL : un bac à sable interactif

Taper python3 sans rien après ouvre le REPL (Read-Eval-Print Loop) : une console interactive qui évalue chaque ligne tapée et affiche immédiatement le résultat. C'est l'endroit idéal pour tester une idée en deux secondes, sans créer de fichier.

Terminal — session REPL

$ python3
>>> 3 + 4
7
>>> print("Bonjour NovaCart")
Bonjour NovaCart
>>> exit()

Écrire et lancer un vrai script

Pour du code destiné à être conservé et réexécuté, on l'écrit dans un fichier avec l'extension .py, puis on le lance avec python3.

bonjour.py

# Ceci est un commentaire : Python l'ignore à l'exécution
print("Bonjour NovaCart")
print("Ce script tourne avec Python", 3)

Terminal — exécuter le fichier

$ python3 bonjour.py
Bonjour NovaCart
Ce script tourne avec Python 3

La fonction print() affiche du texte dans le terminal — c'est l'outil de base pour observer ce que fait un programme, et plus tard pour lire les messages d'erreur d'un test qui échoue. Un commentaire commence par # et s'étend jusqu'à la fin de la ligne ; il sert à expliquer une intention, pas à répéter ce que le code dit déjà.

Variables, types et affichage

Une variable associe un nom à une valeur. En Python, on ne déclare pas de type explicitement : l'affectation avec = suffit, et le type se déduit de la valeur donnée. On parle de typage dynamique.

Affectation de variables

nom_produit = "Sac à dos randonnée"
prix = 59.90
quantite_stock = 12
en_promotion = True

print(nom_produit)
print(prix)

La convention de nommage en Python s'appelle snake_case : des mots en minuscules séparés par des underscores (prix_unitaire, pas prixUnitaire ni PrixUnitaire). C'est une convention forte, respectée par la quasi-totalité du code Python — s'y tenir dès le départ évite de devoir "désapprendre" une habitude plus tard.

Les types de base

TypeReprésenteExemple
strUne chaîne de caractères (texte)"NovaCart"
intUn nombre entier12
floatUn nombre à virgule flottante (décimal)59.90
boolUne valeur booléenne, seulement True ou FalseTrue
NoneTypeL'absence de valeur, représentée par NoneNone

La fonction type() révèle le type réel d'une valeur — précieux pour déboguer quand un comportement surprend :

Inspecter un type

>>> type(prix)
<class 'float'>
>>> type(quantite_stock)
<class 'int'>
>>> type(None)
<class 'NoneType'>

None mérite une attention particulière : ce n'est ni 0, ni "", ni False — c'est l'absence explicite de valeur. On l'utilise, par exemple, pour représenter un champ optionnel qui n'a pas encore été renseigné : un article NovaCart sans date de promotion aurait date_promo = None, pas une chaîne vide.

Convertir entre types

Les fonctions int(), float(), str() et bool() convertissent une valeur d'un type vers un autre, quand c'est possible.

Conversions

>>> int("42")
42
>>> float("3.14")
3.14
>>> str(99)
'99'
>>> int("abc")
Traceback (most recent call last):
ValueError: invalid literal for int() with base 10: 'abc'

Cette dernière ligne montre une exception : Python interrompt l'exécution quand une conversion est impossible. Le module 11 revient en détail sur la gestion de ces erreurs — pour l'instant, retiens juste que convertir une chaîne qui n'est pas un nombre valide fait planter le programme.

Afficher proprement avec print()

print() accepte plusieurs valeurs séparées par des virgules, et les affiche séparées par un espace par défaut.

print() avec plusieurs arguments

>>> print(nom_produit, "coûte", prix, "euros")
Sac à dos randonnée coûte 59.9 euros
>>> print("a", "b", "c", sep=" - ")
a - b - c

Partie 1 · Module 03

Chaînes de caractères

Les chaînes (str) sont le type le plus manipulé en test logiciel : messages d'erreur, noms de sélecteurs, contenus de pages, données de test. Python offre des outils riches pour les construire et les découper.

Les f-strings : la méthode à privilégier

Une f-string (chaîne préfixée par f) permet d'insérer directement des expressions Python entre accolades {} à l'intérieur du texte. C'est la façon moderne et lisible de construire des messages.

f-strings

nom = "Casque audio"
prix = 54.0

message = f"Article : {nom} — {prix} €"
print(message)

# On peut aussi mettre une expression directement dans les accolades
print(f"Prix arrondi : {round(prix)} €")
print(f"Prix formaté : {prix:.2f} €")

Sortie

Article : Casque audio — 54.0 €
Prix arrondi : 54 €
Prix formaté : 54.00 €

Le format {prix:.2f} impose deux décimales — utile pour afficher un montant en euros de façon cohérente, plutôt que de dépendre du nombre de décimales déjà présentes dans la valeur.

Indexation et slicing

Une chaîne se comporte comme une séquence de caractères indexée à partir de 0. Le slicing (debut:fin) extrait une sous-partie, la borne de fin étant exclue.

Indexation et slicing

reference = "NC-1042"

print(reference[0])      # 'N'
print(reference[-1])     # '2' (dernier caractère)
print(reference[3:])     # '1042' (à partir de l'index 3)
print(reference[:2])     # 'NC' (jusqu'à l'index 2 exclu)
print(reference[3:5])    # '10'

Méthodes courantes

Les chaînes sont immuables : aucune méthode ne modifie la chaîne d'origine, chacune en renvoie une nouvelle.

MéthodeEffetExemple
.strip()Retire les espaces (ou autres caractères) en début/fin" ok ".strip() → "ok"
.lower() / .upper()Convertit en minuscules / majuscules"NC".lower() → "nc"
.split(sep)Découpe en liste selon un séparateur"a,b,c".split(",") → ['a','b','c']
"sep".join(liste)Assemble une liste de chaînes avec un séparateur"-".join(['a','b']) → "a-b"
.replace(a, b)Remplace toutes les occurrences de a par b"abc".replace("b","X") → "aXc"

Nettoyer et découper une ligne de données brute

ligne_brute = "  Sac à dos randonnée ; NC-2210 ; 59.90  "

ligne_propre = ligne_brute.strip()
parties = ligne_propre.split(";")
parties = [p.strip() for p in parties]   # on nettoie chaque morceau (module 8)

print(parties)
# ['Sac à dos randonnée', 'NC-2210', '59.90']

Ce type de nettoyage (espaces superflus, séparateurs, casse incohérente) est extrêmement fréquent quand on travaille avec des données réelles — fichiers exportés, réponses d'API, saisies utilisateur — et donc quand on écrit des tests qui vérifient ces données.

Listes et tuples

Une liste (list) est une collection ordonnée et modifiable de valeurs, potentiellement de types différents. C'est la structure de données la plus utilisée en Python.

Créer et indexer une liste

noms_produits = ["Casque audio", "Sac à dos", "Gourde inox"]

print(noms_produits[0])      # 'Casque audio'
print(noms_produits[-1])     # 'Gourde inox' (dernier élément)
print(len(noms_produits))    # 3
print("Sac à dos" in noms_produits)   # True

Slicing et modification

Le slicing fonctionne comme pour les chaînes. Contrairement aux chaînes, une liste est mutable : on peut modifier ses éléments en place.

Modifier une liste

prix = [45.0, 59.9, 12.5]

prix[0] = 42.0            # remplace le premier élément
prix.append(19.99)        # ajoute à la fin
prix.insert(1, 30.0)      # insère à l'index 1
prix.remove(59.9)         # retire la première occurrence de cette valeur
dernier = prix.pop()      # retire et renvoie le dernier élément

print(prix)

Trier, parcourir, combiner

sorted() renvoie une nouvelle liste triée sans toucher l'originale ; .sort() trie la liste en place et ne renvoie rien.

Tri

stocks = [12, 3, 45, 0, 8]

stocks_tries = sorted(stocks)          # nouvelle liste : [0, 3, 8, 12, 45]
print(stocks)                          # inchangée : [12, 3, 45, 0, 8]

stocks.sort()                          # trie stocks en place
print(stocks)                          # [0, 3, 8, 12, 45]

stocks.sort(reverse=True)              # décroissant
print(stocks)                          # [45, 12, 8, 3, 0]

Fonctions utiles sur une liste de nombres : sum(), min(), max(), len().

Agréger une liste

prix = [45.0, 59.9, 12.5, 19.99]

print(sum(prix))    # 137.39
print(max(prix))    # 59.9
print(min(prix))    # 12.5

Les tuples : des séquences figées

Un tuple (tuple) ressemble à une liste, mais il est immuable — une fois créé, il ne peut plus être modifié. On l'utilise pour des données qui forment un tout cohérent et ne doivent pas changer, comme une coordonnée ou un enregistrement fixe.

Tuples et déballage (unpacking)

article = (1042, "Casque audio", 45.0)   # (id, nom, prix)

# article[0] = 999   # lèverait TypeError : un tuple ne se modifie pas

# Déballage : affecter chaque élément à une variable en une ligne
id_article, nom, prix = article
print(f"{nom} coûte {prix} € (id {id_article})")
Liste ou tuple ?

Utilise une liste quand la collection peut évoluer (ajouter, retirer, réordonner) — comme un panier NovaCart. Utilise un tuple pour une donnée fixe dont la structure ne change pas, comme un enregistrement retourné par une fonction ou une paire de coordonnées.

Le piège de l'aliasing

Affecter une liste à une autre variable ne la copie pas — les deux noms pointent vers la même liste en mémoire. Modifier l'une modifie l'autre.

Aliasing vs copie

panier_a = ["Casque audio", "Gourde inox"]
panier_b = panier_a          # panier_b pointe vers la même liste

panier_b.append("Sac à dos")
print(panier_a)              # ['Casque audio', 'Gourde inox', 'Sac à dos'] !

panier_c = panier_a.copy()   # copie indépendante
panier_c.append("Casquette")
print(panier_a)              # inchangée

Étant donné prix_articles = [45.0, 12.5, 89.9, 6.0, 23.5], écris du code qui : (1) construit une nouvelle liste des prix supérieurs à 15 (sans modifier prix_articles), (2) trie cette nouvelle liste par ordre décroissant, (3) affiche le total de la liste triée.

Partie 1 · Module 05

Dictionnaires et ensembles

Un dictionnaire (dict) associe des clés à des valeurs — c'est la structure idéale pour représenter un enregistrement (un article, un utilisateur, une réponse d'API JSON) avec des champs nommés.

Créer et accéder à un dictionnaire

article = {
    "id": 1042,
    "nom": "Casque audio",
    "prix": 45.0,
    "stock": 12,
}

print(article["nom"])          # accès direct — lève KeyError si absente
print(article.get("nom"))      # accès sûr — équivalent ici
print(article.get("couleur"))  # None : la clé n'existe pas, pas d'erreur
print(article.get("couleur", "non renseignée"))  # valeur par défaut

[] lève une exception KeyError si la clé n'existe pas ; .get() renvoie None (ou une valeur par défaut fournie) sans jamais planter. En pratique, .get() est souvent le choix le plus sûr quand on n'est pas certain qu'une clé existe — par exemple en lisant une réponse d'API dont le format peut varier.

Modifier et itérer

Modification et parcours

article["stock"] = 10           # modifie une valeur existante
article["categorie"] = "audio"  # ajoute une nouvelle clé
del article["categorie"]        # supprime une clé

for cle in article:
    print(cle, "→", article[cle])

# Plus explicite : .items() donne les paires clé/valeur directement
for cle, valeur in article.items():
    print(f"{cle} = {valeur}")

print(list(article.keys()))     # ['id', 'nom', 'prix', 'stock']
print(list(article.values()))   # [1042, 'Casque audio', 45.0, 10]

Représenter une collection d'enregistrements

Une liste de dictionnaires modélise naturellement un jeu de données — c'est exactement la forme que prennent, par exemple, les résultats JSON d'une API ou les lignes d'un fichier CSV chargé en mémoire (module 12).

Liste de dictionnaires

catalogue = [
    {"id": 1, "nom": "Casque audio", "prix": 45.0, "stock": 12},
    {"id": 2, "nom": "Sac à dos", "prix": 59.9, "stock": 0},
    {"id": 3, "nom": "Gourde inox", "prix": 12.5, "stock": 8},
]

for article in catalogue:
    print(f"{article['nom']} — {article['prix']} € (stock : {article['stock']})")

Les ensembles (set) : valeurs uniques

Un ensemble (set) est une collection non ordonnée de valeurs uniques — idéal pour dédupliquer, ou pour tester rapidement l'appartenance à un groupe.

Ensembles

categories = {"audio", "sport", "audio", "cuisine"}
print(categories)          # {'audio', 'sport', 'cuisine'} — le doublon disparaît

categories.add("bureau")
categories.discard("sport")

print("audio" in categories)   # True — test d'appartenance très rapide

a = {"audio", "sport"}
b = {"sport", "cuisine"}
print(a | b)   # union : {'audio', 'sport', 'cuisine'}
print(a & b)   # intersection : {'sport'}
print(a - b)   # différence : {'audio'}

Extraire les catégories uniques d'un catalogue

catalogue = [
    {"nom": "Casque audio", "categorie": "audio"},
    {"nom": "Sac à dos", "categorie": "sport"},
    {"nom": "Écouteurs", "categorie": "audio"},
]

categories_uniques = {article["categorie"] for article in catalogue}  # set comprehension
print(categories_uniques)   # {'audio', 'sport'}

Structures de contrôle

Les structures de contrôle décident quelle partie du code s'exécute, et combien de fois. Ce sont elles qui donnent au code sa logique — indispensables pour écrire des assertions de test conditionnelles ou parcourir des jeux de données.

if / elif / else

Condition simple

stock = 3

if stock == 0:
    print("Rupture de stock")
elif stock < 5:
    print("Stock faible")
else:
    print("Stock disponible")

L'indentation (4 espaces, par convention) délimite les blocs en Python — il n'y a pas d'accolades. C'est une contrainte du langage, pas juste une question de style : un bloc mal indenté est une erreur de syntaxe.

Opérateurs de comparaison et logiques

OpérateurSens

orVrai si au moins une condition est vraie

Combiner des conditions

prix = 45.0
stock = 3
categorie = "audio"

if prix < 50 and stock > 0:

if categorie in ("audio", "video") or prix > 100:
    print("Article premium")
Valeurs "truthy" et "falsy"

Dans un if, Python évalue n'importe quelle valeur comme vraie ou fausse. Sont "falsy" : False, None, 0, 0.0, une chaîne vide "", une liste vide [], un dict vide {}. Tout le reste est "truthy". Ainsi if ma_liste: est une façon idiomatique de tester "la liste n'est pas vide", équivalente à if len(ma_liste) > 0: mais plus lisible.

La boucle for

for parcourt les éléments d'une séquence (liste, chaîne, dict, résultat de range()...).

Boucle for

noms = ["Casque audio", "Sac à dos", "Gourde inox"]

for nom in noms:
    print(nom)

for i in range(5):          # 0, 1, 2, 3, 4
    print(i)

for i in range(1, 11, 2):   # début, fin (exclue), pas → 1, 3, 5, 7, 9
    print(i)

La boucle while

while répète un bloc tant qu'une condition reste vraie — utile quand on ne connaît pas à l'avance le nombre d'itérations.

Boucle while

stock = 5
commandes_traitees = 0

    stock -= 1
    commandes_traitees += 1

print(f"{commandes_traitees} commandes traitées, stock épuisé")

Fonctions

Une fonction regroupe un bloc de code sous un nom, avec des entrées (paramètres) et une sortie (valeur de retour). C'est l'outil numéro un pour éviter de répéter du code, et pour découper un problème en morceaux compréhensibles.

Définir et appeler une fonction

def calculer_prix_ttc(prix_ht, taux_tva):
    """Calcule le prix TTC à partir d'un prix HT et d'un taux de TVA."""
    return prix_ht * (1 + taux_tva)

resultat = calculer_prix_ttc(45.0, 0.20)
print(resultat)   # 54.0

Le texte entre triples guillemets juste après def est une docstring : elle documente ce que fait la fonction. Ce n'est pas obligatoire, mais c'est une bonne habitude dès qu'une fonction n'est pas totalement évidente à la lecture de son nom.

Valeurs par défaut et arguments nommés

Un paramètre peut avoir une valeur par défaut, utilisée si l'appelant ne la fournit pas. On peut aussi appeler une fonction en nommant explicitement les arguments, dans n'importe quel ordre.

Paramètres par défaut

def calculer_prix_ttc(prix_ht, taux_tva=0.20):
    return prix_ht * (1 + taux_tva)

print(calculer_prix_ttc(45.0))               # 54.0 — taux_tva par défaut
print(calculer_prix_ttc(45.0, 0.055))        # 47.475 — TVA réduite
print(calculer_prix_ttc(prix_ht=45.0, taux_tva=0.10))  # arguments nommés
Piège classique : valeur par défaut mutable

Ne jamais utiliser une liste ou un dict comme valeur par défaut d'un paramètre (def f(items=[]):) — cet objet par défaut est créé une seule fois, partagé entre tous les appels, ce qui produit des bugs très difficiles à repérer. La convention correcte utilise None comme défaut, puis crée la liste à l'intérieur de la fonction si besoin.

return et valeurs multiples

return renvoie une valeur et termine immédiatement la fonction. Sans return explicite, une fonction renvoie None. On peut renvoyer plusieurs valeurs à la fois — Python les regroupe automatiquement dans un tuple.

Retourner plusieurs valeurs

def analyser_stock(quantite):
    disponible = quantite > 0
    niveau = "faible" if 0 < quantite < 5 else "normal"
    return disponible, niveau

est_dispo, niveau = analyser_stock(3)
print(est_dispo, niveau)   # True faible

Portée des variables

Une variable créée à l'intérieur d'une fonction (variable locale) n'existe que pendant son exécution et n'est pas visible à l'extérieur. Une fonction peut lire une variable globale, mais ne peut pas la modifier sans le mot-clé global (à éviter en général — préférer passer la valeur en paramètre et la recevoir en retour).

Portée locale vs globale

taux_tva_global = 0.20

def calculer_ttc(prix_ht):
    marge_locale = 0.05   # n'existe que dans cette fonction
    return prix_ht * (1 + taux_tva_global)

print(calculer_ttc(100))
# print(marge_locale)  # NameError : marge_locale n'existe pas ici

Compréhensions de liste et de dictionnaire

Une compréhension construit une nouvelle liste (ou dict, ou set) en une seule expression, à partir d'une séquence existante. C'est souvent plus court et plus lisible qu'une boucle for classique avec .append() — à condition de ne pas en abuser.

Compréhension de liste

Boucle classique vs compréhension

catalogue = [
    {"nom": "Casque audio", "prix": 45.0, "stock": 12},
    {"nom": "Sac à dos", "prix": 59.9, "stock": 0},
    {"nom": "Gourde inox", "prix": 12.5, "stock": 8},
]

# Version boucle for classique
noms_disponibles = []
for article in catalogue:
    if article["stock"] > 0:
        noms_disponibles.append(article["nom"])

# Version compréhension — même résultat, une seule ligne
noms_disponibles = [article["nom"] for article in catalogue if article["stock"] > 0]

print(noms_disponibles)   # ['Casque audio', 'Gourde inox']

La syntaxe générale est [expression for element in sequence if condition] — la partie if est optionnelle. On peut aussi transformer chaque élément :

Transformer les éléments

prix = [45.0, 59.9, 12.5]
prix_avec_tva = [p * 1.20 for p in prix]
print(prix_avec_tva)   # [54.0, 71.88..., 15.0]

Même principe, avec la syntaxe {cle: valeur for element in sequence}.

Dès qu'une compréhension a besoin de plusieurs conditions imbriquées ou de plusieurs boucles, elle devient plus difficile à lire qu'une boucle for classique. La lisibilité prime toujours sur la concision : si tu dois relire trois fois ta propre ligne pour comprendre ce qu'elle fait, reviens à une boucle explicite.

Modules, imports et organisation du code

Un module est simplement un fichier .py. Découper un projet en plusieurs modules, chacun avec une responsabilité claire, rend le code plus facile à lire, à tester et à faire évoluer — c'est exactement la structure qu'adoptera plus tard une suite de tests Playwright (un fichier par page, un fichier par suite de tests).

Importer la bibliothèque standard

Python fournit une riche bibliothèque standard, déjà installée avec l'interpréteur. On y accède avec import.

Imports de la bibliothèque standard

import math

from datetime import date

import module importe le module entier, accessible via module.fonction(). from module import element importe directement un élément précis, utilisable sans préfixe. Les deux styles sont valides — le second est pratique quand on n'utilise qu'un ou deux éléments d'un module.

Environnements virtuels, pip et pyproject.toml

pip est le gestionnaire de paquets de Python : il installe des bibliothèques tierces (comme pytest ou playwright) qui ne font pas partie de la bibliothèque standard. Le problème : installer un paquet globalement sur sa machine mélange les dépendances de tous ses projets, ce qui finit tôt ou tard par provoquer des conflits de versions.

Pourquoi isoler ses dépendances

Un environnement virtuel (venv) crée un dossier isolé contenant sa propre copie de l'interpréteur Python et ses propres paquets installés, indépendants du reste du système. Chaque projet a le sien, ce qui évite qu'un projet A ayant besoin de playwright==1.40 n'entre en conflit avec un projet B qui a besoin d'une version différente.

Terminal — créer et activer un venv

# Depuis le dossier du projet
$ python3 -m venv venv

# Activation — macOS / Linux
$ source venv/bin/activate

# Activation — Windows (PowerShell)
$ venv\Scripts\Activate.ps1

# Une fois activé, le prompt affiche généralement (venv)
(venv) $ python3 --version
Python 3.12.3

Une fois le venv activé, toute commande python3 ou pip utilise cette installation isolée, pas celle du système. On désactive avec la commande deactivate.

Installer des paquets avec pip

Terminal — installer des paquets

(venv) $ pip install pytest
(venv) $ pip install playwright

(venv) $ pip list
Package      Version
------------ -------
pytest       8.2.0
playwright   1.44.0

requirements.txt : figer les dépendances du projet

Pour que n'importe qui (ou toi-même sur une autre machine) puisse recréer exactement le même environnement, on liste les dépendances dans un fichier requirements.txt, qu'on installe en une commande.

requirements.txt

pytest==8.2.0
playwright==1.44.0

Terminal — générer et réutiliser requirements.txt

# Sur une autre machine (ou un venv fraîchement créé) :
(venv) $ pip install -r requirements.txt
Ce que tu utiliseras réellement

C'est très exactement cette suite de commandes — python3 -m venv venv, activation, pip install pytest playwright, requirements.txt — qui sert de base à toute installation d'un projet de tests Playwright en Python. Rien de nouveau à apprendre à ce moment-là : juste appliquer ce que tu viens de voir.

Vers pyproject.toml : le standard actuel

requirements.txt fonctionne, mais il n'est plus le standard recommandé pour un projet Python moderne : c'est un simple fichier texte qui liste des versions, sans distinguer les dépendances nécessaires à l'exécution de celles utilisées seulement pour le développement (le lint, par exemple), et sans décrire le projet lui-même (son nom, sa version, ses outils). pyproject.toml (normalisé par la PEP 621) centralise tout ça dans un seul fichier structuré, et c'est aujourd'hui la référence — même pour un petit projet de tests.

pyproject.toml — un projet de tests NovaCart minimal

[project]
name = "novacart-tests"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = [
    "pytest>=8.2",
    "playwright>=1.44",
]

[project.optional-dependencies]
dev = ["ruff>=0.5", "mypy>=1.10"]

La section [project.optional-dependencies] sépare clairement les outils de développement (lint, typage — vus au module suivant) des dépendances nécessaires pour simplement faire tourner les tests. On installe le projet et ses dépendances avec pip install -e ".[dev]" (le -e installe en mode "éditable", pratique pendant le développement).

Et des outils comme uv ou Poetry ?

uv et Poetry sont des gestionnaires de projet plus récents qui s'appuient eux aussi sur pyproject.toml, mais accélèrent l'installation et gèrent un fichier de verrouillage des versions (lockfile) pour garantir des environnements strictement identiques d'une machine à l'autre. Ce cours ne tranche pas entre eux : retiens que pyproject.toml est le format qui compte, quel que soit l'outil utilisé par-dessus.

Partie 3 · Module 11

Gestion des erreurs

Quand Python rencontre une situation qu'il ne peut pas gérer, il lève une exception qui interrompt le programme (sauf si elle est interceptée). Savoir gérer les exceptions correctement est ce qui distingue un script fragile d'un code qui échoue proprement, avec un message clair.

try / except

Intercepter une exception

saisie = "abc"

try:
    quantite = int(saisie)
    print(f"Quantité valide : {quantite}")
except ValueError:
    print(f"'{saisie}' n'est pas un nombre valide")

Le bloc except ne s'exécute que si une exception du type précisé (ici ValueError) survient dans le bloc try. Préciser le type d'exception attendu est important : intercepter Exception sans distinction masque aussi de vraies erreurs de programmation, ce qui rend le débogage bien plus difficile.

Exceptions courantes

ExceptionSe produit quand
ValueErrorUne valeur a le bon type mais une valeur invalide (ex. int("abc"))
TypeErrorUne opération est appliquée à un type incompatible (ex. "3" + 3)
KeyErrorUne clé de dictionnaire n'existe pas
IndexErrorUn index de liste/chaîne est hors limites
ZeroDivisionErrorUne division par zéro

else, finally, et intercepter plusieurs types

try complet

def diviser_stock_par_commande(stock, nb_commandes):
    try:
        resultat = stock / nb_commandes
    except ZeroDivisionError:
        print("Aucune commande à traiter")
        return None
    except TypeError:
        print("Les valeurs fournies ne sont pas des nombres")
        return None
    else:
        # Exécuté seulement si le bloc try n'a levé aucune exception
        print("Calcul réussi")
        return resultat
    finally:
        # Toujours exécuté, qu'il y ait eu une exception ou non
        print("Fin du traitement")

print(diviser_stock_par_commande(20, 4))   # 5.0
print(diviser_stock_par_commande(20, 0))   # None, message d'erreur

Lever ses propres exceptions

raise déclenche volontairement une exception — utile pour signaler qu'une fonction reçoit des données invalides, plutôt que de laisser le programme continuer avec un état incohérent.

raise

def calculer_prix_ttc(prix_ht, taux_tva):
    if prix_ht < 0:
        raise ValueError(f"prix_ht ne peut pas être négatif : {prix_ht}")
    return prix_ht * (1 + taux_tva)

try:
    calculer_prix_ttc(-10, 0.20)
except ValueError as erreur:
    print(f"Erreur : {erreur}")
Attraper ou laisser remonter ?

Dans du code applicatif, on attrape une exception quand on peut réagir intelligemment (proposer une valeur par défaut, réessayer, afficher un message clair). Dans du code de test, c'est souvent l'inverse : on laisse une exception inattendue remonter et faire échouer le test, plutôt que de l'attraper silencieusement — un test qui masque ses erreurs avec un try/except trop large donne une fausse impression de succès.

Exceptions personnalisées : donner un sens métier à l'erreur

Une ValueError générique ne dit pas quoi était invalide dans le contexte de NovaCart. Définir ses propres classes d'exception, héritées de Exception (voir héritage, module 13), rend le code appelant capable de réagir précisément — et rend les tests plus lisibles (pytest.raises(StockInsuffisantError) en dit bien plus que pytest.raises(ValueError)).

Une hiérarchie d'exceptions métier

class NovaCartError(Exception):
    """Classe de base pour toutes les erreurs métier NovaCart."""

class StockInsuffisantError(NovaCartError):
    def __init__(self, sku, demande, disponible):
        self.sku = sku
        super().__init__(f"{sku} : {demande} demandé(s), {disponible} disponible(s)")

class PaiementRefuseError(NovaCartError):
    pass

def retirer_du_stock(sku, quantite_demandee, stock_disponible):
    if quantite_demandee > stock_disponible:
        raise StockInsuffisantError(sku, quantite_demandee, stock_disponible)
    return stock_disponible - quantite_demandee

Hériter d'une classe de base commune (NovaCartError) permet aussi d'intercepter toutes les erreurs métier d'un coup avec except NovaCartError:, tout en gardant la possibilité de cibler un cas précis avec except StockInsuffisantError: — les deux niveaux de granularité restent disponibles.

Chaîner les exceptions avec raise ... from ...

Quand une exception est interceptée puis qu'on en lève une autre à la place (pour donner plus de contexte, par exemple), Python risque de perdre la trace de l'erreur d'origine. raise ... from ... préserve ce lien explicitement dans le traceback.

Sans from — le contexte d'origine se perd

def charger_configuration(chemin):
    try:
        with open(chemin) as f:
            return json.load(f)
    except FileNotFoundError:
        raise NovaCartError(f"Configuration introuvable : {chemin}")
    # Le traceback affiché ne montrera que NovaCartError,
    # sans dire que la cause réelle était un fichier manquant.

Avec from — le lien de causalité est explicite

def charger_configuration(chemin):
    try:
        with open(chemin) as f:
            return json.load(f)
    except FileNotFoundError as erreur:
        raise NovaCartError(f"Configuration introuvable : {chemin}") from erreur
    # Le traceback affiche maintenant les deux exceptions, avec la mention
    # "The above exception was the direct cause of the following exception"
Un pattern minimal de retry

Pour un appel réseau instable (module 21 — Mocking avancé montre comment le tester), une stratégie simple combine un nombre maximal de tentatives et une pause entre chaque essai :

import time

def appeler_avec_retry(fonction, tentatives=3, delai=1):
    for essai in range(1, tentatives + 1):
        try:
            return fonction()
        except ConnectionError:
            if essai == tentatives:
                raise   # dernière tentative épuisée : on laisse l'erreur remonter
            time.sleep(delai)

Fichiers, JSON et CSV

La plupart des jeux de données de test — jeux de données d'entrée, fixtures, réponses d'API enregistrées — vivent dans des fichiers texte, souvent au format JSON ou CSV. Savoir les lire (et les écrire) en Python est une compétence directement réutilisable pour préparer des données de test.

Ouvrir un fichier avec un gestionnaire de contexte

La forme with open(...) as f: est la façon correcte d'ouvrir un fichier : elle garantit sa fermeture automatique, même si une erreur survient pendant la lecture.

Lire et écrire un fichier texte

# Écriture (mode "w" = write, écrase le contenu existant)
with open("notes.txt", "w") as f:
    f.write("Casque audio\n")
    f.write("Sac à dos\n")

# Lecture complète
with open("notes.txt", "r") as f:
    contenu = f.read()
print(contenu)

# Lecture ligne par ligne (mémoire-efficace pour de gros fichiers)
with open("notes.txt", "r") as f:
    for ligne in f:
        print(ligne.strip())   # .strip() retire le \n final

Le mode "a" (append) ajoute à la fin du fichier sans écraser le contenu existant. Sans gestionnaire de contexte (f = open(...) suivi de f.close() manuel), oublier .close() — notamment quand une exception survient entre les deux — laisse le fichier ouvert, ce qui peut corrompre des écritures ou épuiser les ressources système.

JSON : lire et écrire des données structurées

Le module json de la bibliothèque standard convertit entre du JSON (texte) et des structures Python natives (dict, list) — exactement le format que renvoie la plupart des API web.

articles.json

[
    {"id": 1, "nom": "Casque audio", "prix": 45.0, "stock": 12},
    {"id": 2, "nom": "Sac à dos", "prix": 59.9, "stock": 0}
]

Lire et écrire du JSON

import json

# Lire un fichier JSON vers une structure Python
with open("articles.json", "r") as f:
    catalogue = json.load(f)

print(catalogue[0]["nom"])   # 'Casque audio'

# Convertir une structure Python en texte JSON (sans fichier)

print(texte_json)

# Écrire une structure Python vers un fichier JSON

    json.dump(catalogue, f, indent=2)

json.load() / json.dump() travaillent directement avec un fichier ouvert ; json.loads() / json.dumps() (avec un "s") travaillent avec une chaîne de caractères déjà en mémoire — utile par exemple pour parser directement le corps texte d'une réponse d'API.

CSV : lire des données tabulaires

Le module csv lit et écrit des fichiers CSV. csv.DictReader est en général le plus pratique : chaque ligne devient un dictionnaire dont les clés sont les en-têtes de colonnes.

commandes.csv

1,NC-CLIENT-04,89.90,payee
2,NC-CLIENT-11,45.00,payee
3,NC-CLIENT-04,12.50,annulee

Toutes les valeurs CSV sont du texte

DictReader renvoie systématiquement des chaînes de caractères, même pour des colonnes numériques — ligne["montant"] vaut la chaîne "89.90", pas le nombre 89.90. Il faut convertir explicitement avec float() avant tout calcul, sous peine de concaténer des textes au lieu d'additionner des nombres.

Expressions régulières avec re

Certaines validations ne se résument pas à comparer des valeurs — il faut vérifier qu'un texte respecte un motif : un format de référence de commande, un code postal, un email. Le module re, intégré à Python, sert exactement à ça.

Chercher un motif dans une chaîne

import re

texte = "Commande NC-2026-00123 expédiée le 12/03/2026"

resultat = re.search(r"NC-\d{4}-\d{5}", texte)
if resultat:
    print(resultat.group())  # NC-2026-00123

re.search() cherche le motif n'importe où dans la chaîne et renvoie le premier trouvé. re.match() ne vérifie que le tout début de la chaîne — si l'identifiant de commande n'est pas en première position, re.match() renverra None là où re.search() le trouverait quand même.

Extraire toutes les occurrences avec findall

notes_livraison = """
Client A : 75012 Paris
Client B : 69003 Lyon
Client C : 13001 Marseille
"""

codes_postaux = re.findall(r"\d{5}", notes_livraison)
print(codes_postaux)  # ['75012', '69003', '13001']

Les parenthèses créent des groupes de capture : elles permettent d'extraire une sous-partie précise du motif trouvé, plutôt que le texte entier.

Valider et décomposer un identifiant de commande

def extraire_annee_commande(reference):
    resultat = re.match(r"NC-(\d{4})-(\d{5})", reference)
    if resultat is None:
        raise ValueError(f"Référence de commande invalide : {reference}")
    annee, numero = resultat.groups()
    return int(annee)

print(extraire_annee_commande("NC-2026-00123"))  # 2026

Enfin, re.sub() remplace toutes les occurrences d'un motif — utile pour anonymiser des données de test ou normaliser un format avant comparaison :

Masquer les numéros de commande dans des logs

log = "Erreur de paiement pour la commande NC-2026-00123"

print(log_anonymise)  # Erreur de paiement pour la commande NC-XXXX-XXXXX
Pas besoin de tout retenir par cœur

Les motifs regex sont denses à lire. En tant que testeur, l'essentiel est de reconnaître les briques courantes (\d pour un chiffre, + pour "une ou plusieurs fois", {n} pour "exactement n fois") et de savoir tester ton motif sur des exemples avant de l'utiliser dans une vérification automatisée.

Partie 4 · Module 13

Programmation orientée objet

Une classe décrit un modèle d'objet : quelles données il porte (ses attributs) et quelles actions il sait faire (ses méthodes). Un objet (ou instance) est une réalisation concrète de ce modèle. C'est un changement de perspective important — et c'est la base directe du Page Object Model, le pattern que tu utiliseras systématiquement en Playwright.

Définir une classe

Une classe Produit

class Produit:
    def __init__(self, nom, prix, stock):
        self.nom = nom
        self.prix = prix
        self.stock = stock

    def est_disponible(self):
        return self.stock > 0

    def prix_ttc(self, taux_tva=0.20):
        return self.prix * (1 + taux_tva)

    def __repr__(self):
        return f"Produit(nom={self.nom!r}, prix={self.prix}, stock={self.stock})"

casque = Produit("Casque audio", 45.0, 12)
sac = Produit("Sac à dos", 59.9, 0)

print(casque.est_disponible())   # True
print(sac.est_disponible())      # False
print(casque.prix_ttc())         # 54.0
print(casque)                    # Produit(nom='Casque audio', prix=45.0, stock=12)

__init__ est le constructeur : il s'exécute automatiquement à la création d'un objet (Produit(...)) et initialise ses attributs. self représente l'instance elle-même — c'est toujours le premier paramètre d'une méthode, et Python le fournit automatiquement à l'appel (on n'écrit jamais casque.est_disponible(casque), juste casque.est_disponible()). __repr__ définit ce qui s'affiche quand on imprime l'objet ; c'est optionnel mais très utile pour déboguer.

Pourquoi ça compte pour Playwright : le Page Object Model

En automatisation de tests avec Playwright, on modélise généralement chaque page (ou composant) de l'application sous forme de classe : ses attributs représentent les éléments de la page (un bouton, un champ), ses méthodes représentent les actions qu'on peut y faire (cliquer, remplir un champ). C'est exactement le même principe que la classe Produit ci-dessus — seul le contenu change.

Illustration du principe (sans vraie logique Playwright)

class PageProduitNovaCart:
    """Représente la page produit sur NovaCart.
    En Playwright, self.page serait un objet Page fourni par le framework,
    et chaque méthode utiliserait ses sélecteurs pour interagir avec le DOM.
    Ici, on illustre uniquement la structure de la classe."""

    def __init__(self, page):
        self.page = page   # en Playwright : l'objet Page de la session navigateur

    def obtenir_titre(self):
        # équivalent conceptuel de : self.page.locator("h1").text_content()
        return "Casque audio"

    def ajouter_au_panier(self):

        print("Article ajouté au panier")

Retiens la structure, pas les détails Playwright (ils seront couverts dans le cours dédié) : une classe par page, un constructeur qui reçoit l'objet de session, des méthodes nommées par intention (ajouter_au_panier, pas clic_bouton_3) plutôt que par implémentation. C'est ce qui rend une suite de tests lisible et maintenable sur la durée.

Analyse et conception : passer d'un besoin à des classes

Avant d'écrire une classe, il faut décider ce qu'elle représente. Une méthode simple, souvent suffisante au quotidien : dans l'énoncé du besoin, les noms deviennent généralement des candidats à devenir des classes, et les verbes associés à ces noms deviennent des candidats à devenir des méthodes.

On appelle aussi ça la responsabilité unique : une classe bien conçue fait une chose, et la fait bien. Si une classe Commande se met à gérer aussi l'envoi d'emails et le calcul de la TVA et la connexion à la base de données, elle devient difficile à comprendre, à tester et à faire évoluer sans tout casser. Pas besoin de connaître les grands principes de conception pour appliquer cette idée : à chaque fois qu'une classe grossit, se demander "est-ce que tout ça relève vraiment de la même responsabilité ?" suffit déjà à repérer les problèmes.

De l'énoncé à la classe

Besoin : "Un panier doit pouvoir ajouter un produit,
le retirer, et calculer le total."

Nom principal   → la classe : PanierNovaCart
Verbes associés → les méthodes : ajouter_produit(), retirer_produit(), calculer_total()

On construit la classe méthode par méthode, en partant de ce qu'elle doit stocker (son état) et de ce qu'elle doit faire (son comportement) :

Conception pas à pas de PanierNovaCart

class PanierNovaCart:
    def __init__(self):
        self.produits = []  # état : la liste des produits ajoutés

    def ajouter_produit(self, produit):
        self.produits.append(produit)

    def retirer_produit(self, produit):
        if produit in self.produits:
            self.produits.remove(produit)

    def calculer_total(self):
        return sum(produit.prix for produit in self.produits)

Chaque méthode correspond à exactement un verbe de l'énoncé de départ — c'est un bon signe que la classe est bien délimitée.

L'héritage : réutiliser une classe existante

Quand une nouvelle classe ressemble beaucoup à une classe existante, mais avec quelques attributs ou comportements en plus, l'héritage évite de tout réécrire. La nouvelle classe hérite de la classe de base et n'ajoute que ce qui la rend différente.

ProduitNumerique hérite de Produit

class ProduitNumerique(Produit):
    def __init__(self, nom, prix, stock, taille_fichier_mo):
        super().__init__(nom, prix, stock)  # réutilise __init__ de Produit
        self.taille_fichier_mo = taille_fichier_mo

    def duree_telechargement_estimee(self, debit_mo_par_s):
        return self.taille_fichier_mo / debit_mo_par_s

super().__init__(nom, prix, stock) appelle le constructeur de Produit pour initialiser les attributs communs, avant d'ajouter l'attribut propre à ProduitNumerique. Résultat : un ProduitNumerique possède tout ce qu'un Produit possède, plus taille_fichier_mo et sa propre méthode.

livre_numerique = ProduitNumerique("Guide QA débutant", 12.90, stock=999, taille_fichier_mo=8)
print(livre_numerique)  # Produit(nom='Guide QA débutant', prix=12.9, stock=999) — __repr__ hérité de Produit
print(livre_numerique.duree_telechargement_estimee(2))  # 4.0

@dataclass : moins de code répétitif pour porter des données

Beaucoup de classes ne font que porter des données, avec un __init__ répétitif et un __repr__ écrit à la main. Le décorateur @dataclass (module dataclasses) génère ce code automatiquement à partir des annotations de type.

La classe Produit du début du module, en dataclass

from dataclasses import dataclass

@dataclass
class Produit:
    nom: str
    prix: float
    stock: int

    def est_disponible(self):
        return self.stock > 0

casque = Produit("Casque audio", 45.0, 12)
print(casque)                    # Produit(nom='Casque audio', prix=45.0, stock=12) — généré automatiquement
print(casque == Produit("Casque audio", 45.0, 12))   # True — __eq__ généré aussi

@dataclass génère __init__, __repr__ et __eq__ à partir des attributs annotés — exactement ce qu'on écrivait à la main plus haut, en bien moins de lignes. Les méthodes métier (est_disponible) restent définies normalement.

@property : exposer un calcul comme un attribut

@property permet d'appeler une méthode sans parenthèses, comme un simple attribut — utile pour un calcul dérivé qu'on veut présenter comme une donnée, tout en gardant le contrôle sur son calcul.

prix_ttc comme propriété calculée

class Produit:
    def __init__(self, nom, prix_ht, taux_tva=0.20):
        self.nom = nom
        self.prix_ht = prix_ht
        self.taux_tva = taux_tva

    @property
    def prix_ttc(self):
        return round(self.prix_ht * (1 + self.taux_tva), 2)

casque = Produit("Casque audio", 45.0)
print(casque.prix_ttc)   # 54.0 — pas casque.prix_ttc() : c'est un attribut, pas un appel

classmethod et staticmethod

@classmethod reçoit la classe elle-même (cls) plutôt qu'une instance — utile pour un constructeur alternatif. @staticmethod ne reçoit ni l'un ni l'autre : c'est une fonction simplement rangée dans la classe parce qu'elle en est conceptuellement proche.

Un constructeur alternatif depuis une ligne CSV

Conception pragmatique et SOLID

Le module 13 a introduit la responsabilité unique à travers un exemple concret. SOLID regroupe cinq principes de conception orientée objet, dont la responsabilité unique fait partie — pas pour les réciter, mais parce qu'ils décrivent des problèmes réels qui apparaissent tôt ou tard dans une base de tests qui grossit.

Les 5 principes, par le problème qu'ils résolvent

PrincipeLe problème qu'il évite
S — Responsabilité uniqueUne classe qui fait trop de choses devient difficile à comprendre, tester, et modifier sans risque (module 13).
O — Ouvert/ferméAjouter un comportement force à modifier du code existant qui marchait déjà, au lieu d'étendre sans y toucher.
L — Substitution de LiskovUne sous-classe qui ne respecte pas le contrat de sa classe parente casse le code qui utilise cette dernière.
I — Ségrégation des interfacesUne interface trop large force les classes à implémenter des méthodes dont elles n'ont pas besoin.
D — Inversion des dépendancesDu code qui dépend directement d'une implémentation concrète est difficile à tester sans la vraie dépendance.

Cas concret : une architecture de tests devenue impossible à maintenir

Ce runner de tests appelle directement une API de paiement réelle — un problème classique de D (inversion des dépendances) qui, en pratique, rend toute la suite lente, fragile face au réseau, et impossible à faire tourner hors ligne.

Avant : couplage direct à une implémentation concrète

import requests

class ValidateurCommande:
    def valider_paiement(self, commande):
        reponse = requests.post("https://api-paiement.novacart.com/verifier", json={
            "id": commande.id, "montant": commande.montant
        })
        return reponse.json()["valide"]

ValidateurCommande ne peut être testé qu'en appelant le vrai service — lent, instable, et impossible sans connexion. L'inversion des dépendances consiste à dépendre d'une abstraction (un Protocol, module 13) plutôt que d'une implémentation précise, pour pouvoir substituer un faux service pendant les tests.

Après : dépendre d'une abstraction, injectée depuis l'extérieur

from typing import Protocol

class ServicePaiement(Protocol):
    def verifier(self, id_commande: str, montant: float) -> bool: ...

class ValidateurCommande:
    def __init__(self, service_paiement: ServicePaiement):
        self.service_paiement = service_paiement   # injecté, pas construit ici

    def valider_paiement(self, commande):
        return self.service_paiement.verifier(commande.id, commande.montant)

# En test : un faux service, sans aucun réseau
class FauxServicePaiement:
    def verifier(self, id_commande, montant):
        return True

validateur = ValidateurCommande(FauxServicePaiement())

Ce même changement rend ValidateurCommande testable avec un Mock (module 21) exactement de la même façon — l'inversion des dépendances est ce qui rend le mocking possible sans réécrire la classe testée à chaque fois.

Pragmatique, pas dogmatique

SOLID décrit des tensions à surveiller, pas des règles à appliquer partout systématiquement. Un petit script jetable n'a pas besoin d'une interface Protocol pour une seule implémentation qui n'existera jamais autrement. Le signal à repérer : "cette classe est-elle difficile à tester ou à faire évoluer à cause de sa conception ?" — si non, SOLID n'a rien à corriger ici.

Une fonction de test pytest, décryptée

pytest est un framework de test : il découvre automatiquement toute fonction dont le nom commence par test_ dans un fichier dont le nom commence par test_, et l'exécute. Regarde cette fonction avec ce que tu sais déjà :

test_prix.py

def calculer_prix_ttc(prix_ht, taux_tva=0.20):
    return prix_ht * (1 + taux_tva)


def test_prix_ttc_avec_tva_standard():
    resultat = calculer_prix_ttc(45.0)
    assert resultat == 54.0


def test_prix_ttc_avec_tva_personnalisee():
    resultat = calculer_prix_ttc(100, taux_tva=0.10)
    assert resultat == 110.0

Rien d'inconnu ici : def pour définir une fonction (module 7), un appel de fonction avec arguments nommés (module 7), et le mot-clé assert — nouveau, mais simple : il vérifie qu'une expression est vraie, et si ce n'est pas le cas, il lève une AssertionError qui fait échouer le test, en affichant les valeurs comparées pour comprendre immédiatement ce qui a divergé.

Terminal — lancer pytest

(venv) $ pytest test_prix.py -v

test_prix.py::test_prix_ttc_avec_tva_standard PASSED
test_prix.py::test_prix_ttc_avec_tva_personnalisee PASSED

2 passed in 0.02s

assert sur des structures de données

assert fonctionne avec n'importe quelle expression booléenne — y compris des comparaisons sur des listes, dicts, ou le résultat d'une classe entière, exactement les structures vues dans ce cours.

Assertions sur des structures

def test_catalogue_contient_casque():

def test_article_est_disponible():

    assert article["stock"] > 0

Un mot sur les fixtures (aperçu, pas le détail)

Une fixture pytest est une fonction qui prépare quelque chose dont un test a besoin (par exemple, un navigateur Playwright déjà ouvert, ou un jeu de données déjà chargé), et pytest l'injecte automatiquement dans le test en la nommant simplement comme paramètre :

Aperçu d'une fixture (le détail complet vient au module 20, juste après le prochain)

import pytest

@pytest.fixture
def catalogue_test():
    return [{"nom": "Casque audio", "stock": 12}]

def test_premier_article_disponible(catalogue_test):
    assert catalogue_test[0]["stock"] > 0

@pytest.fixture est un décorateur — une syntaxe qui modifie le comportement de la fonction juste en dessous ; retiens pour l'instant seulement le motif visuel : @quelque_chose juste au-dessus d'un def. Le module 28 (Partie 7) explique en détail comment un décorateur fonctionne réellement ; le module 20, juste après celui-ci, détaille les fixtures et conftest.py.

La ligne de commande

Jusqu'ici, tu as sans doute exécuté tes scripts Python depuis un éditeur (VS Code, PyCharm...) en cliquant sur un bouton "Run". C'est pratique pour apprendre, mais un testeur QA passe une bonne partie de sa journée dans un terminal : lancer une suite de tests, cloner un dépôt, installer une dépendance, inspecter des fichiers de logs. Ce module te donne les bases pour t'y sentir à l'aise.

Se repérer dans les dossiers

Le terminal (ou "invite de commandes", ou "console") est une fenêtre où tu tapes des commandes texte au lieu de cliquer sur des icônes. Trois commandes suffisent pour naviguer :

  • pwd ("print working directory") affiche le dossier dans lequel tu te trouves actuellement.
  • ls (Mac/Linux) ou dir (Windows) liste les fichiers et sous-dossiers du dossier courant.
  • cd nom_du_dossier ("change directory") te déplace dans un sous-dossier ; cd .. remonte d'un niveau.

Une session de navigation typique

$ pwd
/home/alex/projets

$ ls

$ cd novacart-tests
$ pwd
/home/alex/projets/novacart-tests

$ ls
test_panier.py    test_commandes.py    conftest.py

$ cd ..
$ pwd
/home/alex/projets

Le $ en début de ligne représente l'invite du terminal (le symbole exact varie) : tu ne le tapes pas, c'est le terminal qui l'affiche pour indiquer qu'il attend une commande.

Une fois dans le bon dossier, on lance un script avec la commande python suivie du nom du fichier (sur certains systèmes, il faut utiliser python3) :

Un script devient bien plus utile s'il peut recevoir des informations depuis la ligne de commande, sans que tu aies à modifier le code à chaque fois. Le module sys donne accès à la liste sys.argv, qui contient les mots tapés après le nom du script.

print(f"Recherche pour {args.client}, montant minimum : {args.min_montant} €")

$ python filtrer_client.py --help

...

Avec argparse, args.client et args.min_montant sont typés et documentés automatiquement — et l'option --help existe sans rien coder de plus.

sys.argv ou argparse ?

Pour un script jetable à un seul argument, sys.argv suffit. Dès que le script est réutilisé par d'autres personnes, ou qu'il accepte plusieurs options, argparse évite les erreurs et rend le script auto-documenté.

Partie 5 · Module 17

Résoudre des problèmes avec Python

Savoir la syntaxe de Python ne suffit pas à résoudre un problème : il faut aussi une méthode pour ne pas se noyer devant un énoncé, et des réflexes pour comprendre pourquoi ça plante. Ces deux compétences comptent autant pour écrire un test que pour écrire le code testé.

Une méthode en 5 étapes

Face à un nouveau problème, résiste à l'envie d'ouvrir directement l'éditeur et de taper du code. Passe d'abord par ces étapes :

  1. Comprendre l'énoncé. Reformule le problème avec tes propres mots. Quelles sont les entrées ? Quelle est la sortie attendue ? Y a-t-il des cas particuliers mentionnés ?
  2. Décomposer en étapes. Écris en français (ou en pseudo-code) la suite d'opérations à faire, sans te soucier de la syntaxe Python.
  3. Coder. Traduis chaque étape en Python, une à la fois.
  4. Tester. Vérifie d'abord avec un cas simple et évident, puis avec des cas limites (liste vide, valeur négative, doublon...).
  5. Améliorer. Une fois que ça marche, relis : le code est-il lisible ? Y a-t-il un cas oublié ?

Cette méthode n'est pas propre à la programmation : c'est la même démarche qu'un testeur QA applique pour analyser un bug avant d'écrire son rapport.

Lire un traceback

Quand un script plante, Python affiche un traceback : la trace des appels de fonctions qui ont mené à l'erreur. Il paraît intimidant, mais il faut le lire dans un ordre précis : le message d'erreur tout en bas d'abord (le type d'erreur et sa description), puis remonter pour trouver la ligne de ton propre code responsable.

Un traceback typique

Traceback (most recent call last):
  File "analyse.py", line 12, in <module>
    moyenne = total / nombre_commandes
              ~~~~~~^~~~~~~~~~~~~~~~~~
ZeroDivisionError: division by zero

On lit : ZeroDivisionError (le type d'erreur, tout en bas) — division by zero (sa description) — et juste au-dessus, la ligne exacte du fichier analyse.py qui a causé le problème. Ici, nombre_commandes valait 0 au moment de la division. Un traceback long avec plusieurs blocs "File ... line ..." indique juste que l'erreur s'est propagée à travers plusieurs fonctions : la dernière ligne du bloc, tout en bas, reste celle qui a réellement échoué.

Le debug par print()

La technique la plus simple pour comprendre ce qui se passe dans un script : afficher l'état des variables à des points clés avec print(), puis relancer le script.

def calculer_total(panier):
    total = 0
    for article in panier:
        print(f"DEBUG : article = {article}")
        total += article["prix"] * article["quantite"]
    print(f"DEBUG : total final = {total}")
    return total

Ce n'est pas élégant, mais c'est rapide et ça fonctionne sans outil supplémentaire. Pense à retirer (ou commenter) ces print() une fois le bug résolu — ou utilise un vrai débogueur (le module pdb, ou celui intégré à ton éditeur) quand le problème devient plus complexe.

Le rubber duck debugging

Une technique connue de tous les développeurs : explique ton code, ligne par ligne, à voix haute, à un objet inanimé — traditionnellement un canard en plastique posé sur le bureau. Le simple fait de formuler à haute voix "ici je récupère le stock, ensuite je compare au seuil..." force ton cerveau à ralentir et révèle très souvent l'erreur avant même d'avoir fini la phrase. Pas de canard sous la main ? Un collègue, ou même un message écrit à toi-même, fonctionne tout aussi bien.

Mise en pratique : le client qui a le plus dépensé

Énoncé : à partir d'une liste de commandes NovaCart, trouver le nom du client ayant dépensé le plus au total.

commandes = [
    {"client": "Léa Fabre", "montant": 42.90},
    {"client": "Karim Nasri", "montant": 128.00},
    {"client": "Léa Fabre", "montant": 15.50},
    {"client": "Sofia Martin", "montant": 89.99},
]

Étape 1 — comprendre : un même client peut apparaître plusieurs fois, il faut donc additionner ses commandes avant de comparer, pas juste prendre le montant le plus élevé d'une seule ligne.

Étape 2 — pseudo-code : pour chaque commande, ajouter son montant au total du client concerné (dans un dictionnaire) ; à la fin, trouver la clé dont la valeur est la plus grande.

Étape 3 — coder

totaux_par_client = {}

for commande in commandes:
    client = commande["client"]
    montant = commande["montant"]
    totaux_par_client[client] = totaux_par_client.get(client, 0) + montant

meilleur_client = max(totaux_par_client, key=totaux_par_client.get)
print(f"{meilleur_client} : {totaux_par_client[meilleur_client]:.2f} €")

Étape 4 — tester : avec ces données, le résultat attendu est Karim Nasri : 128.00 € (58.40 € pour Léa Fabre, 89.99 € pour Sofia Martin). Cas limite : que se passe-t-il si commandes est une liste vide ? max() sur un dictionnaire vide lève une ValueError — il faudrait la gérer si ce cas est possible en pratique.

Étape 5 — améliorer : totaux_par_client.get(client, 0) évite un KeyError la première fois qu'un client apparaît, en renvoyant 0 par défaut plutôt que de planter.

Partie 5 · Module 18

Structures de données et algorithmes

Deux scripts peuvent produire exactement le même résultat, mais l'un met 10 millisecondes et l'autre 10 minutes sur un gros volume de données. La différence vient souvent du choix de la structure de données ou de l'algorithme utilisé. Ce module donne une intuition suffisante pour repérer ces situations — sans notation mathématique compliquée.

La complexité, une idée simple

La "complexité" (souvent notée en Big-O, par exemple O(n)) répond à une seule question : si je multiplie la taille des données par 10, mon programme devient-il 10 fois plus lent, 100 fois plus lent, ou à peine plus lent ?

  • O(1) — temps constant : peu importe la taille des données, l'opération prend le même temps (ex : accéder à ma_liste[0]).
  • O(n) — temps proportionnel à la taille n des données : parcourir toute une liste une fois.
  • O(log n) — le temps augmente très lentement, même avec beaucoup de données (ex : recherche binaire, voir plus bas).

Retiens surtout le réflexe : avant de choisir une structure de données, demande-toi comment elle se comportera si les données NovaCart passent de 100 produits à 100 000.

Chercher dans une liste vs un dict/set

Chercher si un produit existe dans une list oblige Python à examiner les éléments un par un jusqu'à trouver une correspondance (ou arriver au bout) : c'est du O(n). Chercher une clé dans un dict ou une valeur dans un set est quasiment instantané, quelle que soit la taille : c'est du O(1), grâce à une structure interne (une table de hachage) qui calcule directement où se trouve l'élément.

Même besoin, deux structures différentes

# Recherche dans une liste : O(n) — Python compare un par un
ids_en_liste = [101, 205, 309, 412, 578]  # imaginons des milliers d'ids
if 412 in ids_en_liste:
    print("Produit trouvé")

# Recherche dans un set : O(1) — quasi instantané
ids_en_set = {101, 205, 309, 412, 578}
if 412 in ids_en_set:
    print("Produit trouvé")

Sur une liste de 20 éléments, la différence est invisible. Sur un catalogue NovaCart de 200 000 références vérifié à chaque ligne d'un fichier de commandes de 50 000 lignes, passer d'une liste à un set peut transformer un script de plusieurs minutes en quelques secondes.

Piles et files

Une pile (stack) fonctionne comme une pile d'assiettes : le dernier élément ajouté est le premier retiré (LIFO — "last in, first out"). En Python, une list suffit, avec append() pour empiler et pop() pour dépiler.

historique_actions = []

historique_actions.append("ajout_panier: Casque Bluetooth")
historique_actions.append("modif_quantite: 2")
historique_actions.append("suppression: Souris")

derniere_action = historique_actions.pop()
print(derniere_action)   # suppression: Souris (annulée en premier)

Une file (queue) fonctionne à l'inverse comme une file d'attente en magasin : le premier arrivé est le premier servi (FIFO — "first in, first out"). Une list peut simuler une file avec pop(0), mais c'est lent sur de gros volumes (retirer le premier élément oblige à décaler tous les autres en mémoire). Le module collections fournit deque, conçu pour être efficace des deux côtés.

from collections import deque

commandes_a_traiter = deque()

commandes_a_traiter.append("Commande #1042")
commandes_a_traiter.append("Commande #1043")
commandes_a_traiter.append("Commande #1044")

prochaine_commande = commandes_a_traiter.popleft()
print(prochaine_commande)   # Commande #1042 (traitée en premier)

Recherche linéaire vs recherche binaire

La recherche linéaire consiste à parcourir les éléments un par un (c'est ce que fait in sur une liste) : O(n). Si la liste est triée, la recherche binaire fait bien mieux : elle regarde l'élément du milieu, élimine directement la moitié des possibilités selon qu'il est trop grand ou trop petit, et répète — en O(log n). Le module standard bisect l'implémente pour toi.

import bisect

prix_tries = [9.99, 14.50, 19.99, 24.90, 34.00, 49.99, 79.90]

# Trouve l'index où insérer 24.90 pour garder la liste triée
position = bisect.bisect_left(prix_tries, 24.90)
if position < len(prix_tries) and prix_tries[position] == 24.90:
    print(f"Prix trouvé à l'index {position}")
else:
    print("Prix absent de la liste")

Sur 7 éléments, aucune différence perceptible avec une recherche linéaire. Sur une liste triée de 10 millions d'éléments, la recherche binaire fait le travail en une vingtaine de comparaisons contre potentiellement 10 millions.

Pourquoi ça compte pour un testeur QA

Un testeur QA n'écrit pas forcément l'algorithme de recherche du site NovaCart, mais ces notions servent tous les jours :

  • Comprendre pourquoi un test devient soudainement lent quand le jeu de données de test grossit (un test qui passait en 2 secondes sur 50 produits et qui en prend 40 sur 50 000 cache souvent une recherche en O(n) là où un dict ferait l'affaire).
  • Savoir générer des jeux de données de test représentatifs : pour vérifier qu'une fonctionnalité tient la charge, il faut des volumes réalistes (des milliers de commandes, pas trois lignes à la main), et choisir la bonne structure pour les manipuler sans que le test lui-même devienne le goulot d'étranglement.
Pas besoin de tout mémoriser

Retiens surtout deux réflexes : utiliser un set ou un dict plutôt qu'une list dès qu'on cherche souvent "est-ce que cet élément existe ?", et se méfier d'un test qui ralentit anormalement quand le volume de données augmente — c'est souvent le signe d'une structure de données mal choisie, pas d'une fatalité.

La récursion : une fonction qui s'appelle elle-même

Une fonction récursive résout un problème en l'appliquant à une version plus petite du même problème, jusqu'à atteindre un cas de base assez simple pour être résolu directement. Sans cas de base correct, la récursion ne s'arrête jamais.

Parcourir une arborescence de dossiers de résultats de tests

def compter_fichiers(dossier):
    total = 0
    for entree in os.scandir(dossier):
        if entree.is_dir():
            total += compter_fichiers(entree.path)   # cas récursif : sous-dossier
        else:
            total += 1                                # cas de base : un fichier
    return total
Le piège de la récursion infinie

Oublier le cas de base — ou écrire une condition qui ne se rapproche jamais de lui — produit une RecursionError après environ 1000 appels imbriqués (la limite par défaut de Python). C'est l'équivalent récursif d'une boucle while dont la condition ne devient jamais fausse.

Arbres et graphes : modéliser des relations

Un arbre est une structure hiérarchique : chaque nœud a un parent (sauf la racine) et zéro ou plusieurs enfants — une arborescence de fichiers, une structure de menu imbriqué. Un graphe généralise l'idée : des nœuds reliés par des arêtes, sans hiérarchie imposée — un graphe de dépendances entre modules Python, où A peut dépendre de B qui dépend de A.

Un graphe de dépendances, représenté en dictionnaire

dependances = {
    "test_commandes": ["test_panier", "test_paiement"],
    "test_panier": ["test_catalogue"],
    "test_paiement": ["test_catalogue"],
    "test_catalogue": [],
}

Parcourir un graphe : BFS et DFS

Deux stratégies pour parcourir un graphe ou un arbre. Le parcours en largeur (BFS — Breadth-First Search) explore niveau par niveau, avec une file (deque, vu plus haut dans ce module). Le parcours en profondeur (DFS — Depth-First Search) suit une branche jusqu'au bout avant de revenir en arrière, naturellement récursif ou avec une pile.

DFS pour détecter un cycle d'imports

def detecter_cycle(graphe, noeud, visites, en_cours):
    visites.add(noeud)
    en_cours.add(noeud)

    for voisin in graphe.get(noeud, []):
        if voisin in en_cours:
            return True   # on revient sur un nœud déjà en cours de visite : cycle !
        if voisin not in visites and detecter_cycle(graphe, voisin, visites, en_cours):
            return True

    en_cours.remove(noeud)
    return False

# detecter_cycle(dependances, "test_commandes", set(), set())  # False ici : pas de cycle

Ce genre de détection de cycle n'est pas théorique : un cycle d'imports Python (module_a importe module_b qui importe module_a) provoque une ImportError difficile à diagnostiquer sans comprendre ce mécanisme de parcours de graphe.

Exercice

Le script actuel utilise if id_produit in liste_ids_valides: et met plusieurs minutes à s'exécuter. Explique pourquoi, et corrige le script pour qu'il soit rapide.

Voir la correction 
# Avant : O(n) à chaque recherche, répétée 20 000 fois -> très lent

    if id_produit in liste_ids_valides:   # parcourt jusqu'à 50 000 éléments
        pass

# Après : conversion en set une seule fois, puis recherche en O(1)

Avec une list, chacune des 20 000 vérifications parcourt en moyenne la moitié des 50 000 identifiants, soit environ un milliard de comparaisons au total. En convertissant liste_ids_valides en set une seule fois (coût unique, O(n)), chaque recherche suivante devient quasi instantanée : le script passe de plusieurs minutes à une fraction de seconde.

Débogage professionnel

Le module 17 t'a donné les premiers réflexes : lire un traceback, débugger par print(), reformuler le problème. Sur un vrai projet — une suite de tests qui échoue en CI, un bug qui ne se reproduit qu'une fois sur dix — ces réflexes ne suffisent plus. Ce module ajoute un vrai débogueur et une méthode rigoureuse pour ne jamais chercher un bug au hasard.

Le débogueur interactif : pdb et breakpoint()

Contrairement à print(), qui oblige à deviner à l'avance quelle variable afficher puis à relancer le script, un débogueur interrompt l'exécution à un point précis et laisse inspecter l'état du programme en direct — variables, pile d'appels, exécution pas à pas. Python fournit pdb dans sa bibliothèque standard, et la fonction breakpoint() (depuis Python 3.7) l'invoque sans même avoir à l'importer.

Poser un point d'arrêt

def calculer_total_panier(panier):
    total = 0
    for article in panier:
        breakpoint()   # l'exécution s'arrête ici, à chaque itération
        total += article["prix"] * article["quantite"]
    return total

À l'arrêt, le terminal s'ouvre sur une invite (Pdb) qui accepte quelques commandes essentielles :

CommandeEffet
nnext — exécute la ligne courante, sans entrer dans les fonctions appelées
sstep — exécute la ligne courante, en entrant dans la fonction appelée si il y en a une
ccontinue — reprend l'exécution normale jusqu'au prochain point d'arrêt
p nom_variableaffiche la valeur d'une variable à cet instant précis
llist — affiche le code autour de la ligne courante, pour se repérer
qquit — quitte le débogueur et arrête l'exécution
Pourquoi pas juste plus de print() ?

Avec print(), chaque nouvelle question ("et si j'affichais aussi article["prix"] ?") demande de modifier le code et de relancer tout le script depuis le début. Avec breakpoint(), on inspecte, on pose une nouvelle question à l'invite (Pdb) directement, et on continue — sans jamais relancer le script. Sur un bug qui prend plusieurs secondes ou minutes à reproduire, la différence de vitesse est considérable.

Une méthode, pas une intuition : les 8 étapes du débogage professionnel

Face à un bug réel — surtout un bug rapporté par quelqu'un d'autre, ou qui ne se manifeste que dans certaines conditions — improviser fait perdre du temps. Cette méthode en 8 étapes structure la démarche :

  1. REPRODUIRE. Si tu ne peux pas déclencher le bug à volonté, tout le reste est bâti sur du sable. Note les conditions exactes : données, environnement, séquence d'actions.
  2. ISOLER. Réduis le cas au minimum : quel est le plus petit bout de code, la plus petite donnée d'entrée qui déclenche encore le problème ?
  3. HYPOTHÈSE. Formule explicitement ce que tu penses être la cause, avant d'aller regarder — ça t'oblige à raisonner plutôt qu'à fouiller au hasard.
  4. INVESTIGUER. Utilise le débogueur (ou les logs, module 30) pour vérifier ou infirmer ton hypothèse avec des faits, pas des suppositions.
  5. CAUSE RACINE. Ne t'arrête pas au premier symptôme : une KeyError peut être le résultat d'un problème bien plus en amont dans le flux de données.
  6. CORRIGER. Corrige la cause racine identifiée, pas seulement le symptôme observé.
  7. TESTER. Vérifie que le cas reproduit à l'étape 1 est bien résolu — et que rien d'autre ne s'est cassé au passage.
  8. PRÉVENIR LA RÉGRESSION. Ajoute un test automatisé qui couvre ce cas précis : sans lui, rien n'empêche ce même bug de revenir silencieusement dans six mois.
Le piège du symptôme

Corriger un symptôme sans chercher la cause racine (étape 5) donne souvent l'impression d'avoir résolu le problème — jusqu'à ce qu'il ressurgisse ailleurs, sous une autre forme. Un stock qui devient négatif peut être "corrigé" en ajoutant max(stock, 0) partout où il est affiché ; la vraie cause — une fonction qui décrémente le stock sans vérifier la quantité disponible — reste intacte et continue de produire des données incohérentes en base.

Mise en pratique : un bug caché dans le calcul de remise NovaCart

Ce code, censé appliquer une remise de fidélité, produit parfois un montant final supérieur au prix d'origine — un bug rapporté par le support client, sans étapes de reproduction précises.

calcul_remise.py — contient un bug

def appliquer_remise_fidelite(prix, points_fidelite):
    """Applique 1% de remise par tranche de 100 points, plafonnée à 30%."""
    taux_remise = (points_fidelite // 100) * 0.01
    taux_remise = min(taux_remise, 0.30)
    if points_fidelite < 0:
        taux_remise = -0.05   # "bonus" ajouté par erreur lors d'un correctif précédent
    return round(prix * (1 - taux_remise), 2)
Exercice

Voir la correction

Reproduire : appliquer_remise_fidelite(100, -10) renvoie 105.0 — supérieur au prix d'origine.

Isoler : le cas minimal est n'importe quel points_fidelite négatif ; le reste de la fonction n'entre pas en jeu.

Cause racine : la ligne taux_remise = -0.05 pour un solde de points négatif — un taux négatif revient à augmenter le prix dans prix * (1 - taux_remise). Cette branche n'a aucune justification métier claire (un solde de points ne devrait jamais être négatif) : c'est un correctif ad hoc laissé par erreur, pas une règle voulue.

def appliquer_remise_fidelite(prix, points_fidelite):
    """Applique 1% de remise par tranche de 100 points, plafonnée à 30%."""
    points_fidelite = max(points_fidelite, 0)   # un solde ne peut pas être négatif
    taux_remise = (points_fidelite // 100) * 0.01
    taux_remise = min(taux_remise, 0.30)
    return round(prix * (1 - taux_remise), 2)

def test_remise_avec_points_negatifs_ne_depasse_jamais_le_prix():
    assert appliquer_remise_fidelite(100, -10) == 100.0

def test_remise_plafonnee_a_30_pourcent():
    assert appliquer_remise_fidelite(100, 100_000) == 70.0

La correction retire la branche fautive et neutralise un solde négatif en amont, à la source, plutôt que de rajouter un correctif de plus en aval. Le test test_remise_avec_points_negatifs_ne_depasse_jamais_le_prix est celui qui, s'il avait existé avant, aurait empêché ce bug d'atteindre la production — exactement l'étape 8 de la méthode.

Par convention, pytest découvre automatiquement les tests s'ils suivent quelques règles de nommage. Un projet NovaCart typique ressemble à ceci :

Les fixtures pytest en profondeur

Une fixture est une fonction qui prépare quelque chose dont un test a besoin — des données, un objet, une connexion. Pytest l'injecte automatiquement dans le test si le nom du paramètre correspond au nom de la fixture.

Une fixture simple

import pytest

@pytest.fixture
def panier_test():
    return {"produits": [], "total": 0.0}

def test_panier_vide_au_depart(panier_test):
    assert panier_test["produits"] == []
    assert panier_test["total"] == 0.0

Par défaut, une fixture a une portée (scope) "function" : elle est recréée pour chaque test, ce qui garantit qu'un test ne pollue jamais le suivant. On peut élargir la portée pour éviter de refaire un travail coûteux plusieurs fois :

scope="module" : une seule fois par fichier de test

@pytest.fixture(scope="module")
def connexion_catalogue_novacart():
    print("Ouverture de la connexion au catalogue")
    connexion = ouvrir_connexion_catalogue()
    yield connexion
    connexion.fermer()
    print("Connexion fermée")

Le mot-clé yield est essentiel : tout ce qui est avant sert à préparer les données (le setup), tout ce qui est après sert à nettoyer (le teardown) — et ce nettoyage s'exécute même si le test échoue.

Une fixture qui prépare puis nettoie une commande

@pytest.fixture
def commande_novacart():
    commande = creer_commande(client_id=42, produits=["SKU-1001"])
    yield commande
    supprimer_commande(commande.id)  # nettoyage garanti après le test

def test_commande_a_un_statut_initial(commande_novacart):
    assert commande_novacart.statut == "en_attente"
Pourquoi nettoyer

Sans nettoyage, les données créées par un test peuvent fausser les tests suivants (des commandes fantômes en base, par exemple). En environnement de test, on veut repartir d'un état propre à chaque exécution.

Tester plusieurs jeux de données avec parametrize

Plutôt que d'écrire un test par taux de TVA, @pytest.mark.parametrize exécute la même fonction de test avec chaque jeu de valeurs fourni — pytest affiche chaque cas comme un test distinct dans le rapport.

Vérifier qu'une exception est bien levée

Un test ne sert pas qu'à vérifier les cas normaux — vérifier qu'une fonction refuse bien une entrée invalide fait partie du travail. pytest.raises encadre le code censé lever une exception :

Isoler un test avec le mocking

Certains tests dépendent d'un service externe — une API de paiement, un envoi d'email. On ne veut pas vraiment débiter une carte bancaire à chaque exécution des tests : trop lent, trop risqué, et le résultat dépendrait d'un service qu'on ne contrôle pas. unittest.mock.patch remplace temporairement cette dépendance par une version factice.

tests/test_commandes.py

from unittest.mock import patch

def rembourser_client(commande, api_paiement):
    resultat = api_paiement.rembourser(commande.id, commande.montant)
    return resultat["statut"] == "ok"

def test_remboursement_appelle_l_api_avec_le_bon_montant():
    commande = Commande(id="CMD-501", montant=59.90)
    with patch("api_paiement.rembourser") as mock_rembourser:
        mock_rembourser.return_value = {"statut": "ok"}
        succes = rembourser_client(commande, api_paiement)

    assert succes is True
    mock_rembourser.assert_called_once_with("CMD-501", 59.90)

Le test vérifie deux choses sans jamais appeler la vraie API : que la fonction appelle bien le service de paiement avec les bons paramètres, et qu'elle interprète correctement la réponse.

Partie 5 · Module 21

Mocking avancé

Le module 20 a introduit unittest.mock.patch sur un cas simple. En pratique professionnelle, isoler un test d'une dépendance externe demande un vocabulaire précis et des outils plus riches — sans quoi on finit soit par tester de vraies API à chaque exécution, soit par écrire des mocks si permissifs qu'ils ne détectent plus rien.

Le vocabulaire des test doubles

"Mock" est souvent utilisé comme terme générique, mais la littérature du test distingue plusieurs rôles précis — les connaître aide à choisir le bon outil, et à comprendre ce qu'un test vérifie réellement :

TermeRôle
DummyUn objet passé pour satisfaire une signature, jamais réellement utilisé (ex. un paramètre requis mais ignoré par le code testé).
StubRenvoie des réponses préprogrammées, sans logique — sert à fournir des données de test contrôlées.
SpyComme un stub, mais qui enregistre en plus comment il a été appelé (avec quels arguments, combien de fois) pour le vérifier ensuite.
MockUn spy dont les attentes sur les appels sont vérifiées explicitement par le test lui-même (assertions sur les appels).
FakeUne implémentation simplifiée mais fonctionnelle (ex. une base de données en mémoire à la place d'une vraie base) — se comporte vraiment, en plus simple.

En Python, unittest.mock.Mock et MagicMock couvrent en pratique les rôles de stub, spy et mock à la fois — c'est leur usage dans le test qui détermine lequel de ces rôles ils jouent.

Mock et MagicMock

Mock() crée un objet qui accepte n'importe quel appel de méthode ou accès d'attribut sans erreur, et qui enregistre tout ce qui lui arrive. MagicMock fait la même chose, avec en plus le support des méthodes spéciales (__len__, __eq__...).

Un Mock de base : configurer et vérifier

from unittest.mock import Mock

api_paiement = Mock()
api_paiement.rembourser.return_value = {"statut": "ok", "montant": 59.90}

resultat = api_paiement.rembourser("CMD-501", 59.90)

print(resultat)                                   # {'statut': 'ok', 'montant': 59.9}
api_paiement.rembourser.assert_called_once_with("CMD-501", 59.90)

side_effect : simuler plusieurs comportements successifs

side_effect va plus loin que return_value : une fonction, une exception, ou une liste de valeurs à renvoyer une par une à chaque appel successif — utile pour simuler une panne intermittente ou une séquence d'états.

Simuler une API instable avec side_effect

from unittest.mock import Mock

api_paiement = Mock()
api_paiement.rembourser.side_effect = [
    ConnectionError("Timeout"),
    ConnectionError("Timeout"),
    {"statut": "ok"},   # réussit à la 3e tentative
]

for tentative in range(3):
    try:
        resultat = api_paiement.rembourser("CMD-501", 59.90)
        print("Succès :", resultat)
        break
    except ConnectionError:
        print(f"Tentative {tentative + 1} échouée")

C'est exactement ce type de mock qui permet de tester un décorateur reessayer(...) (module 28 — Décorateurs et générateurs) sans dépendre d'un vrai service instable.

autospec : un mock qui respecte la vraie signature

Un Mock nu accepte n'importe quel appel, même incorrect — api_paiement.rembourser(1, 2, 3, 4, 5) ne provoquerait aucune erreur, alors même que la vraie fonction n'accepte que deux arguments. C'est un vrai risque : un test peut rester vert alors que le code appelle mal une dépendance, et l'erreur n'apparaît qu'en production. autospec=True corrige ça en inspectant la vraie fonction ou classe, pour que le mock lève une erreur si l'appel ne correspond pas à sa signature réelle.

patch avec autospec

from unittest.mock import patch

def rembourser_client(commande_id, montant, api_paiement):
    return api_paiement.rembourser(commande_id, montant)

with patch("module_paiement.ApiPaiement", autospec=True) as MockApi:
    instance = MockApi.return_value
    instance.rembourser.return_value = {"statut": "ok"}

    # Un appel avec les mauvais arguments lèverait ici une TypeError,
    # exactement comme le ferait la vraie classe ApiPaiement.
    rembourser_client("CMD-501", 59.90, instance)
Le piège du sur-mocking

Chaque dépendance mockée est une dépendance que le test ne vérifie plus réellement. Un test qui mocke la fonction testée elle-même, ou qui mocke tant de choses qu'il ne reste plus de vraie logique exécutée, donne une fausse confiance : il passe toujours, même si le code réel est cassé. La règle pratique : mocker les dépendances externes (réseau, base de données, horloge, aléatoire), jamais la logique qu'on est censé être en train de tester.

Le lien avec la QA

Une suite de tests d'automatisation qui appelle de vrais services externes à chaque exécution est lente, coûteuse, et dépendante de la disponibilité de systèmes qu'on ne contrôle pas. Savoir mocker précisément — avec le bon niveau de fidélité, ni trop permissif ni trop rigide — est ce qui permet de garder une suite de tests rapide et fiable, en isolant chaque test à la seule chose qu'il doit réellement vérifier.

Exercice

Une fonction verifier_stock_disponible(sku, service_stock) appelle service_stock.consulter(sku), qui renvoie un entier (la quantité en stock), et renvoie True si cette quantité est supérieure à 0. Écris un test qui, avec un Mock configuré en side_effect, vérifie le comportement sur trois appels successifs : stock à 5 (True attendu), stock à 0 (False attendu), puis une ConnectionError levée par le service (à laisser remonter, sans l'attraper dans verifier_stock_disponible).

    return quantite > 0

Comme verifier_stock_disponible ne contient aucun try/except, l'exception remonte naturellement jusqu'au test — c'est le comportement attendu ici, pas une erreur du mock.

TDD, non dogmatique

Le développement piloté par les tests (TDD — Test-Driven Development) inverse l'ordre habituel : on écrit le test avant le code qu'il teste. Ce module montre le cycle sur un cas réel, puis une discussion honnête de quand cette pratique aide vraiment — et quand elle ralentit sans bénéfice clair.

Le cycle Red-Green-Refactor

  1. Red. Écrire un test qui échoue, pour une fonctionnalité qui n'existe pas encore.
  2. Green. Écrire le code le plus simple possible qui fait passer ce test — pas le code "idéal", juste ce qu'il faut pour être vert.
  3. Refactor. Une fois vert, améliorer la structure du code sans changer son comportement, en s'appuyant sur le test comme filet de sécurité.

En pratique : une fonction de calcul de remise NovaCart

Red — le test existe, la fonction non

def test_remise_10_pourcent_sur_100_euros():
    assert calculer_remise(100, code_promo="NOVA10") == 10.0
# NameError : calculer_remise n'existe pas encore — le test échoue, c'est attendu

Green — le code le plus simple qui passe

def calculer_remise(prix, code_promo):
    if code_promo == "NOVA10":
        return prix * 0.10
    return 0

Un second test pousse à généraliser (nouveau Red, puis Green)

def test_remise_20_pourcent():
    assert calculer_remise(100, code_promo="NOVA20") == 20.0

# Green : généraliser plutôt qu'empiler des if
TAUX_PROMO = {"NOVA10": 0.10, "NOVA20": 0.20}

def calculer_remise(prix, code_promo):
    return prix * TAUX_PROMO.get(code_promo, 0)

Refactor : les deux tests restent verts après ce passage d'une chaîne de if à un dictionnaire — c'est exactement ce que le filet de sécurité des tests permet de vérifier immédiatement, sans reparcourir tout le code à la main.

Quand le TDD aide, et quand il ralentit

Le TDD aide quand...Le TDD ralentit inutilement quand...
La logique métier est bien définie à l'avance (règles de calcul, validations)Le problème est exploratoire — on ne sait pas encore à quoi ressemblera la solution

Non dogmatique

Écrire les tests après le code, tant qu'ils sont écrits et qu'ils couvrent vraiment le comportement, reste largement préférable à ne pas les écrire du tout. Le TDD est un outil pour penser la conception avant l'implémentation — pas une obligation morale.

Tests basés sur les propriétés et testabilité

Tous les tests vus jusqu'ici sont des tests par l'exemple : une entrée précise, une sortie attendue précise. Ce module introduit une approche complémentaire — les tests basés sur les propriétés — puis pose une question plus large : qu'est-ce qui rend du code facile ou difficile à tester ?

Test par l'exemple vs test de propriété

Un test par l'exemple vérifie un cas précis : trier([3, 1, 2]) == [1, 2, 3]. Un test de propriété vérifie une règle qui doit rester vraie pour n'importe quelle entrée valide : "pour toute liste, le résultat trié contient les mêmes éléments, dans un ordre croissant". Hypothesis génère automatiquement des centaines d'entrées variées (y compris des cas limites auxquels on ne pense pas) pour vérifier que la propriété tient.

Un test de propriété avec Hypothesis

from hypothesis import given, strategies as st

@given(st.lists(st.integers()))
def test_trier_conserve_les_elements(liste):
    resultat = sorted(liste)
    assert sorted(resultat) == sorted(liste)          # mêmes éléments
    assert all(resultat[i] <= resultat[i+1] for i in range(len(resultat)-1))  # croissant

Hypothesis exécute ce test avec de nombreuses listes générées automatiquement — vides, avec doublons, avec des nombres négatifs, très longues — et signale le plus petit cas qui fait échouer la propriété s'il en trouve un, ce qu'un jeu d'exemples écrits à la main manque facilement.

Une propriété sur le calcul de remise

from hypothesis import given, strategies as st

@given(st.floats(min_value=0, max_value=10000), st.floats(min_value=0, max_value=1))
def test_remise_ne_rend_jamais_negatif(prix, taux):
    resultat = appliquer_remise(prix, taux)
    assert resultat >= 0    # propriété : jamais de prix négatif, quelle que soit l'entrée valide
Complémentaire, pas remplaçant

Les tests de propriété ne remplacent pas les tests par l'exemple : ils sont excellents pour des fonctions avec des règles mathématiques ou structurelles claires (tri, parsing, calculs), moins adaptés pour vérifier qu'un cas métier précis produit exactement le bon message d'erreur.

Mutation testing : la couverture ne suffit pas

Un taux de couverture de 90% signifie que 90% des lignes s'exécutent pendant les tests — pas que ces lignes sont réellement vérifiées. Le mutation testing (des outils comme mutmut) modifie automatiquement le code source (change un > en >=, un + en -) et relance les tests : si un test ne détecte pas la modification, c'est qu'il ne vérifiait pas vraiment ce bout de code, malgré une couverture à 100%.

Ce qui rend du code testable

La testabilité n'est pas une propriété séparée de la qualité du code — c'est souvent son symptôme le plus visible. Du code avec des dépendances injectées (module 14 — SOLID), des fonctions pures (mêmes entrées, même sortie, aucun effet de bord caché) et des responsabilités bien séparées est mécaniquement plus facile à tester que du code fortement couplé à des singletons globaux ou à des appels réseau directs.

Flaky — échoue parfois sans changement de codeDépendance à un ordre, un timing, ou un état partagé mal isolé
Fragile — casse au moindre changement de détail interneLe test vérifie l'implémentation plutôt que le comportement
Couplé — plusieurs tests échouent ensemble pour une seule causeManque d'isolation entre les tests (mocking insuffisant, état partagé)

Projets de développement web

Jusqu'ici, tu as surtout testé du code qui tourne dans un terminal. Qu'est-ce qu'un framework web ?

Un framework web s'occupe de la partie technique répétitive : recevoir une requête HTTP envoyée par un navigateur ou une application, comprendre quelle URL a été demandée, exécuter le bon morceau de code Python, et renvoyer une réponse. Sans framework, il faudrait réécrire tout ça à la main pour chaque projet. Flask est un micro-framework : il fait le minimum nécessaire et te laisse ajouter ce dont tu as besoin. C'est idéal pour comprendre les mécanismes sans être noyé·e sous les fonctionnalités.

Ta première route

Une route associe une URL à une fonction Python. Voici une mini-API qui expose le catalogue NovaCart : un client (navigateur, application, ou un futur test automatisé) qui appelle /produits reçoit la liste des produits en JSON.

app.py

from flask import Flask, jsonify

app = Flask(__name__)

produits = [
    {"id": 1, "nom": "Casque audio sans fil", "prix": 79.99, "stock": 12},
    {"id": 2, "nom": "Clavier mécanique", "prix": 54.50, "stock": 0},
    {"id": 3, "nom": "Souris ergonomique", "prix": 29.90, "stock": 34},
]

@app.route("/produits")
def liste_produits():
    return jsonify(produits)

if __name__ == "__main__":
    app.run(debug=True)

En lançant python app.py, Flask démarre un serveur local (par défaut sur http://127.0.0.1:5000). Appeler cette adresse suivie de /produits, depuis un navigateur ou avec un outil comme curl, déclenche liste_produits() et renvoie le catalogue en JSON.

Le cycle requête / réponse

C'est le principe fondamental à retenir, celui que tu retrouveras dans toutes les applications web que tu testeras : un client envoie une requête HTTP (une méthode comme GET ou POST, une URL, parfois des données) ; le serveur exécute du code et renvoie une réponse (un contenu, souvent du JSON pour une API, et un code de statut comme 200 pour succès ou 404 pour "introuvable"). Flask fait manipuler ce cycle avec très peu de code, ce qui le rend idéal pour bien le comprendre.

Une route avec un paramètre, et une erreur 404 gérée explicitement

from flask import Flask, jsonify, abort

@app.route("/produits/<int:produit_id>")
def detail_produit(produit_id):
    for produit in produits:
        if produit["id"] == produit_id:
            return jsonify(produit)
    abort(404)

Ici, <int:produit_id> indique à Flask que ce morceau de l'URL est un entier variable, transmis directement à la fonction. Si aucun produit ne correspond, abort(404) renvoie une réponse avec le code de statut 404 — exactement le genre de comportement qu'un test d'API vérifiera plus tard : "que se passe-t-il quand je demande un produit qui n'existe pas ?"

Recevoir des données : une route POST

Une API ne fait pas que renvoyer des données, elle en reçoit aussi. Voici une route qui accepte la création d'une commande NovaCart, en lisant le corps JSON de la requête avec request.get_json() :

Créer une commande

from flask import request

@app.route("/commandes", methods=["POST"])
def creer_commande():
    donnees = request.get_json()
    if "produit_id" not in donnees or "quantite" not in donnees:
        return jsonify({"erreur": "produit_id et quantite requis"}), 400

    return jsonify({"statut": "commande créée", "produit_id": donnees["produit_id"]}), 201

Le deuxième élément du tuple renvoyé (400, 201...) est le code de statut HTTP. C'est une bonne habitude à prendre dès maintenant : une API bien conçue renvoie un code cohérent avec ce qui s'est réellement passé, et c'est précisément ce qu'un test d'API va contrôler.

Et Django, dans tout ça ?

Django est un autre framework Python très utilisé, beaucoup plus complet que Flask : il inclut d'office un système d'administration, une gestion de base de données intégrée (l'ORM), l'authentification, etc. Il convient mieux à de grosses applications avec beaucoup de fonctionnalités "standard". Flask, plus minimaliste, est souvent préféré pour de petites API ou pour apprendre les bases sans se perdre dans la configuration. Tu n'as pas besoin de maîtriser Django pour ce cours : sache simplement qu'il existe, et que les concepts de route, requête et réponse vus ici avec Flask s'y retrouvent sous une autre forme.

Le lien avec la QA

Quand tu testeras une application Flask ou Django plus tard dans ce parcours, tu ne liras pas nécessairement tout le code source. Mais savoir qu'une application web est organisée en routes qui répondent à des endpoints (des URLs précises, comme /produits ou /commandes) change ta façon de penser les tests : pour chaque endpoint, quelles méthodes sont acceptées (GET, POST...) ? Quels codes de statut sont attendus dans quels cas ? Que se passe-t-il avec des données manquantes ou invalides ? C'est exactement la logique que tu appliqueras quand tu aborderas le test d'API plus loin dans le programme.

Le principe du machine learning, en une page

Le machine learning a mauvaise réputation de "boîte noire magique". Le principe de base, lui, est simple : on fournit à un algorithme des exemples (des caractéristiques) accompagnés de la bonne réponse (une étiquette), et il cherche un pattern statistique reliant les deux — sans qu'on lui dise explicitement quelle règle appliquer. scikit-learn est la bibliothèque de référence pour ça en Python "classique" (hors deep learning).

Entraîner un classifieur en trois lignes

from sklearn.model_selection import train_test_split
from sklearn.linear_model import LogisticRegression

X_train, X_test, y_train, y_test = train_test_split(X, y, test_size=0.2)
modele = LogisticRegression()
modele.fit(X_train, y_train)
print(modele.score(X_test, y_test))   # proportion de prédictions correctes sur des données jamais vues

Le point à retenir n'est pas la syntaxe scikit-learn, mais une règle qui protège de la plupart des faux résultats : on n'évalue jamais un modèle sur les données qui lui ont servi à apprendre — train_test_split sépare les deux précisément pour ça, sinon un modèle qui a simplement "appris par cœur" ses exemples semble excellent sans avoir rien généralisé.

Le lien avec la QA

Des outils de test s'appuient de plus en plus sur du machine learning ou des modèles de langage — génération de cas de test, détection d'anomalies dans des résultats d'exécution, correction automatique de sélecteurs cassés ("self-healing"). Ce sont de vrais outils, mais ils restent des assistants : ils proposent, et l'humain valide. Savoir qu'un modèle n'est fiable que sur des données proches de son entraînement — et qu'un bon score peut être trompeur — donne un regard critique utile face à eux.

Le squelette universel d'un jeu Pygame

import pygame
pygame.init()

running = True
while running:
    for evenement in pygame.event.get():
        if evenement.type == pygame.QUIT:
            running = False
    ecran.fill((20, 20, 30))
    pygame.display.flip()
    horloge.tick(60)   # limite la boucle à 60 images/seconde

Pourquoi on ne stocke jamais un mot de passe en clair

Si la base de données de NovaCart était un jour compromise, un mot de passe stocké tel quel ("clémence1985") serait immédiatement lisible par quiconque met la main dessus. C'est pour ça qu'on ne stocke jamais un mot de passe en clair : on stocke son empreinte, calculée par une fonction de hachage.

Une fonction de hachage transforme n'importe quelle entrée en une chaîne de longueur fixe, toujours la même pour la même entrée, et impossible à inverser pour retrouver l'entrée d'origine. Le module hashlib de la bibliothèque standard en propose plusieurs.

Hacher un mot de passe avec hashlib

import hashlib

mot_de_passe = "MotDePasse123!"
empreinte = hashlib.sha256(mot_de_passe.encode()).hexdigest()

print(empreinte)
# 8f7c3a2e9d1b4f6a0c5e8d2b7f1a4c9e3d6b8f0a2c4e6d8b1f3a5c7e9d0b2f4a

NovaCart ne stocke donc jamais le mot de passe saisi à l'inscription : elle calcule son empreinte et ne conserve que celle-ci. À la connexion, elle recalcule l'empreinte du mot de passe saisi et la compare à celle stockée — sans jamais avoir besoin de connaître le mot de passe réel.

Vérifier une connexion par comparaison d'empreintes

def verifier_connexion(mot_de_passe_saisi, empreinte_stockee):
    empreinte_calculee = hashlib.sha256(mot_de_passe_saisi.encode()).hexdigest()
    return empreinte_calculee == empreinte_stockee
SHA-256 seul ne suffit pas en production

L'exemple ci-dessus illustre le principe, mais un vrai système ne se contente pas d'un sha256 nu : il ajoute un sel (une valeur aléatoire propre à chaque utilisateur, pour empêcher deux mots de passe identiques d'avoir la même empreinte) et utilise des algorithmes conçus pour être lents, comme bcrypt ou argon2, afin de rendre les attaques par force brute coûteuses. Retiens le principe ici ; les bons outils existent en bibliothèques dédiées.

Ne jamais faire confiance à une entrée utilisateur

Toute donnée saisie par un utilisateur — un champ de formulaire, un paramètre d'URL, un fichier importé — doit être considérée comme potentiellement hostile tant qu'elle n'a pas été validée. C'est vrai pour une adresse e-mail mal formée comme pour une tentative délibérée de manipulation.

Le cours de SQL du parcours a déjà évoqué les requêtes paramétrées : voici pourquoi elles comptent tant. Comparons deux façons d'utiliser une valeur saisie par le client dans une requête SQL.

Deux façons de construire une requête — une dangereuse, une sûre

# Dangereux : la valeur saisie est collée directement dans le texte de la requête
requete = f"SELECT * FROM clients WHERE email = '{email_saisi}'"
curseur.execute(requete)

# Sûr : la valeur est transmise à part, jamais interprétée comme du SQL
requete = "SELECT * FROM clients WHERE email = %s"
curseur.execute(requete, (email_saisi,))

Dans la première version, email_saisi devient une partie du texte de la requête : une chaîne construite pour contenir des caractères SQL peut en changer le sens et faire exécuter au serveur autre chose que ce qui était prévu — c'est le principe d'une injection SQL. Dans la seconde, la base de données sait dès le départ que email_saisi est une valeur, jamais du code SQL : elle ne peut pas modifier la structure de la requête, quel que soit son contenu. Retiens la règle plutôt que le détail technique de l'attaque : une entrée utilisateur ne doit jamais être concaténée directement dans une requête ou une commande.

Secrets et variables d'environnement

Une clé d'API, un mot de passe de base de données ou un token ne doivent jamais être écrits en dur dans le code source — un dépôt Git garde l'historique de chaque version, donc un secret commité une seule fois reste récupérable même après suppression. La pratique standard consiste à les lire depuis des variables d'environnement, injectées au moment de l'exécution plutôt qu'écrites dans le fichier.

Lire un secret depuis l'environnement, jamais en dur

import os

# Mauvais : la clé apparaît en clair dans le code et dans l'historique Git
CLE_API = "sk-live-a1b2c3d4e5f6"

# Correct : la valeur vient de l'environnement, jamais commitée
CLE_API = os.environ["NOVACART_API_KEY"]
# ou, avec une valeur par défaut si absente :
CLE_API = os.environ.get("NOVACART_API_KEY", "")

En pratique, un fichier .env (non commité — listé dans .gitignore) contient ces valeurs en local, et un fichier .env.example (commité, lui) documente les noms de variables attendus sans leurs vraies valeurs — exactement le pattern déjà utilisé dans le projet API Testing du portfolio.

Ne jamais pickle.load() une source non fiable

import hashlib

def inscrire_client(mot_de_passe):

Décorateurs et générateurs

Deux outils qu'on croise partout dans du code Python "adulte" — y compris dans pytest, dont plusieurs mécanismes (@pytest.fixture, @pytest.mark.parametrize) sont eux-mêmes des décorateurs. Comprendre comment ils fonctionnent démystifie une bonne partie de ce que tu utilises déjà sans le savoir.

Les décorateurs : modifier une fonction sans toucher son code

En Python, une fonction est un objet comme un autre : on peut la stocker dans une variable, la passer en argument, ou en créer une nouvelle qui en "enveloppe" une autre. Un décorateur est exactement ça — une fonction qui prend une fonction en entrée et renvoie une nouvelle fonction, généralement pour ajouter un comportement autour de l'originale sans modifier son code.

Un décorateur qui chronomètre une fonction

import time
from functools import wraps

def chronometre(fonction):
    @wraps(fonction)
    def enveloppe(*args, **kwargs):
        debut = time.time()
        resultat = fonction(*args, **kwargs)
        duree = time.time() - debut
        print(f"{fonction.__name__} a pris {duree:.3f}s")
        return resultat
    return enveloppe

@chronometre
def calculer_total_panier(panier):
    return sum(article["prix"] * article["quantite"] for article in panier)

La syntaxe @chronometre au-dessus de calculer_total_panier est un raccourci pour calculer_total_panier = chronometre(calculer_total_panier) : à chaque appel, c'est en réalité enveloppe qui s'exécute, et elle appelle la fonction d'origine au milieu de son propre travail (ici, avant et après avoir mesuré le temps écoulé).

Pourquoi @wraps(fonction) ?

Sans cette ligne, la fonction décorée "perd" son identité : calculer_total_panier.__name__ renverrait "enveloppe" au lieu de "calculer_total_panier", ce qui complique le débogage et casse la documentation générée automatiquement. @wraps, fourni par le module standard functools, recopie ces métadonnées sur la fonction enveloppante. C'est un détail facile à oublier, mais qu'on retrouve dans quasiment tout décorateur écrit sérieusement.

Générateurs : produire des valeurs une par une avec yield

Une fonction classique calcule un résultat et le renvoie avec return, une seule fois. Une fonction qui contient yield devient un générateur : au lieu de renvoyer une valeur et de s'arrêter, elle "met en pause" à chaque yield et reprend exactement où elle en était à l'appel suivant. C'est utile pour parcourir de grandes quantités de données sans toutes les charger en mémoire d'un coup.

Paginer les commandes NovaCart sans tout charger en mémoire

def pages_de_commandes(commandes, taille_page=50):
    for debut in range(0, len(commandes), taille_page):
        yield commandes[debut:debut + taille_page]

for page in pages_de_commandes(toutes_les_commandes, taille_page=50):
    traiter_page(page)

À chaque tour de la boucle for, Python redemande une valeur au générateur, qui reprend son exécution juste après le yield précédent. Contrairement à une fonction qui renverrait une liste complète de pages, rien n'est calculé avant que la valeur suivante ne soit réellement demandée — c'est ce qu'on appelle l'évaluation paresseuse ("lazy").

Expression génératrice — la version compacte d'une compréhension

# Compréhension de liste : calcule et stocke TOUT immédiatement
totaux = [c["prix"] * c["quantite"] for c in commandes]

# Expression génératrice : ne calcule qu'au fur et à mesure
totaux = (c["prix"] * c["quantite"] for c in commandes)
print(sum(totaux))  # sum() consomme le générateur valeur par valeur

Le module standard itertools fournit des outils prêts à l'emploi pour travailler avec ce genre de séquences, sans jamais tout charger en mémoire.

itertools.chain — enchaîner plusieurs listes de clients

import itertools

clients_paris = ["Clémence", "Yanis"]
clients_lyon = ["Farid", "Inès"]

for client in itertools.chain(clients_paris, clients_lyon):

# Farid

Le lien avec la QA

Un décorateur de type "réessayer en cas d'échec" est exactement le mécanisme derrière certaines stratégies de gestion des tests flaky (des tests instables qui échouent parfois sans changement de code). Et les générateurs deviennent précieux dès qu'un test doit parcourir un très gros jeu de données — un export de logs, un fichier CSV volumineux — sans faire exploser la mémoire de la machine qui fait tourner la suite de tests.

import random
from functools import wraps

def reessayer(nombre_tentatives):
    def decorateur(fonction):
        @wraps(fonction)
        def enveloppe(*args, **kwargs):
            derniere_erreur = None
            for tentative in range(1, nombre_tentatives + 1):
                try:
                    return fonction(*args, **kwargs)
                except ConnectionError as erreur:
                    derniere_erreur = erreur
                    print(f"Tentative {tentative}/{nombre_tentatives} échouée : {erreur}")
            raise derniere_erreur
        return enveloppe
    return decorateur

@reessayer(nombre_tentatives=3)
def appeler_api_novacart():
    if random.random() < 0.7:
        raise ConnectionError("Le serveur NovaCart n'a pas répondu.")
    return {"statut": "ok"}

reessayer(nombre_tentatives) est un décorateur "avec paramètre" : il faut un niveau d'imbrication supplémentaire — une fonction qui renvoie un décorateur, qui lui-même renvoie l'enveloppe — pour que nombre_tentatives reste accessible à chaque appel. C'est le même principe qu'un décorateur simple, avec une couche de plus autour.

Context managers et blocs with

Tu utilises déjà with open(...) as f: depuis le module sur les fichiers. Ce module explique ce qui se passe réellement derrière ce mot-clé, et comment créer ton propre bloc with — une compétence qui éclaire aussi le fonctionnement des fixtures pytest vues au module 20.

Ce que with garantit réellement

with open("commandes.csv") as f: ne se contente pas d'ouvrir un fichier : il garantit que f.close() sera appelé en sortie du bloc, même si une exception est levée à l'intérieur. C'est ce qu'on appelle un context manager — un objet qui définit explicitement ce qui doit se passer à l'entrée et à la sortie d'un bloc de code, peu importe comment on en sort.

Sans with — le risque d'oublier de fermer

f = open("commandes.csv")
donnees = f.read()
# Si une erreur se produit avant cette ligne, f.close() n'est jamais appelé
f.close()

Avec with — la fermeture est garantie

with open("commandes.csv") as f:
    donnees = f.read()
# f.close() est appelé automatiquement ici, erreur ou non

Créer son propre context manager avec une classe

N'importe quel objet peut devenir utilisable avec with à condition de définir deux méthodes spéciales : __enter__, exécutée à l'entrée du bloc, et __exit__, exécutée à la sortie — y compris en cas d'exception.

Une connexion NovaCart qui s'ouvre et se ferme proprement

class ConnexionNovaCart:
    def __enter__(self):
        print("Connexion à la base NovaCart ouverte")
        self.connexion = creer_connexion()
        return self.connexion

    def __exit__(self, type_erreur, valeur_erreur, traceback):
        self.connexion.fermer()
        print("Connexion à la base NovaCart fermée")
        return False  # False : on ne "avale" pas l'exception, elle continue de remonter

with ConnexionNovaCart() as connexion:
    connexion.executer("SELECT * FROM commandes")

Le retour False de __exit__ indique à Python de laisser une éventuelle exception se propager normalement après la fermeture — c'est presque toujours ce qu'on veut : fermer proprement la ressource, sans pour autant cacher l'erreur.

La version courte : contextlib.contextmanager

Écrire une classe complète pour un context manager simple est parfois lourd. Le module standard contextlib permet d'en écrire un à partir d'une simple fonction génératrice : tout ce qui précède le yield correspond à __enter__, tout ce qui le suit correspond à __exit__.

Le même exemple, en version générateur

from contextlib import contextmanager

@contextmanager
def connexion_novacart():
    print("Connexion à la base NovaCart ouverte")
    connexion = creer_connexion()
    try:
        yield connexion
    finally:
        connexion.fermer()
        print("Connexion à la base NovaCart fermée")

with connexion_novacart() as connexion:
    connexion.executer("SELECT * FROM commandes")

Le try / finally autour du yield joue le même rôle que __exit__ : le code après finally s'exécute toujours, que le bloc with se soit terminé normalement ou par une exception.

Ça te rappelle quelque chose ?

C'est exactement le mécanisme derrière une fixture pytest qui utilise yield (module 20) : la partie avant yield est la préparation ("setup"), la partie après est le nettoyage ("teardown"). Une fixture pytest avec yield est, ni plus ni moins, un context manager déguisé.

Le lien avec la QA

Les context managers reviennent constamment dans des tests bien écrits : ouvrir puis fermer une connexion de test, créer puis supprimer un fichier temporaire, activer puis désactiver un mode "simulation" le temps d'un test. La fixture tmp_path de pytest, par exemple, s'appuie sur ce principe pour te fournir un dossier temporaire qui est automatiquement nettoyé après chaque test.

Typing avancé et logging pour du code professionnel

Deux habitudes qui séparent souvent un script "qui marche" d'un code qu'une équipe peut relire, maintenir et déboguer sans perdre de temps : annoter les types, et journaliser proprement plutôt que semer des print() partout.

Annoter son code avec des type hints

Python reste un langage à typage dynamique : rien n'empêche techniquement d'appeler une fonction avec des types inattendus. Mais on peut documenter les types attendus directement dans la signature, avec les type hints — introduits au fil des versions du langage et aujourd'hui largement adoptés dans le code professionnel.

Une fonction sans puis avec type hints

# Sans indication de type : on doit deviner ou aller lire le corps de la fonction
def calculer_total(prix, quantite, remise):
    return prix * quantite * (1 - remise)

# Avec type hints : la signature dit tout, sans avoir à lire le code
def calculer_total(prix: float, quantite: int, remise: float = 0.0) -> float:
    return prix * quantite * (1 - remise)

La syntaxe nom: type annote chaque paramètre, et -> type après les parenthèses annote la valeur renvoyée. Pour des structures plus riches, on utilise list[str], dict[str, float], ou Optional[str] (une valeur qui peut être None).

Types plus riches sur une fonction NovaCart

from typing import Optional

def trouver_client(email: str, clients: list[dict]) -> Optional[dict]:
    for client in clients:
        if client["email"] == email:
            return client
    return None  # Optional[dict] : peut renvoyer un dict, ou rien
Les type hints ne sont pas vérifiés à l'exécution

Un point souvent mal compris : écrire quantite: int n'empêche personne d'appeler la fonction avec quantite="dix" — Python ne lève aucune erreur de lui-même. Les type hints sont avant tout de la documentation exécutable, lue par les éditeurs de code pour l'autocomplétion, et par des outils d'analyse statique comme mypy, qui peuvent, eux, détecter ces incohérences avant l'exécution — typiquement dans une étape de CI dédiée, séparée des tests.

def charger_commande(id_commande: str) -> Resultat[Commande]:
    ...   # Resultat[Commande] : un Resultat spécialisé pour un type Commande précis

TypedDict documente ici qu'une Commande n'est pas "un dict quelconque" mais un dict avec exactement ces clés et ces types — mypy signale une erreur si le code tente d'accéder à une clé absente de la définition. Literal restreint statut aux trois valeurs valides : passer "en_cours" serait détecté avant l'exécution, pas découvert en production.

Utiliser mypy ou pyright en pratique

Écrire des type hints sans jamais les vérifier revient à écrire des tests qu'on ne lance jamais. mypy et pyright (l'un ou l'autre suffit, pas besoin des deux) analysent le code sans l'exécuter et signalent les incohérences de type.

Détecter une incohérence avant l'exécution

# fichier commandes.py

    return prix * quantite

C'est exactement le genre de vérification qu'on place dans une étape dédiée d'un pipeline CI (avant les tests, après le lint) : elle attrape une catégorie entière de bugs — passer le mauvais type à une fonction — sans avoir à écrire le moindre test pour ça.

Documentation, tooling, détection précoce — jamais une garantie totale

Même avec mypy en CI, les type hints restent un filet de sécurité partiel : du code qui contourne le typage (un dict générique passé partout, un Any explicite) échappe à la vérification. L'objectif réaliste n'est pas "zéro bug de type", mais une base de code où l'intention est explicite et où la majorité des erreurs de type se voient avant l'exécution plutôt qu'en production.

Le module logging, une alternative sérieuse à print

print() est parfait pour explorer rapidement un problème, mais pose problème dans un vrai projet : impossible de désactiver certains messages sans supprimer les lignes, aucune indication de gravité, aucune trace de l'heure ni du fichier d'origine. Le module standard logging résout ces trois problèmes.

Configuration de base et niveaux de gravité

Organiser un projet Python

Un script de quelques lignes n'a pas besoin de structure. Un projet qui grossit — plusieurs fichiers, des tests, une CLI (module 31), une CI (module 33) — en a besoin, et une mauvaise organisation coûte cher à corriger une fois le projet avancé.

Le "src layout"

Deux façons courantes de structurer un projet : le code directement à la racine ("flat layout"), ou dans un dossier src/ ("src layout"). Le second est aujourd'hui recommandé car il empêche d'importer accidentellement le code non installé — une erreur fréquente qui masque de vrais problèmes d'import lorsqu'on teste un package avant de l'installer correctement.

La direction des dépendances

Une règle simple évite la plupart des imports circulaires : les modules de bas niveau (accès aux données, clients API) ne doivent jamais importer les modules de haut niveau (logique métier, CLI) qui les utilisent — la dépendance va dans un seul sens.

Import circulaire : deux modules qui dépendent l'un de l'autre

# rapport.py

# ImportError au chargement : dépendance circulaire

La correction typique : extraire ce dont les deux ont besoin (souvent une classe de données ou une interface, module 13) dans un troisième module que les deux importent, sans dépendre l'un de l'autre.

Le rôle de __init__.py

Un __init__.py (même vide) marque un dossier comme package Python importable. Il sert aussi à définir l'API publique d'un package — ce qu'un fichier from novacart_qa import Verification peut réellement importer, sans exposer les détails internes de chaque sous-module.

# src/novacart_qa/__init__.py
from .verification import Verification
from .cli import main

__all__ = ["Verification", "main"]   # ce que "from novacart_qa import *" expose
Le bon moment pour structurer

Structurer un script de 30 lignes en package avec src/, sous-modules et __init__.py est de la sur-ingénierie. Le signal à surveiller : le projet devient difficile à naviguer, ou un import commence à casser de façon inattendue — c'est à ce moment que la structure apporte une vraie valeur, pas avant.

Partie 9 · Module 35

asyncio et la concurrence

Quand un programme attend beaucoup — des réponses réseau, par exemple — il passe le plus clair de son temps inactif. asyncio permet d'exécuter plusieurs de ces attentes en même temps plutôt que l'une après l'autre, sans utiliser plusieurs threads.

Le problème : des appels API en série

Séquentiel : chaque appel attend le précédent

import requests, time

def verifier_tous(urls):
    resultats = []
    for url in urls:
        resultats.append(requests.get(url).status_code)
    return resultats

# 10 URLs à 300ms chacune ≈ 3 secondes, en attendant chaque réponse l'une après l'autre

async / await : attendre sans bloquer

import asyncio, httpx

async def verifier_une(client, url):
    reponse = await client.get(url)          # rend la main pendant l'attente réseau
    return reponse.status_code

async def verifier_tous(urls):
    async with httpx.AsyncClient() as client:
        taches = [verifier_une(client, url) for url in urls]
        return await asyncio.gather(*taches)  # exécute les 10 appels en concurrence

resultats = asyncio.run(verifier_tous(urls))
# Les 10 appels partent quasiment en même temps ≈ 300ms au lieu de 3 secondes

await ne bloque pas le programme : pendant qu'une requête attend sa réponse réseau, l'event loop d'asyncio peut avancer sur une autre tâche. asyncio.gather lance plusieurs coroutines et attend qu'elles se terminent toutes.

Concurrence, pas parallélisme

asyncio tourne sur un seul thread : il ne fait jamais deux calculs en même temps, il alterne intelligemment entre des tâches qui attendent. C'est excellent pour des opérations I/O-bound (réseau, disque) où le temps est passé à attendre — inutile pour des calculs CPU-bound (module 36) où il n'y a pas d'attente à combler.

Où ça sert vraiment en QA

Un cas d'usage concret : vérifier que 50 endpoints d'une API répondent correctement. En séquentiel, un test lent à 300ms par appel prend 15 secondes. En concurrent avec asyncio.gather, il peut descendre sous la seconde — une différence qui compte directement sur le temps d'exécution d'une suite de tests.

Partie 9 · Module 36

Threading, multiprocessing et le GIL

Le module précédent a montré asyncio pour la concurrence I/O-bound sur un seul thread. Ce module couvre les deux autres outils de parallélisme de Python — et explique pourquoi le choix entre eux dépend d'une contrainte particulière au langage : le GIL.

Le GIL, en une explication concrète

Le Global Interpreter Lock (GIL) est un verrou interne à l'interpréteur CPython qui garantit qu'un seul thread exécute du bytecode Python à la fois, même sur une machine à plusieurs cœurs. Conséquence directe : le module threading n'accélère jamais un calcul pur Python, quel que soit le nombre de threads lancés.

Threading : utile pour l'attente, pas le calcul

import threading, time

def telecharger(url, resultats, index):
    time.sleep(0.5)              # simule une attente réseau — le GIL est relâché ici
    resultats[index] = f"contenu de {url}"

urls = ["url1", "url2", "url3"]
resultats = [None] * len(urls)
threads = [threading.Thread(target=telecharger, args=(u, resultats, i)) for i, u in enumerate(urls)]
for t in threads: t.start()
for t in threads: t.join()
# ≈ 0.5s au total, pas 1.5s : le GIL est relâché pendant les opérations d'I/O (réseau, disque)

Le GIL est relâché pendant les opérations bloquantes (réseau, disque, time.sleep) — c'est pour cela que threading aide bien pour des tâches d'I/O, exactement comme asyncio, mais avec un modèle de programmation différent (pas d'async/await).

Multiprocessing : contourner le GIL pour du vrai calcul

from concurrent.futures import ProcessPoolExecutor

def calcul_lourd(n):
    return sum(i * i for i in range(n))   # CPU-bound : aucune attente à combler

with ProcessPoolExecutor() as executor:
    resultats = list(executor.map(calcul_lourd, [10_000_000] * 4))
# Chaque processus a son propre interpréteur Python et son propre GIL :
# les 4 calculs tournent vraiment en parallèle sur 4 cœurs

multiprocessing lance des processus séparés, chacun avec sa propre mémoire et son propre GIL — un vrai parallélisme, au prix d'un coût de démarrage plus élevé et de données qui doivent être sérialisées pour passer d'un processus à l'autre.

Choisir le bon outil

SituationOutil
Beaucoup d'attente réseau, code déjà écrit en asyncasyncio (module 35)
Beaucoup d'attente réseau/disque, code existant non asynchronethreading
Calcul intensif (CPU-bound) : traitement d'image, calcul numériquemultiprocessing
Le piège classique

Utiliser threading pour accélérer un calcul CPU-bound est l'erreur la plus fréquente sur ce sujet : le GIL empêche tout gain, et le code devient plus complexe pour rien. Vérifier d'abord si la tâche est I/O-bound (attente) ou CPU-bound (calcul) est la question qui détermine le bon outil.

Exercice

Une équipe QA doit (1) appeler 20 endpoints d'API différents pour vérifier leur disponibilité, et (2) calculer une somme de contrôle (checksum) sur 20 gros fichiers locaux. Pour chaque tâche, indique si threading ou multiprocessing est le plus adapté, et pourquoi.

Voir la correction

(1) Appeler 20 endpoints : I/O-bound — la majorité du temps est passée à attendre le réseau. threading (ou asyncio) convient bien : le GIL est relâché pendant l'attente réseau, donc les 20 appels peuvent réellement se chevaucher dans le temps.

(2) Calculer un checksum sur 20 fichiers : CPU-bound — le calcul du checksum sollicite le processeur en continu, sans attente à combler. threading n'apporterait aucun gain à cause du GIL ; multiprocessing permet de répartir réellement les 20 calculs sur plusieurs cœurs.

Partie 9 · Module 37

Ingénierie API côté client

Le cours "Qualité Logicielle Automatisée" couvre le test d'API. Ce module aborde l'autre face : écrire un client Python robuste pour consommer une API — ce qu'un outil d'automatisation ou un script de vérification fait en permanence.

Le strict minimum ne suffit pas

Fragile : aucune gestion d'erreur

import requests

def recuperer_commande(id_commande):
    reponse = requests.get(f"https://api.novacart.com/commandes/{id_commande}")
    return reponse.json()   # plante si le réseau échoue, si le JSON est invalide, si le statut est une erreur

Ce code suppose que le réseau répond toujours, instantanément, avec du JSON valide. En pratique, un réseau peut être lent, une API peut renvoyer une erreur 500, ou ne jamais répondre — un client robuste doit gérer ces trois cas explicitement.

Timeouts, retries et gestion des statuts

import requests
from requests.adapters import HTTPAdapter, Retry

def creer_session():
    session = requests.Session()
    retries = Retry(total=3, backoff_factor=0.5, status_forcelist=[500, 502, 503])
    session.mount("https://", HTTPAdapter(max_retries=retries))
    return session

def recuperer_commande(id_commande, session):
    try:
        reponse = session.get(
            f"https://api.novacart.com/commandes/{id_commande}",
            timeout=5,                       # jamais d'appel sans timeout
        )
        reponse.raise_for_status()           # lève une exception sur 4xx/5xx (module 11)
        return reponse.json()
    except requests.exceptions.Timeout:
        raise RuntimeError(f"L'API n'a pas répondu en 5s pour la commande {id_commande}")
    except requests.exceptions.HTTPError as e:
        raise RuntimeError(f"Erreur API ({reponse.status_code}) pour {id_commande}") from e

Trois protections essentielles : un timeout explicite (jamais d'attente infinie), des retries automatiques avec backoff progressif pour les erreurs temporaires (5xx), et raise_for_status() pour transformer un statut d'erreur HTTP en exception Python explicite plutôt qu'un JSON silencieusement incohérent.

Réutiliser une session

Créer une requests.Session() une fois et la réutiliser pour tous les appels (plutôt qu'un requests.get à chaque fois) réutilise la connexion TCP sous-jacente — un gain de performance réel sur un client qui fait beaucoup d'appels, dans le même esprit que la performance mesurée au module 34.

Isoler le client pour le tester

Encapsuler les appels API dans une classe ou un module dédié (module 32 — architecture) rend le reste du code testable avec un mock (module 21) plutôt que dépendant d'un vrai réseau à chaque exécution de test — le même principe d'inversion des dépendances que le module 14 (SOLID).

Partie 9 · Module 38

Python et les bases de données

Le cours "Qualité Logicielle Automatisée" couvre SQL. Ce module montre comment interagir avec une base de données depuis Python — utile pour vérifier l'état d'une base après un test, ou préparer des données de test.

sqlite3 : intégré, sans installation

import sqlite3

with sqlite3.connect("novacart.db") as connexion:   # context manager : commit/rollback auto
    curseur = connexion.cursor()
    curseur.execute(
        "SELECT id, statut FROM commandes WHERE client_id = ?", (42,)
    )
    for id_commande, statut in curseur.fetchall():
        print(id_commande, statut)

sqlite3 fait partie de la bibliothèque standard — aucune installation nécessaire, une base entière tient dans un seul fichier. Excellent pour des tests, des scripts, ou des prototypes ; une base comme PostgreSQL prend le relais pour une application en production avec plusieurs utilisateurs concurrents.

Requêtes paramétrées : la seule façon sûre

Dangereux : injection SQL (voir aussi module 27, cybersécurité)

id_client = input("ID client : ")
curseur.execute(f"SELECT * FROM commandes WHERE client_id = {id_client}")
# Une entrée comme "1 OR 1=1" renvoie TOUTES les commandes, pas seulement celles du client 1

Sûr : le paramètre est transmis séparément de la requête

curseur.execute("SELECT * FROM commandes WHERE client_id = ?", (id_client,))
# Le pilote traite id_client comme une donnée, jamais comme du SQL exécutable

La règle est absolue, sans exception : ne jamais construire une requête SQL par concaténation ou f-string avec une valeur venant de l'utilisateur ou d'une source externe — toujours passer par les paramètres (? avec sqlite3, %s avec d'autres pilotes).

Un aperçu des ORM

Un ORM (Object-Relational Mapper) comme SQLAlchemy représente les lignes d'une table comme des objets Python, évitant d'écrire du SQL brut pour les opérations courantes :

from sqlalchemy import select
from sqlalchemy.orm import Session

with Session(moteur) as session:
    commandes = session.scalars(
        select(Commande).where(Commande.client_id == 42)
    ).all()
    for commande in commandes:
        print(commande.id, commande.statut)   # objet Python, pas un tuple brut

Un ORM protège nativement contre l'injection SQL (les paramètres passent toujours par des valeurs liées) et rend le code plus proche du reste de la base orientée objet — au prix d'une couche d'abstraction supplémentaire à comprendre pour déboguer une requête lente ou inattendue.

Toujours fermer la connexion

Utiliser with sqlite3.connect(...) (module 12) garantit que la transaction est validée (commit) ou annulée (rollback) automatiquement, et que la connexion se libère même si une exception survient au milieu de la requête — une connexion oubliée ouverte finit par épuiser les connexions disponibles sur une base partagée.
