Partie 1 · Module 01

Qu'est-ce que Git ?

Avant Git, il fallait imaginer autre chose : des dossiers nommés site_final, site_final_v2, site_final_v2_VRAI. Un système de contrôle de version comme Git résout ce problème en gardant l'historique complet de chaque changement, avec la possibilité de revenir à n'importe quel état passé, de comparer deux versions, ou de travailler sur plusieurs idées en parallèle sans qu'elles se marchent dessus.

Git a été créé en 2005 par Linus Torvalds (le créateur de Linux) pour gérer le développement du noyau Linux — un projet avec des milliers de contributeurs. C'est un outil distribué : chaque copie du projet contient l'historique complet, pas seulement les derniers fichiers. Concrètement, ça veut dire que Git fonctionne très bien sans connexion internet — tu peux committer, créer des branches, consulter tout l'historique en local. Internet n'entre en jeu que lorsque tu veux synchroniser ton travail avec une copie distante.

Git et GitHub, ce n'est pas la même chose

Confusion très courante chez les débutants — et normale, vu qu'on les apprend souvent ensemble.

GitGitHub
Un logiciel installé sur ton ordinateurUn site web qui héberge des dépôts Git
Gère l'historique en local, sans compte, sans internetAjoute la collaboration : pull requests, issues, revue de code, CI
Créé en 2005, open sourceCréé en 2008, racheté par Microsoft en 2018
Seul système sérieux du marchéAlternatives : GitLab, Bitbucket — GitHub reste le plus utilisé

Autrement dit : tu pourrais utiliser Git toute ta carrière sans jamais toucher à GitHub. Mais en entreprise, la quasi-totalité des équipes combinent les deux — Git pour l'historique, GitHub pour le travail à plusieurs. C'est ce combo qu'on construit dans ce cours.

Exercice

Vrai ou faux : "Git a besoin d'une connexion internet pour fonctionner." Justifie ta réponse en une phrase.

Voir la correction

Faux. Git est un outil distribué et local : commit, branches, historique, tout fonctionne sans réseau. Internet n'est nécessaire que pour synchroniser avec un dépôt distant comme GitHub (via push/pull), ce qu'on verra au module 7.

Partie 1 · Module 02

Le cycle de vie d'un fichier

Un fichier suivi par Git traverse trois zones. Comprendre ces trois zones, c'est comprendre 80 % de Git.

ZoneCe que ça veut direCommande pour y arriver
Répertoire de travailTes fichiers tels qu'ils sont sur le disque, modifiés ou non—
Zone de staging (index)Les changements que tu as choisis d'inclure dans le prochain commitgit add
Dépôt (historique)Les changements enregistrés définitivement, avec un messagegit commit

Le point important : git add ne "sauvegarde" rien de définitif, ça prépare juste ce qui ira dans le prochain commit. Tu peux modifier trois fichiers, n'en add que deux, et committer seulement ces deux-là — le troisième reste en attente pour un commit séparé, plus propre.

Démarrer le suivi du projet livret-mission

cd livret-mission
git init                     # crée le dépôt (dossier caché .git)
git status                   # que voit Git en ce moment ?
git add site/index.html      # met ce fichier en staging
git add .                    # ou : tout ce qui a changé
git commit -m "Ajout de la page d'accueil"
git log                      # l'historique des commits

.gitignore : ce qu'on ne suit jamais

Certains fichiers ne doivent jamais entrer dans l'historique : des secrets (clés d'API, mots de passe), des fichiers générés automatiquement, ou des dossiers volumineux comme node_modules/ ou __pycache__/. Un fichier .gitignore à la racine du projet liste ces exclusions.

__pycache__/
*.pyc
.env
node_modules/
.DS_Store
Le piège classique

Un fichier déjà suivi par Git n'est pas retiré rétroactivement si tu l'ajoutes après coup à .gitignore — il faut d'abord faire git rm --cached nom_du_fichier. C'est pour ça qu'on écrit son .gitignore dès le tout premier commit, avant d'ajouter quoi que ce soit de sensible.

Exercice

Tu viens de modifier trois fichiers dans livret-mission : site/index.html, pdf/generate.py et un fichier temporaire notes.txt que tu ne veux pas committer. Écris la séquence de commandes qui committe uniquement les deux premiers, avec le message "Corrige la mise en page et la génération PDF".

Voir la correction 
git add site/index.html pdf/generate.py
git commit -m "Corrige la mise en page et la génération PDF"

notes.txt n'étant jamais passé par git add, il reste dans le répertoire de travail, non suivi — libre à toi de l'ajouter à .gitignore s'il doit rester définitivement hors du dépôt.

Partie 1 · Module 03

Créer, changer, fusionner une branche

Une branche est simplement une étiquette mobile qui pointe vers un commit — pas une copie du projet, juste un pointeur. C'est ce qui rend les branches Git légères et quasi instantanées à créer, contrairement à d'autres systèmes plus anciens.

La branche par défaut s'appelle généralement main. En pratique, on ne travaille presque jamais directement dessus : on crée une branche de fonctionnalité pour chaque tâche, on y committe, puis on la fusionne dans main une fois le travail terminé et validé.

Ajouter le mode hors-ligne de la PWA sans toucher à main

git switch -c feature/pwa-offline   # crée la branche et bascule dessus
# ... on travaille, on committe ...
git add pwa/service-worker.js
git commit -m "Ajoute la mise en cache hors-ligne"

git switch main                     # retour sur main
git merge feature/pwa-offline       # rapatrie le travail dans main

git switch -c est la commande moderne (elle remplace l'ancien git checkout -b, qu'on croise encore beaucoup en entreprise — les deux font la même chose).

Fast-forward ou commit de fusion ?

Si main n'a reçu aucun nouveau commit depuis la création de ta branche, Git fait un fast-forward : il avance simplement le pointeur de main, sans créer de commit supplémentaire. Si main a évolué entre-temps, Git crée un commit de fusion qui relie les deux historiques.

Fast-forward :          Commit de fusion :
main → A─B─C            main → A─B────────M
             ╲feature              ╲      ╱
              (rien à fusionner)     C─D──╯ feature
Exercice

Écris la séquence de commandes pour créer une branche fix/lien-casse depuis main, corriger un lien dans site/index.html, committer, puis fusionner cette correction dans main.

Voir la correction 
git switch main
git switch -c fix/lien-casse
git add site/index.html
git commit -m "Corrige le lien vers le formulaire"
git switch main
git merge fix/lien-casse
Partie 1 · Module 04

Résoudre un conflit de fusion

Un conflit survient quand Git ne peut pas décider tout seul comment combiner deux changements — typiquement, deux branches ont modifié les mêmes lignes du même fichier de façons différentes. Ce n'est pas une erreur ni un échec : c'est Git qui te demande, légitimement, de trancher.

Git signale le conflit dans le fichier lui-même

<<<<<<< HEAD
<title>Livret de mission — v1</title>
=======
<title>Livret de mission — Édition 2026</title>
>>>>>>> feature/renommage

Tout ce qui est entre <<<<<<< HEAD et ======= vient de ta branche actuelle ; entre ======= et >>>>>>> vient de la branche qu'on fusionne. Résoudre le conflit consiste à éditer le fichier pour ne garder que le résultat voulu, en supprimant les marqueurs.

- <title>Livret de mission — v1</title>
+ <title>Livret de mission — Édition 2026</title>

Une fois le fichier corrigé à la main

git add site/index.html      # marque le conflit comme résolu
git commit                   # Git propose déjà un message de fusion
Bon réflexe

En cas de doute sur ce qui doit vraiment rester, ne devine pas : va relire le contexte des deux commits (git log), ou demande à la personne qui a écrit l'autre changement. Un conflit mal résolu à la va-vite est une source classique de régression.

Exercice

Voici un conflit sur le fichier pdf/generate.py :

<<<<<<< HEAD
MARGE_PAGE = 20
=======
MARGE_PAGE = 15
>>>>>>> feature/mise-en-page

Tu décides de garder la marge de 15. Écris le contenu final du fichier après résolution, puis les commandes pour finaliser la fusion.

Voir la correction 
MARGE_PAGE = 15

Tous les marqueurs de conflit disparaissent — il ne reste que la ligne choisie. Puis :

git add pdf/generate.py
git commit
Partie 1 · Module 05

Revenir en arrière sans casse

Git offre plusieurs façons d'annuler quelque chose — mais elles n'ont pas du tout le même niveau de danger. Les confondre est l'une des façons les plus sûres de perdre du travail ou de mettre une équipe entière dans l'embarras.

CommandePortéeDangerQuand l'utiliser
git restore fichierUn fichier, non commitéSûrAnnuler des modifications locales pas encore ajoutées
git revert <commit>Un commit précisSûrAnnuler un commit déjà poussé, en créant un nouveau commit d'annulation
git reset --softDéplace l'historique localPrudenceRefaire un commit local pas encore partagé
git reset --hardRéécrit l'historique ET les fichiersDestructeurUniquement sur du travail 100% local, jamais partagé
Règle à ne jamais transgresser

Ne fais jamais git reset --hard (ou tout autre réécriture d'historique) sur une branche déjà poussée et partagée, comme main. Ça force ensuite tout le monde à resynchroniser son historique local, souvent dans la confusion. Sur une branche déjà partagée, la commande sûre pour annuler un commit est git revert : elle ajoute un nouveau commit qui inverse les changements, sans réécrire ce qui existe déjà.

Annuler proprement un commit déjà poussé sur main

git log --oneline           # repérer le hash du commit fautif, ex. a1b2c3d
git revert a1b2c3d          # crée un nouveau commit qui annule celui-ci
git push
Exercice

Un commit cassant la génération du PDF a été poussé sur main il y a deux heures, et un collègue a déjà récupéré ces changements. Quelle commande utilises-tu pour l'annuler, et pourquoi pas une autre ?

Voir la correction

git revert <hash-du-commit>. Le commit est déjà partagé (le collègue l'a récupéré) : réécrire l'historique avec git reset --hard désynchroniserait son dépôt local. git revert ajoute un commit d'annulation visible dans l'historique, sans rien casser chez personne.

Un compte GitHub gratuit suffit largement pour tout ce cours, y compris les dépôts privés (illimités depuis 2019) et GitHub Actions dans une certaine limite de minutes gratuites par mois. Une fois inscrit, la première étape est de créer un dépôt (repository) pour livret-mission.

Aperçu illustratif de la page de création d'un dépôt.

Une fois le dépôt créé côté GitHub, deux chemins possibles : partir de zéro sur GitHub puis clone en local (module suivant), ou — ton cas — relier un dossier local existant à ce nouveau dépôt vide :

cd livret-mission

Partie 2 · Module 07

Clone, remote, push, pull, fetch

git clone télécharge un dépôt distant complet, avec tout son historique, et configure automatiquement origin comme raccourci vers son adresse.

git clone https://github.com/ton-compte/livret-mission.git
cd livret-mission
git remote -v          # vérifie l'adresse d'origin (lecture et écriture)

HTTPS demande ton mot de passe ou un token à chaque envoi (ou une seule fois si tu utilises un gestionnaire d'identifiants) ; SSH utilise une paire de clés générée une fois pour toutes. En entreprise, SSH est souvent la norme pour éviter de ressaisir des identifiants en boucle.

Trois commandes qu'on confond souvent

CommandeCe qu'elle fait
git fetchTélécharge les nouveautés distantes, sans toucher à ton travail local
git pullfetch + fusion automatique dans ta branche courante
git pushEnvoie tes commits locaux vers le dépôt distant

git fetch est le choix le plus sûr quand tu veux juste "voir" où en sont les autres avant de décider comment intégrer leurs changements — git pull fusionne tout de suite, ce qui peut créer un conflit surprise si tu avais des changements locaux en cours.

Exercice

Quelle est la différence concrète entre git fetch et git pull, et dans quel cas préférerais-tu fetch ?

Voir la correction

fetch récupère les commits distants sans les fusionner dans ta branche — tu peux les inspecter avant d'agir. pull fait la même chose puis fusionne immédiatement. On préfère fetch quand on a des changements locaux en cours et qu'on veut d'abord vérifier ce qui a changé côté distant avant de risquer un conflit.

Une issue GitHub sert à suivre un bug, une amélioration ou une tâche — l'équivalent d'un ticket Jira (vu au module 22 du cours QA), mais intégré directement au dépôt de code. En tant que futur testeur, c'est probablement l'outil GitHub que tu utiliseras le plus souvent au quotidien.

Aperçu illustratif d'une issue.

Une bonne issue reprend la même rigueur qu'un bon rapport de bug (module 22, cours QA) : titre précis, étapes de reproduction, résultat attendu vs obtenu, environnement. Les labels (bug, enhancement, documentation...) et les assignees permettent de trier et répartir le travail. Petit plus utile : écrire Fixes #14 dans le message d'un commit ou d'une pull request ferme automatiquement l'issue correspondante dès la fusion.

Exercice

Rédige le titre et la description d'une issue pour ce bug : sur mobile, le bouton "Télécharger le PDF" du livret-mission ne réagit pas au premier clic, il faut cliquer deux fois.

Voir la correction

Partie 2 · Module 09

Pull requests : créer et décrire

Une pull request (PR) propose de fusionner une branche dans une autre — le plus souvent, ta branche de fonctionnalité vers main. C'est le cœur du travail collaboratif sur GitHub : au lieu de pousser directement sur main, tu ouvres une PR, quelqu'un la relit, et elle n'est fusionnée qu'une fois validée.

git push -u origin feature/pwa-offline
# puis, sur GitHub : "Compare & pull request"
github.com/ton-compte/livret-mission/pull/new
base: main ← compare: feature/pwa-offline
TitleAjoute le mode hors-ligne à la PWA
DescriptionFixes #9 — voir détail ci-dessous
Draft pull requestCreate pull request

Aperçu illustratif de la création d'une pull request.

Une bonne description de PR répond à trois questions : qu'est-ce que ce changement fait, pourquoi, et comment le vérifier. Beaucoup d'équipes utilisent un template (fichier .github/PULL_REQUEST_TEMPLATE.md) qui pré-remplit ces sections à chaque nouvelle PR.

PR "brouillon" (draft)

Une PR peut être ouverte en mode draft — visible par l'équipe, mais explicitement marquée comme non prête à être fusionnée ni même relue en détail. Pratique pour partager un travail en cours, demander un avis préliminaire, ou déclencher la CI sans demander une revue complète.

Exercice

Écris une description de PR pour la branche feature/pwa-offline qui ajoute la mise en cache hors-ligne du livret-mission et corrige l'issue #9.

Voir la correction

Ce que ça fait : ajoute un service worker qui met en cache les pages consultées, pour un accès hors-ligne sur intervention.
Pourquoi : les équipes sur le terrain signalent une couverture réseau instable lors de leurs interventions (Fixes #9).
Comment vérifier : ouvrir le site, naviguer sur 2-3 pages, couper le réseau, recharger — les pages visitées doivent rester accessibles.

Partie 2 · Module 10

La revue de code

La revue de code (code review) est l'étape où un ou plusieurs collègues examinent une pull request avant fusion. En tant que testeur, tu seras autant relu (sur tes scripts de test) que relecteur (sur le code applicatif) — savoir lire une diff avec méthode est une compétence à part entière.

Trois issues possibles pour une revue :

VerdictCe que ça signifie
ApproveLe changement est bon, prêt à être fusionné
CommentRemarques sans bloquer la fusion
Request changesDes modifications sont nécessaires avant de pouvoir fusionner

Les commentaires peuvent être laissés directement sur une ligne précise de la diff, et peuvent inclure une suggestion — un bout de code que l'auteur accepte ou rejette en un clic.

def calcule_total(commande):
- return sum(l.prix for l in commande.lignes)
+ return sum(l.prix * l.quantite for l in commande.lignes)

💬 Commentaire attaché : "Le total actuel ignore la quantité — voir la suggestion ci-dessus."

Donner un bon feedback

Commente le code, pas la personne ; distingue ce qui est bloquant de ce qui est une préférence ; explique le pourquoi, pas seulement le quoi. Ces réflexes comptent particulièrement en alternance, où tu seras souvent le plus junior — savoir relire proprement, même sans trancher, est déjà remarqué.

Exercice

Un relecteur a mis "Request changes" sur ta PR avec un commentaire pertinent. Quelle est la bonne suite d'actions ?

Voir la correction

Corriger le code sur ta branche locale, committer la correction, la pousser — la PR se met à jour automatiquement (pas besoin d'en recréer une). Répondre au commentaire pour indiquer que c'est corrigé, puis attendre une nouvelle relecture ou une ré-approbation avant fusion.

Partie 2 · Module 11

Fusionner et protéger une branche

Au moment de fusionner une PR approuvée, GitHub propose trois stratégies :

StratégieEffet sur l'historiqueQuand la choisir
Merge commitGarde tous les commits de la branche + un commit de fusionHistorique détaillé souhaité, branches longues
Squash and mergeCompresse toute la PR en un seul commit propre sur mainLe plus courant en équipe : historique de main lisible, un commit = une fonctionnalité
Rebase and mergeRejoue les commits de la branche un par un sur main, sans commit de fusionHistorique linéaire, équipes plus expérimentées avec Git

En 2026, squash and merge reste le choix par défaut le plus répandu dans les équipes produit : il garde l'historique de main facile à parcourir, même si la branche de travail contenait quinze petits commits "wip" ou "fix typo".

Protéger la branche main

Une branch protection rule empêche de pousser directement sur main et impose des conditions avant toute fusion — c'est ce qui rend la revue de code réellement obligatoire, et pas juste une convention d'équipe.

github.com/.../settings/branches
Require a pull request before merging☑
Require approvals☑ (1 minimum)
Require status checks to pass☑ (CI Playwright)
Do not allow bypassing the above☑

Aperçu illustratif des règles de protection de branche.

Exercice

Une PR contient douze commits, dont plusieurs "fix typo" et "wip". L'équipe veut un historique de main propre, une fonctionnalité = un commit. Quelle stratégie de fusion choisir ?

Voir la correction

Squash and merge — les douze commits deviennent un seul commit propre sur main, avec un message unique décrivant la fonctionnalité dans son ensemble.

Partie 2 · Module 12

README, Wiki, GitHub Pages

Le fichier README.md, à la racine du dépôt, est la première chose que tout le monde voit — recruteur y compris si ton profil GitHub est public. Il mérite autant de soin que le code lui-même.

Ce qu'un bon README contient

  • Une phrase qui dit ce que fait le projet, et pour qui
  • Comment l'installer et le lancer en local (les vraies commandes, testées)
  • Une capture d'écran ou un GIF, si c'est visuel
  • Comment lancer les tests — précieux pour montrer ta pratique QA
  • La stack technique utilisée

Extrait de README pour livret-mission

# Livret de mission

Application pour les équipes de terrain : site web, génération
de PDF et PWA installable hors-ligne.

## Installation
pip install -r requirements.txt
python pdf/generate.py

## Tests
pytest tests/ --headed

Le Wiki d'un dépôt convient à une documentation plus longue et évolutive (procédures internes, décisions d'architecture) qui n'a pas sa place dans un README déjà long. GitHub Pages, lui, héberge gratuitement un site statique directement depuis le dépôt — exactement adapté à un projet comme le site du livret-mission, sans serveur à gérer.

Exercice

Liste, dans l'ordre, les cinq sections que tu mettrais dans le README de livret-mission pour qu'un recruteur qui le découvre comprenne le projet en moins d'une minute.

Voir la correction

1) Une phrase de résumé du projet et son contexte réel (usage sur le terrain). 2) Un aperçu visuel (capture ou GIF). 3) La stack technique. 4) Installation et lancement. 5) Comment lancer les tests — c'est cette dernière section qui parle directement à un recruteur QA.

Partie 2 · Module 13

Projects : organiser le travail

GitHub Projects est un tableau Kanban intégré au dépôt, qui relie directement issues et pull requests aux colonnes d'avancement — pas besoin d'un outil externe séparé pour un petit projet ou une petite équipe.

ColonneContenu
To doIssues pas encore prises en charge
In progressIssue assignée, branche créée, travail en cours
In reviewPR ouverte, en attente de relecture
DonePR fusionnée, issue fermée

Des règles d'automatisation peuvent déplacer une carte toute seule — par exemple, faire glisser automatiquement une issue vers "Done" dès que la PR qui la referme est fusionnée.

Exercice

Trois cartes existent sur le board de livret-mission : "Corriger le bug du double-clic" (issue ouverte, personne assignée), "Ajouter le mode hors-ligne" (PR ouverte, en attente de relecture), "Renommer le titre de la page" (PR fusionnée hier). Place chacune dans la bonne colonne.

"Corriger le bug du double-clic" → To do. "Ajouter le mode hors-ligne" → In review. "Renommer le titre de la page" → Done.

GitHub Desktop

Installer et découvrir l'interface

Partie 3 · Module 15

Le workflow quotidien

Le geste répété toute la journée avec GitHub Desktop tient en quatre étapes, sans jamais toucher au terminal :

ÉtapeDans GitHub DesktopÉquivalent en ligne de commande
1. Récupérer les nouveautésBouton "Fetch origin"git fetch
2. Revoir ses changementsOnglet "Changes", diff colorée par fichiergit diff
3. CommitterChamp résumé + description, bouton "Commit to ..."git add -A && git commit
4. EnvoyerBouton "Push origin"git push

Un détail pratique : dans l'onglet "Changes", chaque fichier a une case à cocher — décocher un fichier revient à ne pas faire son git add, exactement comme au module 2. Tu peux même cocher seulement certaines lignes d'un fichier modifié, pour un commit encore plus précis.

L'onglet "History" affiche l'équivalent de git log, avec la diff de chaque commit consultable en un clic — pratique pour retrouver "c'est quand exactement que j'ai cassé ça".

Partie 3 · Module 17

Nouveauté 2026 : worktrees et Copilot

GitHub Desktop 3.6 (juin 2026) a ajouté deux évolutions notables, à connaître même si tu ne les utilises pas encore au quotidien — ça se remarque en entretien de savoir ce qui bouge dans l'écosystème.

Les worktrees

Un worktree permet de travailler sur plusieurs branches en parallèle, chacune dans son propre dossier, sans avoir à cloner le dépôt plusieurs fois ni à faire des allers-retours de stash/switch. Concrètement : tu peux avoir feature/pwa-offline ouvert dans un dossier pendant que fix/lien-casse tourne dans un autre, en parallèle, sans jamais perdre de contexte ni interrompre ce que tu étais en train de faire.

Copilot intégré à Desktop

Deux usages concrets ont été ajoutés : la génération de messages de commit (qui respecte les conventions du dépôt si un fichier .github/copilot-instructions.md existe), et une proposition de résolution lors d'un conflit de fusion — Copilot explique ce qui diverge entre les deux versions et propose une fusion, que tu peux accepter, modifier ou rejeter.

🤖 Copilot : "Les deux versions renomment le titre différemment — je propose de garder la version la plus récente (feature/renommage)."

ModifierRejeterAccepter

Aperçu illustratif de la suggestion de résolution de conflit par Copilot.

Le même principe que dans tes deux autres cours

Un message de commit ou une résolution de conflit générés par l'IA restent des propositions, jamais une vérité automatique. Avant d'accepter, vérifie que le résumé du commit correspond vraiment à ce que tu as changé, et qu'une résolution de conflit proposée ne fait pas disparaître silencieusement une des deux intentions en jeu. Exactement le réflexe déjà vu pour les cas de test générés par IA (cours QA, module 15) et le SQL généré par IA (cours SQL, module 22).

Partie 4 · Module 18

GitHub Actions : les concepts

GitHub Actions est le moteur de CI/CD intégré à GitHub : il exécute automatiquement des tâches (lancer les tests, construire une application, déployer) en réaction à des événements comme un push ou une pull request. C'est directement la suite du module 20 du cours QA, mais vu ici côté configuration GitHub plutôt que côté script de test.

TermeCe que c'est
WorkflowUn fichier YAML dans .github/workflows/ qui décrit l'automatisation
EventCe qui déclenche le workflow : push, pull_request, planification...
JobUn ensemble d'étapes exécutées sur une même machine
StepUne action précise dans un job : cloner le code, installer, exécuter une commande
RunnerLa machine (fournie par GitHub, ou auto-hébergée) qui exécute le job

Workflow minimal — .github/workflows/hello.yml

name: Hello CI
on: [push]

jobs:
  say-hello:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Le code vient d'être poussé !"

Partie 4 · Module 19

Un pipeline CI pour Playwright

On assemble maintenant un vrai pipeline pour livret-mission : à chaque pull request, on installe les dépendances Python, on lance la suite pytest-playwright vue dans le cours QA, et on archive le rapport de test même en cas d'échec.

.github/workflows/tests.yml

name: Tests

on:
  pull_request:
    branches: [main]

jobs:
  playwright-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: Installer les dépendances
        run: |
          pip install -r requirements.txt
          playwright install --with-deps

      - name: Lancer les tests
        run: pytest tests/ --html=report.html

      - name: Archiver le rapport
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: rapport-tests
          path: report.html

if: always() est le détail qui change tout : sans lui, l'étape d'archivage serait sautée dès qu'un test échoue — exactement le moment où le rapport est le plus utile à consulter.

Partie 4 · Module 20

Sécurité : Dependabot & scanning

GitHub embarque trois protections automatiques gratuites sur les dépôts publics (et activables sur les dépôts privés selon l'offre), qu'un testeur QA doit savoir reconnaître même sans les configurer soi-même — elles apparaissent régulièrement dans les PR et les alertes du dépôt.

FonctionnalitéCe qu'elle fait
DependabotDétecte les dépendances avec des failles connues et ouvre automatiquement une PR pour les mettre à jour
Secret scanningDétecte une clé d'API ou un mot de passe accidentellement commité, et peut bloquer le push avant qu'il n'atteigne le dépôt (push protection)
Code scanning (CodeQL)Analyse statiquement le code à la recherche de vulnérabilités (injection SQL, XSS...)

Évolution 2026 à connaître : GitHub a étendu le support OIDC (OpenID Connect) pour Dependabot et le code scanning, permettant une authentification par jeton temporaire plutôt que par identifiants stockés en dur dans la configuration CI — une amélioration de sécurité pour les pipelines eux-mêmes, pas seulement pour le code qu'ils testent.

Si un push est bloqué pour "secret détecté"

Ne contourne jamais ce blocage en désactivant la protection pour "juste pousser ce commit" — le secret concerné (clé, token, mot de passe) doit être considéré comme compromis dès qu'il a été commité, même localement. La bonne réaction : retirer le secret du code, le régénérer côté service concerné, et le déplacer dans une variable d'environnement ou un secret GitHub Actions (Settings → Secrets and variables), jamais dans le code source.

Exercice

GitHub bloque ton git push avec le message "Push cannot contain secrets — detected: OpenAI API Key". Que fais-tu, dans l'ordre ?

Voir la correction

1) Retirer la clé du fichier concerné et la remplacer par une lecture depuis une variable d'environnement. 2) Régénérer la clé côté OpenAI (elle est compromise dès qu'elle a existé dans un commit, même local et jamais poussé avec succès). 3) Ajouter le fichier contenant la vraie clé (.env) à .gitignore s'il n'y était pas déjà. 4) Recommencer le commit et le push proprement.

Partie 4 · Module 21

Bonnes pratiques de collaboration

Trois habitudes distinguent immédiatement un profil qui a déjà travaillé en équipe d'un profil purement solo — précisément ce que cherche à évaluer un recruteur en repensant ton historique GitHub.

Des messages de commit qui se lisent

La convention Conventional Commits préfixe chaque message par son type — largement adoptée en 2026, notamment parce qu'elle permet de générer un changelog automatiquement.

✓ feat: ajoute le mode hors-ligne à la PWA
✓ fix: corrige le calcul du total avec quantité
✓ docs: complète le README avec les instructions de test
✗ update
✗ fix bug
✗ ça marche enfin!!

Les types les plus courants : feat (nouvelle fonctionnalité), fix (correction de bug), docs, test, refactor, chore (tâche technique sans impact fonctionnel).

Trunk-based vs Git flow

Deux modèles de branches dominent le marché. Git flow, plus ancien, multiplie les branches longues (develop, release, hotfix...) — encore présent dans certaines grandes équipes avec des cycles de release stricts. Trunk-based development, aujourd'hui largement dominant dans les équipes produit modernes, garde main comme unique branche longue et privilégie des branches de fonctionnalité courtes, fusionnées vite. C'est le modèle utilisé tout au long de ce cours.

Exercice

Classe ces messages de commit en "bon" ou "à corriger", et pour ceux à corriger, réécris-les selon Conventional Commits : (a) "wip", (b) "fix: le PDF ne s'ouvrait plus sous Firefox", (c) "changements divers".

Voir la correction

(a) À corriger — ex. fix: corrige l'ouverture du PDF (une fois le travail terminé, pas laissé en "wip"). (b) Bon — type clair, description précise. (c) À corriger — trop vague ; ex. refactor: réorganise les fonctions de génération PDF si c'est bien de ça qu'il s'agit.
