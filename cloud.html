Cloud pour Testeurs

Ce cours ne fait pas de toi un ingénieur cloud — ce n'est pas ton métier. L'objectif est plus modeste et plus ciblé : comprendre où vit réellement l'application que tu testes, savoir lire des logs cloud pour diagnostiquer un échec de test, et parler intelligemment d'AWS ou d'Azure en entretien, sans bluffer ni paniquer face au sujet.

12 modules 5 parties : bases → AWS → Azure → tests cloud → marché 12 exercices corrigés
Le lien avec tes autres cours

Tu as déjà touché au cloud sans le savoir : chaque fois qu'un workflow GitHub Actions (cours GitHub) exécute tes tests Playwright, c'est une machine virtuelle louée dans le cloud de GitHub/Microsoft Azure qui tourne quelques minutes puis disparaît. Ce cours te donne le vocabulaire et les repères pour comprendre ce qui se passe vraiment derrière ce mot "cloud" que tu croises déjà partout.

PARTIE 1

Les bases du cloud

Trois modules pour poser le vocabulaire, sans jargon inutile.

Partie 1 · Module 01

Pourquoi un testeur a besoin du cloud

En 2026, la quasi-totalité des applications professionnelles — y compris NovaCart, dans notre scénario fil rouge — ne tournent plus sur un serveur physique dans les locaux de l'entreprise, mais sur des machines louées chez un fournisseur cloud : AWS (Amazon), Azure (Microsoft), ou Google Cloud Platform, les trois plus utilisés.

Pour un testeur, ça change concrètement plusieurs choses : l'environnement de test sur lequel tu travailles est probablement une copie cloud de la production, pas ta machine locale ; quand un test échoue en CI (cours GitHub, module 19), le "pourquoi" se trouve parfois dans des logs cloud plutôt que dans le code lui-même ; et de plus en plus d'offres d'emploi QA mentionnent AWS ou Azure, même pour des postes qui ne demandent pas de les administrer.

Ce que ce cours n'est pas

Tu ne vas pas apprendre à administrer une infrastructure cloud — ce n'est pas ton métier, et ce n'est attendu d'aucun poste de testeur QA junior. L'objectif est de comprendre suffisamment le vocabulaire et les mécanismes pour ne jamais être bloqué par le mot "cloud" en entretien ou face à un environnement de test réel.

Exercice

Un test Playwright échoue uniquement en environnement de staging (hébergé sur AWS), jamais en local. Cite deux raisons possibles, liées spécifiquement au fait que staging tourne dans le cloud.

Voir la correction

Par exemple : une différence de configuration réseau (règles de sécurité, latence) entre local et cloud ; des données de test différentes en staging (base partagée, pas remise à zéro comme en local) ; ou une variable d'environnement/un secret mal configuré spécifiquement sur l'environnement cloud.

Partie 1 · Module 02

IaaS, PaaS, SaaS

Trois niveaux de service cloud, qui déterminent ce que le fournisseur gère pour toi et ce qui reste à la charge de l'équipe — une distinction citée dans presque toutes les questions d'entretien "bases cloud".

ModèleCe que le fournisseur gèreCe que l'équipe gère encoreExemple
IaaS (Infrastructure)Serveurs physiques, réseau, virtualisationSystème d'exploitation, applications, donnéesAWS EC2, Azure Virtual Machines
PaaS (Plateforme)+ système d'exploitation, environnement d'exécutionUniquement le code applicatif et les donnéesAWS Elastic Beanstalk, Azure App Service
SaaS (Logiciel)Tout, y compris l'application elle-mêmeUniquement l'usage et la configurationGmail, Salesforce, GitHub lui-même

Plus on descend dans ce tableau (IaaS → PaaS → SaaS), moins il y a de contrôle technique, mais moins il y a aussi de charge de maintenance. NovaCart, en tant qu'application développée en interne, tournerait typiquement en IaaS ou PaaS — jamais en SaaS, réservé aux logiciels qu'on consomme tout faits.

Exercice

L'équipe NovaCart utilise Jira (déjà vu dans le cours QA) pour son suivi de projet. De quel modèle de service s'agit-il pour l'équipe NovaCart, et pourquoi ?

Voir la correction

SaaS. L'équipe NovaCart ne gère ni serveur, ni système d'exploitation, ni même le code de Jira — elle consomme directement le logiciel fini via un abonnement, sans aucune responsabilité d'infrastructure.

Partie 1 · Module 03

Régions, disponibilité, environnements

Quelques concepts transverses, valables chez tous les fournisseurs cloud, qu'un testeur croise régulièrement sans forcément les nommer.

ConceptCe que ça veut direPourquoi ça concerne un testeur
RégionUne zone géographique où sont hébergés les serveurs (ex. Europe/Paris, US-East)La latence et parfois le comportement (conformité RGPD) diffèrent selon la région testée
ScalabilitéLa capacité à ajouter automatiquement des ressources selon la chargeDirectement liée au test de performance (k6, cours QA module 21) — vérifier que ça scale vraiment
Haute disponibilitéLe système reste accessible même si une machine ou une région tombe en panneUn test de résilience (couper volontairement un service) vérifie que ce n'est pas juste théorique

Les environnements, du développement à la production

Presque toutes les équipes cloud répliquent plusieurs copies de leur application, avec des noms proches d'un projet à l'autre : dev (instable, changements fréquents), staging (le plus proche de la production, où l'on teste avant de livrer réellement), production (l'environnement réel, utilisé par les vrais clients). Le test avant mise en production se fait presque toujours sur staging, jamais directement en production — sauf pour des vérifications spécifiques et prudentes après déploiement.

Exercice

Un bug n'apparaît qu'en production, jamais en staging, alors que les deux environnements sont censés être identiques. Cite une cause plausible liée à la scalabilité ou à la région.

Voir la correction

Par exemple : la production reçoit un volume de trafic réel bien plus élevé, ce qui déclenche un problème de scalabilité invisible sous la faible charge de staging (un cas typique de bug de performance ou de concurrence). Autre piste : staging tourne dans une seule région alors que la production est répartie sur plusieurs, exposant un problème de synchronisation entre régions.

PARTIE 2

AWS essentiels

AWS est le fournisseur cloud le plus utilisé au monde — le plus probable à rencontrer en entreprise, donc celui sur lequel on s'attarde le plus dans ce cours.

Partie 2 · Module 04

Panorama AWS pour la QA

AWS propose plusieurs centaines de services — un testeur n'a besoin d'en reconnaître qu'une poignée, ceux qui reviennent le plus souvent dans une architecture applicative classique.

ServiceÀ quoi il sertPourquoi un testeur le croise
EC2Des machines virtuelles louées (IaaS)C'est souvent là que tourne l'environnement de staging
S3Stockage de fichiers (objets) — images, PDF, sauvegardesNovaCart y stockerait les PDF de factures, par exemple
RDSBase de données relationnelle managée (PostgreSQL, MySQL...)Directement lié au cours SQL — c'est souvent là que vit la base NovaCart en production
LambdaExécuter du code à la demande, sans gérer de serveur (serverless)Utile pour comprendre des architectures event-driven modernes
IAMGestion des identités et des droits d'accèsComprendre pourquoi un accès est refusé ou autorisé lors d'un test

Le point commun à retenir : la console AWS (interface web) permet de consulter l'état de ces services sans avoir à les administrer soi-même — utile pour un testeur qui veut, par exemple, vérifier qu'un fichier a bien été déposé sur S3 après un test, sans avoir besoin des droits pour créer ou supprimer des ressources.

Exercice

Un test vérifie qu'après la génération d'une facture PDF sur NovaCart, le fichier est bien accessible en téléchargement. En te basant sur le tableau, quel service AWS est probablement concerné, et que pourrais-tu vérifier directement dans la console pour diagnostiquer un échec ?

Voir la correction

S3, le service de stockage de fichiers. En cas d'échec, on peut vérifier directement dans la console AWS si le fichier PDF a bien été déposé dans le bon compartiment (bucket) — ce qui permet de distinguer un problème de génération du PDF (côté application) d'un problème de dépôt ou de permission sur S3.

Partie 2 · Module 05

Un environnement de test sur AWS

Comment un environnement de staging existe-t-il concrètement sur AWS ? De plus en plus rarement créé "à la main" dans la console — la pratique moderne s'appuie sur l'Infrastructure as Code (IaC) : décrire l'infrastructure voulue dans un fichier texte, versionné comme du code (donc dans Git, cours GitHub), plutôt que de cliquer manuellement dans une interface.

Extrait simplifié d'une définition Terraform (l'outil IaC le plus répandu)

resource "aws_instance" "staging_novacart" {
  ami           = "ami-0abcdef1234567890"
  instance_type = "t3.micro"
  tags = {
    Name        = "novacart-staging"
    Environment = "staging"
  }
}

Ce fichier, une fois appliqué, crée automatiquement une machine identique à chaque fois — ce qui élimine le fameux "ça marche sur mon poste, pas sur l'environnement de test" causé par une configuration créée manuellement et jamais reproduite à l'identique.

IAM, en une phrase

Un testeur n'a généralement besoin que de droits en lecture sur les ressources qu'il doit vérifier (logs, fichiers, état d'une base) — jamais de droits de création ou de suppression sur l'infrastructure elle-même, sauf rôle spécifique. Un accès refusé pendant un test (erreur "Access Denied") est souvent un signal légitime de sécurité bien configurée, pas un bug à corriger en élargissant les droits sans réflexion.

Exercice

Pourquoi préfère-t-on, en 2026, décrire une infrastructure de test en Infrastructure as Code plutôt que de la créer manuellement dans la console AWS ?

Voir la correction

Parce que ça garantit une infrastructure reproductible et versionnée : la même définition recrée toujours exactement le même environnement, on peut suivre son historique de modification comme du code, et on élimine les divergences accumulées par des changements manuels non documentés au fil du temps.

Partie 2 · Module 06

Logs et monitoring avec CloudWatch

CloudWatch est le service AWS qui centralise logs et métriques de tous les autres services — le premier endroit où chercher quand une application se comporte anormalement en environnement cloud et que le message d'erreur côté test ne suffit pas à comprendre pourquoi.

Ce que tu y trouvesUtile pour
Logs applicatifs (erreurs, requêtes)Comprendre pourquoi une requête API a échoué côté serveur
Métriques (CPU, mémoire, latence)Corréler un test de performance qui échoue avec une vraie saturation de ressources
AlarmesÊtre notifié automatiquement si un seuil est dépassé — pas directement ton rôle, mais utile à savoir lire

Un réflexe précieux pour un testeur : quand un test échoue avec une erreur 500 (erreur serveur générique) sans détail exploitable côté client, aller consulter les logs CloudWatch du service concerné donne souvent la vraie cause — une exception non gérée, une dépendance externe indisponible, une base de données saturée — avant même de solliciter un développeur.

Exercice

Un test Playwright échoue avec "Erreur 500" sur la page de paiement NovaCart, sans plus de détail. Décris, étape par étape, comment tu utiliserais CloudWatch pour avancer dans le diagnostic avant de solliciter un développeur.

Voir la correction

1) Noter l'heure exacte de l'échec du test. 2) Ouvrir CloudWatch, filtrer les logs du service de paiement autour de cet horodatage précis. 3) Chercher une exception ou une erreur explicite dans les logs à ce moment-là. 4) Vérifier aussi les métriques (CPU/mémoire) au même instant, pour écarter une saturation de ressources. Ce diagnostic préliminaire, présenté au développeur, accélère énormément la résolution comparée à "ça a planté, je ne sais pas pourquoi".

Azure et comparaison

Deux modules pour ne pas être perdu si ton prochain employeur utilise Azure plutôt qu'AWS — un choix aussi fréquent, surtout dans les entreprises déjà équipées en outils Microsoft.

Partie 3 · Module 07

Panorama Azure

Azure, le cloud de Microsoft, est particulièrement répandu dans les grandes entreprises déjà équipées en outils Microsoft (Office 365, Active Directory) — le passage vers Azure y est souvent plus naturel qu'un changement complet d'écosystème vers AWS. Tu l'as d'ailleurs déjà frôlé : les runners GitHub Actions (cours GitHub) tournent en réalité sur l'infrastructure Azure de Microsoft, propriétaire de GitHub depuis 2018.

Service AzureÉquivalent du rôle
Virtual MachinesMachines virtuelles (IaaS)
App ServiceHéberger une application web sans gérer le serveur (PaaS)
Blob StorageStockage de fichiers
Azure SQL DatabaseBase de données relationnelle managée
Azure DevOpsSuite intégrée : dépôt Git, pipelines CI/CD, gestion de projet — une alternative à GitHub + GitHub Actions
Azure MonitorLogs et métriques — l'équivalent d'Azure à CloudWatch
Exercice

Une entreprise déjà équipée en Office 365 et Active Directory envisage de migrer une application interne vers le cloud. Pourquoi Azure serait-il un choix naturel dans ce contexte ?

Voir la correction

Azure s'intègre nativement avec l'écosystème Microsoft déjà en place (authentification via Active Directory, outils Office) — ce qui réduit le travail d'intégration et la formation nécessaire, comparé à l'adoption d'un cloud entièrement séparé de l'existant.

Tester dans le cloud

Trois modules qui relient directement ce cours à ta pratique déjà réelle : Playwright, Docker, GitHub Actions.

Partie 4 · Module 09

Où tournent réellement tes tests CI

Quand un workflow GitHub Actions (cours GitHub, module 19) exécute runs-on: ubuntu-latest, GitHub loue en réalité, pour la durée du job, une machine virtuelle éphémère hébergée sur Azure — créée à la demande, utilisée quelques minutes, puis totalement détruite. C'est un exemple concret et déjà pratiqué de ce que "cloud" veut dire pour un testeur : de la puissance de calcul à la demande, jamais une machine physique dédiée qui t'appartient.

Cette nature éphémère explique certains comportements qu'on observe parfois en CI sans les comprendre : un test qui dépend d'un état laissé par une exécution précédente échoue en CI (machine neuve à chaque fois) alors qu'il passait en local (même machine réutilisée) — un bug d'isolation de test que le cloud révèle plutôt qu'il ne cause.

Exercice

Un test passe systématiquement en local mais échoue systématiquement en CI GitHub Actions, avec une erreur "fichier introuvable" sur un fichier créé par un test précédent. Explique ce phénomène à la lumière de ce module.

Voir la correction

En local, la même machine persiste entre les exécutions — un fichier créé une fois reste disponible. En CI, chaque run démarre sur une machine virtuelle cloud neuve et éphémère : rien de précédent ne subsiste. Le test a probablement une dépendance cachée à un état local qui n'existe jamais en environnement cloud propre — un bug d'isolation à corriger en rendant le test autonome (le fichier doit être créé par le test lui-même, pas hérité d'un run antérieur).

Partie 4 · Module 10

BrowserStack, Sauce Labs, Device Farm

Tester sur tous les navigateurs et appareils mobiles réels du marché est impossible à maintenir en interne — d'où l'existence de plateformes cloud spécialisées qui louent l'accès à des milliers de combinaisons réelles, à la demande.

PlateformePoints forts
BrowserStackTrès large parc d'appareils réels, test manuel rapide via "Live", test visuel avec Percy
Sauce LabsReporting et débogage détaillés (logs réseau, commandes Selenium/Appium complètes)
AWS Device FarmSpécialisé mobile, fortement intégré aux autres services AWS (CodePipeline, CloudWatch)

Le principe technique est le même partout : ton framework d'automatisation (Playwright, Appium — déjà pratiqués dans le cours QA) se connecte à distance à un appareil réel hébergé sur leur infrastructure, plutôt qu'à un navigateur ou émulateur local.

Pointer Playwright vers une exécution distante (principe général)

browser = playwright.chromium.connect(
    "wss://cdp.plateforme-cloud.com/?os=Windows&browser=chrome"
)
Le vrai piège : les coûts

Ces plateformes facturent le plus souvent à la minute d'utilisation. Une suite de tests mal maîtrisée (boucle infinie, timeout mal configuré, exécution en continu sans nécessité) peut générer une facture disproportionnée en quelques heures — un réflexe de base est de toujours vérifier qu'un test a une limite de temps claire (timeout) avant de le lancer sur une plateforme cloud payante.

Exercice

Pourquoi une équipe choisirait-elle de payer pour BrowserStack ou Sauce Labs plutôt que de maintenir elle-même un parc de vrais appareils mobiles en interne ?

Voir la correction

Maintenir soi-même des centaines de combinaisons d'appareils/navigateurs réels (achat, mises à jour, câblage, maintenance physique) coûte bien plus cher et demande une expertise dédiée, comparé à louer l'accès à la demande sur une plateforme déjà équipée et maintenue par quelqu'un d'autre — le même raisonnement économique qui justifie le cloud en général.

Partie 4 · Module 11

Docker et conteneurs dans le cloud

Le cours QA (module 25) t'a déjà fait manipuler Docker en local. En entreprise, ces conteneurs sont presque toujours déployés et orchestrés dans le cloud, via des services spécialisés — le passage naturel de "ça marche sur ma machine, en conteneur" à "ça tourne en production, à grande échelle".

ServiceFournisseurRôle
ECS (Elastic Container Service)AWSOrchestrer des conteneurs Docker à grande échelle
AKS (Azure Kubernetes Service)AzureKubernetes managé — l'orchestrateur de conteneurs le plus répandu, opéré par Azure
KubernetesOpen source, multi-cloudLe standard de facto pour orchestrer des conteneurs — gère automatiquement le redémarrage, la répartition de charge, la mise à l'échelle

Pour un testeur, l'essentiel à retenir : ces services répondent à la question "comment fait-on tourner, de façon fiable, des dizaines ou centaines de conteneurs en même temps, en remplaçant automatiquement ceux qui tombent en panne ?" — un problème que le simple docker run du cours QA ne résout pas à cette échelle. Tu n'as pas besoin de savoir configurer Kubernetes, seulement de reconnaître le terme et son rôle si un développeur ou un DevOps le mentionne.

Exercice

Un développeur explique qu'un pod Kubernetes a "crashé et a été automatiquement redémarré". En une phrase, que signifie ce comportement au niveau conceptuel ?

Voir la correction

Kubernetes surveille en permanence l'état de ses conteneurs (pods) et redémarre automatiquement ceux qui tombent en panne, sans intervention humaine — c'est exactement le rôle d'un orchestrateur : maintenir un état désiré (par exemple "toujours 3 instances actives") malgré les pannes individuelles.

Partie 5 · Module 12

Le cloud sur le marché en 2026

Contrairement à Git ou à l'agilité, la connaissance du cloud reste, pour un testeur junior, un vrai plus différenciant plutôt qu'un prérequis implicite — la majorité des candidats juniors n'ont aucune notion cloud, ce qui rend même ce niveau de base remarqué.

Niveau attendu d'un juniorCe qui te distingue
Aucune connaissance cloudSavoir expliquer IaaS/PaaS/SaaS avec des exemples concrets
Confondre AWS et AzureTransposer un service AWS vers son équivalent Azure sans hésiter
Ne jamais avoir lu un log cloudSavoir utiliser CloudWatch (ou équivalent) pour diagnostiquer un échec de test
Ignorer le coût des plateformes cloud de testAvoir le réflexe de vérifier les timeouts avant de lancer une suite sur une plateforme facturée à la minute

Une certification à envisager, plus tard

La certification AWS Cloud Practitioner est le premier niveau AWS, généraliste et accessible sans prérequis technique poussé — une bonne suite logique après ce cours et après l'ISTQB, si tu veux continuer à enrichir ton profil. Ce n'est pas une priorité immédiate pour ton alternance de février/mars 2027, mais un objectif réaliste pour la suite, une fois en poste.

Pour l'entretien

Tu n'as pas besoin d'expérience professionnelle cloud pour en parler avec crédibilité : explique que tu comprends où vit une application moderne, que tu sais lire des logs pour diagnostiquer un échec de test, et que tu connais les bases AWS et leur équivalence Azure — largement suffisant pour un poste junior, et nettement au-dessus de la moyenne des candidats à ce niveau.

Exercice

En entretien, on te demande : "Avez-vous une expérience du cloud ?" Prépare une réponse honnête et valorisante de 30 secondes.

Voir la correction

Un exemple de structure : "Pas d'expérience professionnelle directe, mais je me suis formé aux bases AWS et Azure spécifiquement utiles à un testeur — comprendre où tourne l'application que je teste, savoir lire des logs CloudWatch pour diagnostiquer un échec, et faire le lien entre les deux plateformes si besoin. Je sais aussi que mes tests CI, via GitHub Actions, tournent déjà sur une infrastructure cloud Azure à chaque exécution." Cette réponse montre une compréhension réelle et connectée à une pratique déjà existante, sans survendre une expertise qui n'existe pas encore.
