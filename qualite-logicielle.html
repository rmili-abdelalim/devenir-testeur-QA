NIVEAU 1

Comprendre ce qu'est un test

Trois modules pour poser un vocabulaire précis. Rien de ça n'est daté par 2026 : les techniques de conception de tests d'ISTQB ont 30 ans et fonctionnent toujours, elles sont juste rarement expliquées avec un exemple qu'on peut suivre du regard.

Niveau 1 · Module 01

Tester, qu'est-ce que ça veut dire

Tester un logiciel, c'est l'exécuter volontairement pour trouver les endroits où il se comporte mal — avant que quelqu'un d'autre ne le découvre en production. Ce n'est pas prouver qu'un programme fonctionne (on ne peut jamais le prouver complètement), c'est réduire le risque de surprise.

Trois mots qu'on confond souvent :

TermeCe que c'est
TestL'activité concrète : exécuter le logiciel, comparer le résultat obtenu au résultat attendu.
QC — Contrôle qualitéL'ensemble des activités qui vérifient que le produit est conforme (dont le test fait partie).
QA — Assurance qualitéL'ensemble des activités qui améliorent le processus de fabrication, pour que les défauts apparaissent moins souvent en amont.

En clair : un testeur QC clique sur le bouton "payer" de NovaCart avec une carte invalide pour voir ce qui se passe. Une démarche QA se demande pourquoi ce cas n'était pas prévu dans les specs, et change le process d'écriture des tickets pour que ça n'arrive plus. Dans la vraie vie, un même poste fait souvent les deux.

Pourquoi ça coûte de ne pas tester

Un bug coûte à peu près 10 fois plus cher à corriger à chaque étape où il n'est pas attrapé : trouvé pendant que le développeur écrit le code, c'est quasi gratuit ; trouvé en recette, ça mobilise un testeur et un aller-retour ; trouvé en production, ça mobilise le support, parfois les clients, parfois la réputation. Ce n'est pas un chiffre magique à retenir par cœur, c'est l'idée à retenir : plus un défaut est détecté tôt, moins il coûte. Tout ce que ce cours enseigne sur l'automatisation (niveaux 3 à 5) n'est qu'une façon de détecter plus tôt et plus souvent.

À retenir

Un test qui ne trouve jamais rien n'est pas forcément un mauvais test — mais un testeur qui ne trouve jamais rien, sur un logiciel qui a des bugs en production, cherche probablement au mauvais endroit. On verra comment mieux choisir où chercher dans le module 5.

Exercice

NovaCart remarque que la moitié des bugs remontés en production concernent des cas jamais prévus dans les tickets, et décide de changer sa façon d'écrire les spécifications pour que ces cas soient pensés en amont. Est-ce une activité de QC ou de QA ? Justifie en une phrase.

Voir la correction

C'est de la QA : on ne corrige pas un défaut sur le produit lui-même (ça, ce serait du QC), on change le processus de fabrication pour que ce type de défaut apparaisse moins souvent — exactement la distinction du tableau plus haut.

Niveau 1 · Module 02

Où le test se glisse dans le cycle de dev

Historiquement (modèle en V), on testait à la toute fin : les devs livrent, les testeurs testent, ça arrive une fois. Le problème, c'est que le module 1 vient de le dire — plus on teste tard, plus c'est cher. Le monde a bougé vers deux idées complémentaires :

Shift-left : tester plus tôt

Faire remonter le test vers l'amont : un développeur écrit un test unitaire en même temps que sa fonction, une revue de code cherche les cas oubliés, un analyste écrit les critères d'acceptation avant même que le code existe. Sur NovaCart, ça veut dire : le critère "le champ carte bancaire refuse un numéro de moins de 13 chiffres" est écrit avant que le développeur code le formulaire de paiement, pas après.

Shift-right : apprendre aussi en production

Certains problèmes (charge réelle, comportements d'utilisateurs imprévus, pannes d'infrastructure) ne se voient qu'en conditions réelles. Le monitoring, les tests A/B, les déploiements progressifs (canary releases) sont une forme de test — plus tardive, mais qui complète le reste sans le remplacer.

ContexteRythme du testCe qui change concrètement
Cycle en VUne phase de test, en fin de projetLong feedback loop, bugs chers à corriger
Agile / ScrumÀ chaque sprint (1–2 semaines)Tests écrits avec les user stories, pas après
DevOps / CI-CDÀ chaque commitTests automatisés obligatoires, exécutés en minutes

C'est cette dernière ligne qui motive toute l'automatisation qui suit : si les tests s'exécutent à la main, "à chaque commit" est physiquement impossible. L'automatisation n'est pas un luxe, c'est ce qui rend le shift-left tenable.

Exercice

Classe ces trois pratiques dans le bon camp — shift-left ou shift-right : (1) un Product Owner écrit les critères d'acceptation avant que le développement commence, (2) un déploiement progressif limité à 5% des utilisateurs pour observer le comportement réel, (3) une revue de code qui cherche les cas oubliés avant la mise en recette.

Voir la correction

(1) et (3) sont du shift-left — le test remonte avant l'écriture ou juste après le code. (2) est du shift-right — on apprend depuis la production réelle, pas avant.

Niveau 1 · Module 03

Les familles de tests

Deux découpages se superposent tout le temps dans le métier — il faut les garder séparés.

Fonctionnel vs non-fonctionnel

Le test fonctionnel vérifie ce que le logiciel fait : "quand j'ajoute un article au panier, le total se met à jour". Le test non-fonctionnel vérifie comment il le fait :

  • Performance — la page panier de NovaCart s'affiche en moins de 2 secondes avec 500 utilisateurs simultanés (module 13)
  • Sécurité — un utilisateur ne peut pas voir le panier d'un autre en modifiant l'URL
  • Utilisabilité — un nouvel utilisateur trouve le bouton "payer" sans aide
  • Compatibilité — le site fonctionne sur Safari mobile comme sur Chrome desktop
  • Accessibilité — le formulaire de paiement est utilisable au clavier et par un lecteur d'écran

Boîte noire, boîte blanche, boîte grise

ApprocheCe que le testeur voitExemple sur NovaCart
Boîte noireSeulement les entrées et les sorties, pas le codeSaisir un code promo et vérifier la réduction affichée
Boîte blancheLe code sourceVérifier que chaque branche if de la fonction de calcul de réduction est exécutée par au moins un test
Boîte griseUn peu des deuxSavoir que la réduction est plafonnée à 50 € en base de données, et tester spécifiquement cette limite depuis l'interface

Dans ce cours, le module 5 (conception de cas de test) est très majoritairement de la boîte noire — c'est ce dont un testeur QA a besoin en premier. Le module 11 (Playwright) reste aussi en boîte noire : on pilote l'interface comme le ferait un utilisateur, sans lire le code de l'application testée.

Exercice

Un testeur vérifie que chaque branche if de la fonction de calcul de réduction de NovaCart est exécutée par au moins un test : boîte noire, blanche ou grise ? Et s'il sait, sans lire le code, que la réduction est plafonnée à 50 € en base de données, et teste spécifiquement cette limite depuis l'interface ?

Voir la correction

La première situation est de la boîte blanche — il regarde le code pour décider quoi tester. La seconde est de la boîte grise : il connaît un détail interne (le plafond en base) mais teste depuis l'interface, sans lire le code.

Niveau 2 · Module 04

Les niveaux de test

Un même bug peut être attrapé à plusieurs étages. Sur NovaCart, prenons la fonctionnalité "connexion utilisateur" et suivons-la à travers les quatre niveaux classiques.

NiveauCe qu'on isoleSur NovaCart, concrètementQui l'écrit, en général
UnitaireUne seule fonction, isolée du resteLa fonction validerMotDePasse(mdp) renvoie false pour un mot de passe de 5 caractèresLe développeur
IntégrationDeux composants qui communiquentLe service d'authentification appelle bien le service e-mail pour envoyer un code à deux facteursDéveloppeur ou testeur automaticien
SystèmeL'application entière, de bout en boutUn utilisateur peut se connecter, ajouter un article, payer et recevoir un e-mail de confirmationÉquipe QA
AcceptationLe besoin métier réel, du point de vue clientLe Product Owner valide que le parcours correspond à ce qui a été commandéProduct Owner / client

Un exemple de critère d'acceptation, écrit en Gherkin (le format lisible utilisé par Cucumber, très répandu pour ce niveau) :

Scénario : Connexion avec identifiants valides
  Étant donné que je suis sur la page de connexion de NovaCart
  Quand je saisis un e-mail et un mot de passe valides
  Et que je clique sur "Se connecter"
  Alors je suis redirigé vers mon tableau de bord
  Et je vois mon prénom en haut de la page
Pourquoi ça compte

Plus on descend vers "unitaire", plus un test est rapide à exécuter et facile à isoler quand il échoue — mais moins il prouve que l'expérience utilisateur réelle fonctionne. C'est tout l'objet de la pyramide de tests, module 8.

Exercice

Le service d'authentification de NovaCart plante quand il tente d'appeler le service e-mail pour envoyer un code à deux facteurs — alors que les deux services, testés séparément, fonctionnent très bien. Quel niveau de test aurait dû attraper ce bug avant la mise en production ?

Voir la correction

Le niveau intégration : chaque composant est correct isolément, c'est leur communication qui casse — exactement ce que le test unitaire ne peut pas voir, et que le test système aurait vu bien trop tard.

Niveau 2 · Module 05

Concevoir des cas de test

C'est le module que la plupart des cours bâclent — normalement celui qui devrait être le plus concret. Voici quatre techniques, chacune avec un cas de test réel dessus, pas juste la théorie.

1. Partitionnement en classes d'équivalence

Idée : si le programme traite un groupe de valeurs de la même façon, teste une seule valeur du groupe, pas toutes. Sur NovaCart, le champ mot de passe exige entre 8 et 20 caractères.

ClasseExemple de valeurRésultat attendu
Invalide — trop court"abc123"Rejeté
Valide"MotDePasse2026"Accepté
Invalide — trop long"a" × 25Rejeté

Trois cas suffisent à couvrir la règle entière, au lieu de tester 20 mots de passe différents pour rien.

2. Analyse aux valeurs limites

Les bugs adorent se cacher pile sur les frontières des classes ci-dessus — les erreurs de type < au lieu de <= sont le pain quotidien du développeur. On teste donc juste avant, sur, et juste après chaque limite (8 et 20 caractères) :

LongueurPositionRésultat attendu
7Juste sous la limite basseRejeté
8Limite basseAccepté
9Juste au-dessusAccepté
19Juste sous la limite hauteAccepté
20Limite hauteAccepté
21Juste au-dessusRejeté

Ces six cas, combinés aux trois du partitionnement, forment un jeu de tests solide pour une seule règle de validation — et ce sont exactement les cas qu'on automatisera au module 11.

3. Table de décision

Utile quand le résultat dépend de plusieurs conditions combinées. Sur NovaCart : que se passe-t-il à la connexion selon que l'e-mail est valide, le mot de passe correct, et le compte verrouillé (après 5 échecs) ?

E-mail valide ?Mot de passe correct ?Compte verrouillé ?Résultat
OuiOuiNonConnexion réussie
OuiNonNon"Mot de passe incorrect"
Oui—Oui"Compte verrouillé, réessayez dans 15 min"
Non——"Aucun compte associé à cet e-mail"

Chaque ligne de cette table devient un cas de test. C'est aussi le meilleur outil pour repérer les combinaisons que personne n'avait pensé à spécifier (ici : que dit-on si le mot de passe est faux et que le compte est déjà verrouillé ? La table force la question.)

4. Test de transition d'état

Utile quand un objet passe par des états distincts. Le compte NovaCart : Actif → (5 échecs) → Verrouillé → (15 min ou réinitialisation) → Actif. On teste les transitions valides, mais surtout les transitions invalides qui ne devraient pas être possibles : peut-on se connecter alors que le compte est verrouillé ? Le système doit refuser, quel que soit le mot de passe saisi.

5. Trois mots qu'on entend tous les jours : smoke, sanity, regression

Ce ne sont pas des techniques de conception comme les quatre précédentes, mais un vocabulaire que tout le monde utilise sans jamais l'expliquer en entretien ou en réunion d'équipe — mieux vaut le maîtriser avant d'arriver sur le terrain.

TermeQuand on l'utiliseExemple sur NovaCart
Smoke testJuste après un déploiement, avant d'aller plus loin — "est-ce que ça vaut le coup de continuer à tester ?"Se connecter, ajouter un article au panier, arriver à l'écran de paiement — si l'une de ces trois étapes casse, on arrête tout et on remonte l'alerte immédiatement
Sanity testAprès un correctif ciblé, pour vérifier rapidement que la zone concernée fonctionne — pas toute l'applicationLe bug d'arrondi du code promo (module 16) est corrigé → on revérifie l'application du code promo et rien d'autre
Regression testAvant une mise en production, sur l'ensemble des fonctionnalités déjà validées — vérifier qu'un changement récent n'a rien cassé ailleursRejouer toute la suite connexion + panier + paiement + code promo avant la mise en production de vendredi
Exercice — Prioriser avec le risque (module 7)

Il reste deux jours de test avant une mise en production, et pas le temps de tout tester en profondeur. Voici six fonctionnalités de NovaCart, avec une estimation de la probabilité qu'un bug s'y cache et de l'impact s'il passe en production :

FonctionnalitéProbabilité de bugImpact si bug en production
Paiement par carte bancaireFaible (code stable, non modifié récemment)Élevé (perte de vente directe, image de marque)
Filtre de prix (juste modifié — module 26)Élevée (changement tout juste livré)Moyen (gêne la recherche, contournable)
Inscription à la newsletterFaibleFaible
Recherche produitMoyenneÉlevé (point d'entrée de la quasi-totalité des ventes)
Affichage des avis clientsMoyenneFaible
Code promo (bug d'arrondi corrigé récemment — module 16)Moyenne (zone récemment retouchée)Élevé (impact financier direct sur chaque commande)

Dans quel ordre concentrer le temps de test restant, et pourquoi ?

Voir la correction

Le risque se raisonne comme probabilité × impact, pas comme l'un des deux facteurs pris isolément. Ordre de priorité défendable : (1) Recherche produit — impact élevé et probabilité non négligeable, c'est le point d'entrée de presque toutes les ventes ; (2) Code promo — zone récemment retouchée (probabilité moyenne) avec un impact financier direct ; (3) Paiement — impact maximal, mais probabilité faible car non modifié : à couvrir par un smoke test solide plutôt qu'une campagne complète ; (4) Filtre de prix — changement tout juste livré donc probabilité élevée, mais impact plus limité (contournable en parcourant le catalogue) ; (5) et (6) Avis clients et newsletter — impact faible dans les deux cas, à ne tester que si le temps le permet vraiment. L'erreur classique serait de tout traiter à égalité, ou de se focaliser uniquement sur ce qui vient de changer (le filtre) en négligeant une zone à fort impact business qui n'a pourtant pas bougé (le paiement) : le risque combine toujours les deux facteurs.

Exercice

Le champ "code promo" de NovaCart doit accepter entre 4 et 8 caractères. En reprenant les deux premières techniques de ce module, liste les cas de test à écrire.

Voir la correction

Classes d'équivalence : une valeur invalide trop courte (ex. 3 caractères), une valeur valide (ex. 6 caractères), une valeur invalide trop longue (ex. 10 caractères). Valeurs limites : 3, 4, 5 autour de la borne basse, et 7, 8, 9 autour de la borne haute — six cas au total, sur le même principe que le mot de passe.

Sévérité ≠ priorité

Deux axes qu'on confond souvent en début de carrière :

  • Sévérité — l'impact technique du bug (mineur, majeur, critique, bloquant). Objectif, indépendant du contexte business.
  • Priorité — l'urgence de le corriger, décidée par l'équipe produit (peut dépendre d'une date de lancement, d'un client important, etc.).

Exemple : une faute d'orthographe sur la page d'accueil est sévérité mineure mais peut être priorité haute se déroule un lancement presse le lendemain. À l'inverse, un bug qui plante une fonctionnalité rarement utilisée peut être sévérité critique mais priorité basse si le correctif est complexe et l'usage marginal.

Niveau 2 · Module 07

Stratégie et plan de test

Avant d'écrire le premier cas de test, une équipe QA sérieuse répond à quelques questions par écrit — ça évite de tester deux fois la même chose et d'oublier un pan entier de l'application.

Section du planQuestion à laquelle elle répondExemple NovaCart
PérimètreQu'est-ce qui est testé, et surtout qu'est-ce qui ne l'est pas ?Le tunnel d'achat complet. Hors périmètre : le back-office de gestion des stocks
ApprocheManuel, automatisé, ou les deux ? À quels niveaux ?Automatisé pour la régression, manuel/exploratoire pour les nouvelles fonctionnalités
Critères d'entréeQuand peut-on commencer à tester ?L'environnement de staging est déployé et stable
Critères de sortieQuand peut-on dire "c'est testé" ?100% des cas critiques passent, 0 bug bloquant ouvert
RisquesOù sont les zones fragiles ?Le module de paiement, réécrit récemment

Tester en fonction du risque

On n'a jamais le temps de tout tester exhaustivement — le test basé sur les risques consiste à croiser deux facteurs pour décider où investir l'effort : la probabilité qu'un défaut existe (code récent, complexe, souvent modifié) et l'impact s'il survient (le paiement, pas la page "À propos"). Le module de paiement de NovaCart, récemment réécrit, cumule les deux — c'est là que va l'essentiel du budget de test, pas également réparti sur toute l'application.

Exercice

NovaCart a deux zones à tester avant une mise en production, mais pas le temps de tout couvrir : le module de paiement, récemment réécrit, et la page "À propos", inchangée depuis deux ans. Où concentrer l'effort, et pourquoi en termes de probabilité et d'impact ?

Voir la correction

Le module de paiement : probabilité de défaut élevée (code récent, donc moins éprouvé) et impact élevé (bloque toute vente) — les deux facteurs du test basé sur les risques pointent dans la même direction. La page "À propos" cumule au contraire faible probabilité et faible impact.

Niveau 3 · Module 08

Pourquoi (et quoi) automatiser

Un test manuel coûte le même temps humain à chaque exécution. Un test automatisé coûte du temps une fois (pour l'écrire), puis quasiment rien à chaque exécution suivante. La bascule vaut le coup pour tout ce qui est répétitif, stable, et important — pas pour tout.

Bon candidat à l'automatisationMauvais candidat
Test de régression exécuté à chaque commitTest exploratoire d'une fonctionnalité tout juste livrée
Parcours critique (connexion, paiement)Détail visuel subjectif ("est-ce que ça a l'air pro ?")
Interface stable depuis plusieurs sprintsÉcran en pleine refonte, qui va encore changer
Calculs avec beaucoup de combinaisons (module 5)Test d'accessibilité fin nécessitant un jugement humain

La pyramide de tests

Le principe : beaucoup de tests unitaires (rapides, bon marché, faciles à isoler), moins de tests d'intégration, encore moins de tests de bout en bout (E2E — lents, plus fragiles, mais qui vérifient le vrai comportement utilisateur). Une variante plus récente et très citée en 2026, la testing trophy de Kent C. Dodds, met l'accent sur les tests d'intégration plutôt que sur les tests unitaires : l'idée est que tester "à peu près comme un utilisateur le ferait" donne plus confiance par test écrit. Dans ce cours, le module 11 (Playwright) se situe justement au niveau intégration/E2E — c'est là que la confiance utilisateur est la plus directe, et c'est pour ça qu'on commence par là niveau outillage.

Exercice

Voir la correction

Niveau 4 · Module 12

Tester une API

Tout ne se teste pas par l'interface. Tester directement l'API de NovaCart est plus rapide et plus stable — pas de navigateur à démarrer, pas de CSS à charger. Mais avant d'ouvrir Postman ou d'écrire une ligne de code, il faut maîtriser le vocabulaire HTTP lui-même — sans ça, on apprend une syntaxe d'outil sans comprendre ce qu'elle vérifie vraiment.

Les fondamentaux HTTP

Une API REST s'utilise avec un petit nombre de méthodes, chacune avec un rôle précis :

MéthodeRôleExemple NovaCart
GETLire une ressource, sans effet de bord — on peut la rejouer sans risqueGET /api/produits
POSTCréer une ressourcePOST /api/panier
PUTRemplacer entièrement une ressource existantePUT /api/produits/42
PATCHModifier partiellement une ressourcePATCH /api/panier/3 (changer la quantité)
DELETESupprimer une ressourceDELETE /api/panier/3

Chaque réponse renvoie un code statut qui dit immédiatement ce qui s'est passé, avant même de lire le corps de la réponse :

PlageSignificationExemples utiles en QA
2xxSuccès200 OK · 201 Created · 204 No Content
3xxRedirection301 Moved Permanently · 302 Found
4xxErreur côté client — la requête envoyée est incorrecte400 Bad Request · 401 Unauthorized · 403 Forbidden · 404 Not Found · 422 Unprocessable Entity
5xxErreur côté serveur — même une requête correcte échoue500 Internal Server Error · 503 Service Unavailable

Deux headers (en-têtes) reviennent dans presque tous les tests d'API : Content-Type: application/json (annonce que le corps de la requête/réponse est du JSON) et Authorization: Bearer <token> (transporte l'authentification — le token obtenu après une connexion réussie, comme au module 11). Le corps d'une requête ou d'une réponse est presque toujours du JSON : un objet {"email": "test@novacart.fr"}, une liste [{"id": 1, ...}, {"id": 2, ...}], ou une valeur simple.

API vs UI : pourquoi tester aux deux niveaux

Un test API vérifie que le serveur fait ce qu'il doit (bon statut, bonnes données) sans se soucier de l'affichage. Un test UI (module 11) vérifie que ce que le serveur renvoie s'affiche correctement à l'écran. Les deux peuvent être vrais indépendamment l'un de l'autre : une API peut renvoyer les bonnes données pendant qu'un bug d'affichage les cache, ou une page peut sembler correcte pendant que l'API renvoie un statut d'erreur ignoré silencieusement par le front. D'où l'intérêt de tester les deux niveaux plutôt qu'un seul.

Pour débuter : Postman

Interface graphique, aucune ligne de code nécessaire. On envoie une requête, on écrit une assertion dans l'onglet "Tests" — à noter, ces scripts sont toujours en JavaScript, quel que soit ton langage principal : c'est une particularité de l'outil, pas un choix à faire :

Idempotence : rejouer un appel sans effet de bord supplémentaire

Une opération est idempotente si l'exécuter plusieurs fois produit le même résultat qu'une seule fois. GET, PUT et DELETE sont censées l'être par convention HTTP ; POST ne l'est presque jamais — c'est justement ce qui en fait un point à tester explicitement, en particulier sur un appel de paiement où un double clic ou une requête rejouée après un timeout réseau ne doit pas débiter deux fois.

MéthodeIdempotente ?Risque si elle ne l'est pas
PUT /api/produits/42Oui, attenduDeux appels identiques doivent laisser la ressource dans le même état
DELETE /api/panier/3Oui, attenduUn second appel doit renvoyer 404, pas une erreur serveur
POST /api/paiementNon, par natureRejouée sans protection (clé d'idempotence), elle peut débiter deux fois

Pour un appel critique comme un paiement, une API bien conçue accepte une clé d'idempotence envoyée par le client (Idempotency-Key: abc123) : le serveur reconnaît une requête déjà traitée avec cette clé et renvoie le même résultat sans débiter une seconde fois — un point à vérifier explicitement plutôt qu'à supposer.

Validation de schéma : au-delà du statut et d'un champ isolé

Vérifier un champ à la fois (assert "token" in corps) devient vite insuffisant à mesure qu'une réponse s'enrichit — un champ renommé, un type qui change silencieusement de string à number, passent inaperçus. Un test de schéma vérifie la forme entière de la réponse en une fois :

test_schema_produit.py (avec jsonschema)

schema_produit = {
    "type": "object",
    "required": ["id", "nom", "prix", "enStock"],
    "properties": {
        "id": {"type": "string"},
        "nom": {"type": "string"},
        "prix": {"type": "number"},
        "enStock": {"type": "boolean"},

Un test fonctionnel vérifie qu'une requête réussit. Un test de charge vérifie que ça tient quand des milliers de requêtes arrivent en même temps — k6 est aujourd'hui l'outil de référence pour ça, construit spécifiquement pour ce cas d'usage (contrairement à JMeter, plus ancien et plus lourd à configurer, encore utilisé mais de moins en moins recommandé pour un nouveau projet). Précision utile : les scripts k6 s'écrivent toujours en JavaScript — même dans une suite Python, c'est propre à l'outil, pas une incohérence ; ça tombe bien, c'est aussi la syntaxe la plus proche du TypeScript utilisé ailleurs dans ce cours.

charge-connexion.js

import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  vus: 50,           // 50 utilisateurs virtuels simultanés
  duration: '30s',
};

export default function () {
  const reponse = http.post('https://novacart.exemple/api/connexion', JSON.stringify({
    email: 'test@novacart.fr',

Terminal

k6 sort un rapport avec les métriques qui comptent vraiment sous charge : le p95 (95% des requêtes répondent plus vite que ce chiffre — plus parlant qu'une moyenne, que quelques requêtes très lentes peuvent fausser), et le taux d'erreur. C'est la combinaison "Playwright pour le fonctionnel/E2E, k6 pour la charge" qui domine chez les équipes JS/TS en 2026.

Aller plus loin : seuils et montée en charge progressive

Un script réaliste ne se contente pas de lancer 50 utilisateurs d'un coup — il monte en charge progressivement (comme le trafic réel) et échoue automatiquement si une métrique dépasse un seuil, plutôt que de laisser un humain relire le rapport à l'œil :

charge-connexion-avancee.js

export const options = {
  stages: [
    { duration: '30s', target: 50 },   // montée progressive à 50 VUs
    { duration: '1m', target: 50 },    // palier à 50 VUs
    { duration: '30s', target: 200 },  // pic à 200 VUs
    { duration: '1m', target: 200 },   // palier à 200 VUs
    { duration: '30s', target: 0 },    // redescente

    http_req_duration: ['p(95)<500'],   // 95% des requêtes en moins de 500ms

};

Avec des thresholds, la commande k6 run se termine avec un code d'erreur si le seuil est dépassé — exactement ce qu'il faut pour brancher un test de charge en CI/CD (module 14) sans surveillance humaine à chaque exécution.

Niveau 5 · Module 14

Brancher les tests en CI/CD

Un test qui ne s'exécute que quand quelqu'un pense à le lancer à la main finit par ne plus s'exécuter du tout. L'objectif du module 2 (shift-left) se concrétise ici : les tests tournent tout seuls à chaque push, et bloquent la mise en production si l'un d'eux échoue. C'est aussi une compétence QA très recherchée en 2026, au-delà de l'automatisation elle-même : comprendre le rôle du testeur dans le pipeline, pas seulement écrire des tests.

Le rôle réel du QA dans le pipeline

Code → Git (module 17) → Pull Request → CI → Tests automatisés (module 11) → Rapport → Échec ou Succès → Analyse → Correction → Nouvelle exécution. Le QA n'écrit pas que les tests qui tournent dans la CI : c'est lui qui lit le rapport quand ça passe au rouge, qui distingue un vrai bug d'un test fragile (module 11), qui documente l'anomalie (module 6/21) si c'est un vrai bug, et qui vérifie que la nouvelle exécution est bien verte avant de considérer que c'est corrigé — le cycle recommence à chaque nouveau commit, pas seulement à la fin du sprint.

Exercice — MISSION QA : "le pipeline est rouge, pourquoi ?"

Autonome

Un push sur main fait échouer le job e2e. Voici ce que montre l'onglet Actions de GitHub :

✗ e2e / pytest --browser chromium --tracing retain-on-failure

tests/test_checkout.py::test_paiement_carte FAILED

AssertionError: Expected "Commande validée" but got ""
  at test_checkout.py:34

1 failed, 47 passed in 58.2s

Avant de relancer le job "pour voir si ça repasse", applique une vraie méthode de diagnostic. (1) Ce commit a-t-il touché le tunnel de paiement, ou un fichier sans rapport ? (2) Ce test a-t-il déjà échoué sur des runs précédents (flaky connu) ou est-ce la première fois ? (3) Le test passe-t-il en local, sur la même branche ? (4) Si oui en local mais rouge en CI : qu'est-ce qui diffère entre les deux environnements ? Donne au moins 4 causes possibles distinctes et comment tu éliminerais chacune.

Voir la correction

Un pipeline rouge n'a jamais une seule cause possible — la première étape est de réduire le champ, pas de corriger au hasard.

1. Bug applicatif réel — le commit a modifié le service de paiement, le test a raison de rater : diff du commit + trace Playwright (module 11) pour voir l'état réel de la page au moment de l'échec.

2. Test flaky connu — vérifier l'historique du job sur les 10-20 derniers runs (onglet Actions) : si ce test échoue déjà de façon intermittente sans lien avec les commits, c'est le sujet du module 21, pas un bug du jour.

3. Problème d'environnement CI vs local — le test passe en local mais rate en CI : différence de fuseau horaire, de locale, de résolution d'écran, ou une variable d'environnement / un secret (module 14) absent ou différent sur le runner GitHub par rapport au poste local.

4. Problème de données — l'environnement de test partagé contient des données modifiées par un autre run parallèle (carte de test expirée, stock épuisé) : le test échoue sur la donnée, pas sur le code.

5. Problème d'infrastructure — le service de paiement de test (sandbox) était temporairement indisponible : vérifier le statut du service tiers avant de chercher plus loin dans le code.

La méthode qui départage ces cinq hypothèses : rejouer le test en boucle en local (module 21) pour écarter le flaky, comparer les variables d'environnement CI vs local, regarder si d'autres tests du même run ont aussi échoué (signe d'infra/données partagées plutôt qu'un bug isolé), et seulement ensuite lire le diff du commit si aucune des causes externes ne colle.

Le garde-fou à garder

Un test généré par IA reste un test que tu dois comprendre et pouvoir justifier — s'il échoue en CI, c'est toi qui le débogueras, pas l'IA qui l'a écrit. La tendance qui se confirme en 2026 n'est pas "l'IA remplace le testeur", c'est une collaboration où l'humain garde les cas complexes, l'UX et le jugement, et délègue les tâches répétitives.

Confidentialité : ce qu'on ne colle jamais dans un outil IA public

Un outil d'IA grand public (chat en ligne, extension de navigateur non validée par l'entreprise) n'est pas un environnement de confiance pour des données sensibles — ce qui y est collé peut être conservé, utilisé pour entraîner un modèle, ou simplement quitter le périmètre de l'entreprise. À ne jamais y coller : des données clients réelles (le module 26 explique pourquoi), des secrets (mots de passe, clés d'API, jetons d'authentification), et du code propriétaire non anonymisé qui révèle la logique métier de l'entreprise.

Exercice — Que peux-tu coller dans un outil IA public ?

Pour chacun des quatre cas suivants, dis si c'est sûr de le coller dans un outil d'IA public pour demander de l'aide, ou non — et pourquoi :

1. Une pile d'erreur (stack trace) qui contient une chaîne de connexion à la base de données avec un mot de passe réel en clair.

2. Une description de cas de test générique : "l'utilisateur doit voir un message d'erreur si le mot de passe fait moins de 8 caractères."

3. Un export CSV de 200 vraies commandes clients, pour demander à l'IA d'aider à écrire un script de test à partir de ces données.

4. Un extrait du code propriétaire de l'algorithme de calcul des prix de l'entreprise, pour demander pourquoi un bug s'y produit.

Voir la correction

1 — Non, pas tel quel. Le mot de passe doit être masqué ou remplacé par une valeur fictive avant de coller quoi que ce soit — c'est un secret, exactement comme une clé d'API.

2 — Oui, sans problème. Aucune donnée réelle, aucun secret : c'est une description de règle métier générique, exactement le genre de contenu pour lequel un outil d'IA est utile.

3 — Non. 200 vraies commandes clients contiennent des données personnelles réelles (module 26) — les coller dans un outil public, c'est les faire sortir du périmètre protégé de l'entreprise. L'alternative : générer un jeu de données fictif avec Faker qui a la même forme, et poser la question sur ce jeu-là.

4 — Non, par défaut. Un algorithme de calcul des prix est souvent un avantage concurrentiel de l'entreprise — le coller dans un outil public revient à le communiquer à l'éditeur de l'outil, voire indirectement à des concurrents selon la politique de réutilisation des données de l'outil. La bonne pratique : utiliser un outil d'IA interne validé par l'entreprise pour ce genre de code, ou génériser l'extrait (renommer les variables, remplacer les vrais barèmes par des valeurs inventées) avant de le montrer à un outil public.

Voir la correction

Étape 6 — Classifier avant de conclure (module 14)

Nouveau scénario, avant même de rédiger un ticket : le pipeline CI échoue sur test_application_code_promo, mais uniquement le vendredi après-midi, jamais en semaine. Voir la correction

Le motif temporel (vendredi après-midi seulement) pointe fortement vers un problème d'infrastructure ou d'environnement plutôt qu'un bug applicatif ou un test mal écrit : une tâche planifiée (sauvegarde, purge, déploiement d'une autre équipe) qui tourne à ce moment précis et ralentit ou perturbe l'environnement partagé de recette est une hypothèse bien plus probable qu'un bug de code qui ne se manifesterait qu'un jour précis de la semaine. La prochaine action n'est pas de corriger le test ni le code : c'est de vérifier avec l'équipe infra ce qui tourne sur cet environnement à ce créneau, et de comparer les temps de réponse de l'API à ce moment-là avec ceux d'un jour normal (module 22, observabilité) avant de conclure quoi que ce soit sur le code lui-même.

Niveau 6 · Module 18

Le Page Object Model

Les tests du module 11 fonctionnent très bien à trois. À trente, un problème apparaît : le sélecteur du champ "Mot de passe" est répété dans quinze fichiers, et le jour où le design change ce champ, il faut corriger quinze fichiers à la main. Le Page Object Model (POM) résout exactement ça.

Le principe : une classe par page, qui regroupe les sélecteurs et les actions possibles sur cette page. Les tests appellent des méthodes qui ont un sens métier, jamais un sélecteur brut.

pages/login_page.py

from playwright.sync_api import Page, expect


class LoginPage:
    def __init__(self, page: Page):
        self.page = page

    def goto(self):
        self.page.goto("https://novacart.exemple/connexion")

    def se_connecter(self, email: str, mot_de_passe: str):
        self.page.get_by_label("E-mail").fill(email)
        self.page.get_by_label("Mot de passe").fill(mot_de_passe)
        self.page.get_by_role("button", name="Se connecter").click()

    def attendre_erreur(self, message: str):
        expect(self.page.get_by_text(message)).to_be_visible()

export class LoginPage {
  constructor(private page: Page) {}

  async goto() {
    await this.page.goto('https://novacart.exemple/connexion');
  }

  async seConnecter(email: string, motDePasse: string) {
    await this.page.getByLabel('E-mail').fill(email);
    await this.page.getByLabel('Mot de passe').fill(motDePasse);
    await this.page.getByRole('button', { name: 'Se connecter' }).click();
  }

    await expect(this.page.getByText(message)).toBeVisible();
  }
}

Collaborer avec les développeurs pour la testabilité

Tous les sélecteurs de ce module (get_by_role, get_by_label) fonctionnent parce que le HTML de NovaCart expose des rôles et des labels accessibles — ce n'est pas toujours vrai sur une vraie application, surtout sur des composants visuels complexes (un graphique, un widget maison, une liste générée dynamiquement sans texte distinctif). Dans ce cas, la solution n'est pas de bricoler un sélecteur CSS fragile : c'est de demander au développeur d'ajouter un attribut data-testid dédié.

<!-- Avant : rien de stable à cibler -->
<div class="card_a83f x-42">...</div>

<!-- Après : un attribut dédié, jamais modifié pour des raisons de style -->
<div class="card_a83f x-42" data-testid="carte-produit-SKU-042">...</div>

La testabilité ne se limite pas aux sélecteurs : demander une route API dédiée pour créer un état de test directement (plutôt que de passer par dix clics d'interface juste pour arriver à l'écran à tester), ou des logs suffisamment détaillés pour diagnostiquer un échec sans avoir à rejouer le scénario en local (module 22) sont les mêmes types de demandes. Un développeur qui comprend que ces ajouts servent la fiabilité de toute l'équipe les accepte en général sans discussion — le rôle du QA est de les demander tôt, dès la conception d'une fonctionnalité, plutôt que de contourner leur absence avec des sélecteurs fragiles après coup.

Niveau 6 · Module 19

Architecture d'une suite d'automatisation

Le module 18 a montré le Page Object Model — une bonne pratique, mais qui ne répond qu'à une seule question : "comment isoler les sélecteurs d'une page". La vraie question que se pose une équipe qui adopte une suite d'automatisation est plus large : comment dix développeurs peuvent-ils maintenir cette suite pendant plusieurs années, sans qu'elle devienne un poids mort que plus personne n'ose toucher ? La réponse ne tient pas dans un seul pattern, mais dans une architecture complète.

Anatomie d'une suite professionnelle

Au-delà de quelques fichiers de test, une suite qui doit durer sépare clairement ses responsabilités :

tests-novacart/
├── pages/              # Page Object Model (module 18) — UI uniquement
├── services/           # clients API réutilisables (module 12)
├── fixtures/           # préparation et nettoyage de l'état de test
├── config/             # un fichier de config par environnement (module 33)
├── data/               # générateurs et jeux de données de test
├── helpers/            # assertions personnalisées, utilitaires partagés
├── tests/
│   ├── ui/
│   ├── api/
│   └── e2e/
├── reports/             # sortie des rapports HTML, captures, traces
└── .github/workflows/  # CI (module 14)

Chaque dossier a une seule responsabilité : un test qui échoue à cause d'un sélecteur se corrige dans pages/, jamais dans un fichier de test — exactement le principe déjà vu au module 18, mais généralisé à toute la suite plutôt qu'à une seule page.

Fixtures : séparer la préparation du test de sa logique

Une fixture prépare un état (navigateur ouvert, utilisateur connecté, données de test créées) et le nettoie après, indépendamment du contenu du test lui-même — c'est ce qui évite qu'un test dépende de ce qu'un autre test a laissé derrière lui.

conftest.py

import pytest
from playwright.sync_api import Page

@pytest.fixture
def utilisateur_connecte(page: Page):
    page.goto("/login")
    page.get_by_label("Email").fill("qa.test@novacart.com")
    page.get_by_label("Mot de passe").fill("Test1234!")
    page.get_by_role("button", name="Se connecter").click()
    yield page
    page.get_by_role("button", name="Déconnexion").click()   # nettoyage systématique

@pytest.fixture
def commande_de_test(api_client):
    commande = api_client.creer_commande(produits=["SKU-042"])
    yield commande
    api_client.supprimer_commande(commande["id"])   # aucune donnée de test ne survit au test

Un test qui utilise utilisateur_connecte et commande_de_test n'a plus besoin de savoir comment se connecter ou créer une commande — il reçoit un état prêt, garanti propre, et garanti nettoyé même si le test échoue en cours de route.

Configuration par environnement

Une suite codée en dur sur une seule URL ne peut tourner que là où elle a été écrite. Une suite professionnelle lit sa configuration depuis l'extérieur — variable d'environnement, fichier .env par environnement (module 33) — jamais depuis une constante codée en dur dans le test.

# config/staging.env
BASE_URL=https://staging.novacart.com
API_URL=https://api-staging.novacart.com
DB_HOST=staging-db.internal

# Lancer la suite contre un environnement précis :
BASE_URL=$(cat config/staging.env | grep BASE_URL | cut -d= -f2) pytest tests/

Secrets : jamais dans le code

Un mot de passe de test, une clé API, un token — même de test — ne doivent jamais apparaître en clair dans un fichier versionné sur Git. Ils vivent dans les secrets de la CI (GitHub Actions secrets., module 14) ou un gestionnaire de secrets dédié, et sont injectés en variables d'environnement au moment de l'exécution — exactement le même principe que pour une application en production.

# .github/workflows/tests.yml (extrait)
env:
  QA_TEST_PASSWORD: ${{ secrets.QA_TEST_PASSWORD }}
  API_TOKEN: ${{ secrets.STAGING_API_TOKEN }}

Parallélisation et retry : deux outils, un vrai risque

Faire tourner les tests en parallèle (pytest-xdist, ou les workers natifs de Playwright) réduit le temps total d'exécution — mais expose immédiatement toute donnée partagée entre tests, qui se transforme alors en source d'échecs aléatoires (module 21). Le retry automatique d'un test qui échoue (relancer 2-3 fois avant de déclarer l'échec) est utile pour absorber une vraie instabilité réseau ponctuelle — mais devient dangereux dès qu'il sert à masquer un test réellement mal écrit plutôt qu'à le corriger.

Reporting, traces et captures

Un test qui échoue en CI, sans personne devant l'écran, doit laisser des preuves exploitables : un rapport HTML consultable après coup, une capture d'écran au moment de l'échec, et une trace Playwright rejouable pas à pas (--tracing retain-on-failure, déjà vu au module 14) — sans ces preuves, chaque échec en CI oblige à relancer le test en local pour comprendre ce qui s'est passé, ce qui ralentit toute l'équipe.

Le POM est une brique, pas toute l'architecture

Une équipe qui applique le Page Object Model sans jamais s'occuper de fixtures, de configuration ou de secrets se retrouve avec des pages bien organisées... et une suite tout aussi difficile à maintenir sur le reste. L'architecture ne se résume à aucun pattern unique : c'est l'ensemble de ces décisions, prises ensemble, qui rend une suite maintenable dans la durée.

Niveau 6 · Module 20

Le module 4 a introduit le format Gherkin comme façon lisible d'écrire un critère d'acceptation. Le BDD va plus loin : ce même texte devient exécutable, sans le retaper en code — chaque ligne du scénario est reliée à une fonction par une "step definition". Côté Python, pytest-bdd fait ça avec pytest (module 11) ; côté TypeScript, playwright-bdd génère des tests Playwright standards à partir des fichiers .feature — les deux cohabitent avec les tests E2E déjà écrits, pas besoin d'un outil séparé comme Cucumber avec son propre runner.

Niveau 7 · Module 21

Diagnostiquer et éliminer les tests flaky

Un test flaky (instable) échoue parfois, sans qu'aucun changement de code n'explique la différence — il passe 9 fois sur 10, ou 95 fois sur 100, de façon apparemment aléatoire. C'est l'une des compétences les plus demandées en entretien QA Automation, et l'une des moins enseignées : savoir écrire un test ne suffit pas si on ne sait pas comprendre pourquoi il devient instable une fois exécuté des centaines de fois en CI.

Les causes les plus fréquentes

CauseCe qui se passe
Race condition / mauvaise attenteLe test vérifie un élément avant que l'interface ait fini de le mettre à jour — passe quand la machine est rapide, échoue quand elle est chargée.
Données partagéesDeux tests lisent ou modifient la même ligne en base — l'ordre d'exécution devient déterminant.
Dépendance entre testsUn test suppose qu'un autre a tourné avant lui et a laissé un état précis (module 19).
TimingUne animation, un debounce, un délai réseau variable selon la charge du moment.
RéseauUn appel externe réel (API tierce, service non mocké) répond parfois lentement ou échoue ponctuellement.
EnvironnementUn environnement de test partagé par plusieurs équipes, dont l'état change sans lien avec le test.
ParallélisationDes tests lancés en parallèle qui n'étaient prévus que pour tourner en série se marchent dessus.
Retry abusifUn retry automatique masque le symptôme sans jamais corriger la cause — le test "passe" en CI en 2ᵉ tentative pendant des mois.
Mauvaise isolationUn test dépend d'un singleton, d'un cache global, ou d'un état de navigateur laissé par le test précédent.

Attente explicite plutôt qu'attente fixe

Instable : la course entre le clic et le rendu

page.click("button.valider-commande")
time.sleep(2)                                    # pari sur une durée fixe
assert page.inner_text(".confirmation") == "Commande validée"
# Sur une machine chargée, ou si le serveur répond en 2.3s au lieu de 2s : échec

Stable : attendre l'état, pas une durée

page.click("button.valider-commande")
expect(page.locator(".confirmation")).to_have_text("Commande validée", timeout=10000)
# Playwright réessaie automatiquement jusqu'à ce que la condition soit vraie, ou jusqu'au timeout

La différence n'est pas cosmétique : time.sleep() parie sur une durée, expect(...).to_have_text(...) attend une condition — le test devient déterministe par rapport à ce qu'il vérifie, plutôt que par rapport à une hypothèse de timing.

Isoler les données de chaque test

Deux tests qui créent une commande avec le même identifiant produit et la même quantité entrent en compétition dès qu'ils tournent en parallèle. Générer une donnée unique par test (identifiant aléatoire, timestamp) élimine la collision à la racine :

import uuid

def test_creation_commande(api_client):
    email_unique = f"qa-{uuid.uuid4().hex[:8]}@novacart.com"   # jamais de collision entre tests parallèles
    commande = api_client.creer_commande(email=email_unique, produits=["SKU-042"])
    assert commande["statut"] == "en_attente"
Le retry n'est pas une correction

Configurer un retry automatique (2-3 tentatives) peut absorber une instabilité réseau ponctuelle et légitime — mais dès qu'un test "flaky connu" tourne toujours avec ce retry activé sans qu'on cherche la cause, il devient un tapis sous lequel on cache un vrai problème. Un test qui a besoin d'un retry pour passer de façon fiable mérite un ticket de diagnostic, pas juste une configuration qui le fait taire.

2. Analyser : le toast de notification est probablement une animation qui apparaît puis disparaît après quelques secondes ; le test lit inner_text immédiatement après le clic, sans attendre que le toast soit effectivement monté dans le DOM.

3. Cause : race condition / mauvaise attente — le test et l'interface ne sont pas synchronisés sur le même événement.

6. Éviter la régression : ajouter une règle de revue de code qui refuse tout time.sleep() dans un test d'interface, et documenter ce cas dans un guide interne "pièges courants" pour que l'équipe reconnaisse le même symptôme la prochaine fois.

Niveau 7 · Module 22

Observabilité : logs, métriques, traces

Une trace Playwright (module 11) montre ce que voyait le navigateur au moment de l'échec — mais pas pourquoi le serveur a répondu une erreur, ni si la base de données a mis 4 secondes à répondre, ni si un service tiers était en cause. Dès que NovaCart n'est plus un seul processus mais plusieurs services (API, base, paiement, notifications), diagnostiquer un échec E2E demande de savoir lire ce qui s'est passé derrière l'interface — c'est l'observabilité.

Les trois piliers

PilierCe qu'il montreExemple NovaCart
LogsDes événements horodatés, un par ligne : ce qui s'est produit, dans quel service.[api] 14:32:07 POST /paiement 500 — carte refusée (code: insufficient_funds)
MétriquesDes chiffres agrégés dans le temps : taux d'erreur, temps de réponse, volume de requêtes.Taux d'erreur de /paiement : 2% habituellement, 18% dans les 10 dernières minutes.
TracesLe chemin complet d'une requête à travers plusieurs services, avec la durée de chaque étape.Requête de checkout : 40ms (frontend) → 12ms (API) → 2400ms (base de données) → 30ms (notification).

Une trace Playwright et une trace d'observabilité ne sont pas la même chose malgré le nom commun : la première rejoue ce que voyait le navigateur, la seconde montre le trajet d'une requête à travers le système derrière ce navigateur.

Le correlation ID : relier les logs entre eux

Un incident implique presque toujours plusieurs services. Sans identifiant commun, retrouver les bonnes lignes de log dans chacun revient à chercher une aiguille dans une meule de foin, filtrée seulement par horodatage approximatif. La solution : chaque requête entrante reçoit un identifiant unique (X-Request-ID ou X-Correlation-ID), transmis à chaque service qu'elle traverse, et présent dans chaque ligne de log qu'elle génère.

[frontend]     14:32:07 req_a83f2 → POST /api/paiement
[api]          14:32:07 req_a83f2 → validation OK, appel service-paiement
[service-pay]  14:32:09 req_a83f2 → timeout après 2000ms, aucune réponse du fournisseur
[api]          14:32:09 req_a83f2 → 502 renvoyé au frontend

Avec ce req_a83f2, un grep (ou une recherche dans l'outil de log centralisé — Datadog, Grafana Loki, CloudWatch) sur les trois services suffit à reconstituer l'histoire complète d'une seule requête au milieu de milliers d'autres. Un test E2E qui échoue avec juste "502 Bad Gateway" ne dit rien ; le request-id renvoyé dans la réponse (souvent visible dans les headers réseau capturés par Playwright) est le point de départ pour aller lire les bons logs.

Les logs avant le "ça remarche en relançant"

Relancer un test qui échoue et voir qu'il passe la deuxième fois ne prouve rien — ça peut être un vrai flaky (module 21) comme un vrai problème d'infrastructure qui s'est résolu tout seul entre-temps. Avant de fermer l'incident, un réflexe simple : chercher le request-id de l'échec dans les logs. S'il y a une erreur serveur horodatée à la bonne seconde, ce n'est pas le test qui ment.

Exercice — MISSION QA : diagnostiquer un échec E2E avec les logs

Autonome

Un test test_ajout_avis_produit échoue : l'avis client n'apparaît jamais sur la page produit après soumission. Voici trois extraits de logs, du même intervalle de temps, sur trois services différents :

[frontend]      15:04:12 req_f291c → POST /api/avis {"produit": "SKU-042", "note": 5}
[api-avis]      15:04:12 req_f291c → avis créé en base, id=8821
[worker-index]  15:04:41 req_f291c → réindexation du produit SKU-042 pour recherche
[frontend]      15:04:13 GET /api/produits/SKU-042/avis → 0 avis retournés

Le test fait la requête GET immédiatement après avoir soumis le formulaire. Où est le problème, et est-ce un bug applicatif ou un problème de test ?

Voir la correction

Ce n'est pas un bug applicatif au sens strict : l'avis est bien créé (id=8821 à 15:04:12) mais la réindexation pour la recherche/l'affichage prend jusqu'à 15:04:41 dans le service worker-index — un traitement asynchrone, probablement une file d'attente. Le GET du test arrive à 15:04:13, une seconde après la création, bien avant que la réindexation soit terminée.

C'est donc un problème de test : il suppose une cohérence immédiate (écrire puis relire aussitôt) alors que le système est conçu avec une cohérence différée. La correction n'est pas un time.sleep() arbitraire (module 21) mais soit une attente explicite sur l'apparition de l'avis avec un timeout généreux (expect(...).to_have_text(..., timeout=15000)), soit — si l'équipe considère que 29 secondes de délai est un vrai problème produit — un ticket séparé sur la performance de la réindexation plutôt qu'une correction du test qui masquerait le vrai sujet.

La leçon générale : sans le request-id commun aux trois logs, ces trois lignes auraient semblé sans rapport ; avec lui, la chronologie exacte reconstitue en quelques secondes ce qui aurait pris de longues minutes à deviner depuis le seul message d'erreur du test.

Niveau 7 · Module 23

Relire une suite de tests comme une revue de code

Une pull request qui ajoute du code applicatif passe presque toujours par une revue. Une pull request qui ajoute des tests est souvent approuvée plus vite, avec moins d'attention — alors qu'un mauvais test coûte cher dans la durée : il ralentit la CI, génère du bruit (faux positifs), ou pire, donne une fausse confiance en ne testant en réalité rien d'utile. Relire des tests est une compétence à part entière, avec sa propre liste de vigilance.

Ce qu'on cherche dans une revue de tests

ProblèmeSignal à repérer
DuplicationLe même scénario de connexion recopié dans 15 fichiers de test plutôt qu'une fixture partagée (module 19).

La question à se poser en revue n'est pas seulement "est-ce que ce test passe ?" mais "si le comportement réel cassait demain, est-ce que ce test le détecterait ?".

Aller plus loin : JOIN, GROUP BY et sous-requêtes en contexte QA

Un SELECT sur une seule table suffit pour un cas simple. Mais la plupart des bugs de cohérence en base impliquent plusieurs tables reliées entre elles — c'est là que JOIN, GROUP BY et les sous-requêtes deviennent des outils QA à part entière, pas juste une compétence "développeur".

Vérifier qu'une commande est bien enregistrée avec toutes ses lignes — après un checkout dans l'interface, on confirme que chaque article affiché a bien sa ligne correspondante en base, avec le bon prix et la bonne quantité :

JOIN — commande NovaCart n°8823

SELECT c.id AS commande_id, c.statut, p.nom AS produit, l.quantite, l.prix_unitaire
FROM commandes c
JOIN lignes_commande l ON l.commande_id = c.id
JOIN produits p ON p.id = l.produit_id
WHERE c.id = 8823
ORDER BY p.nom;

Détecter une incohérence qu'aucun écran ne montre — une "commande fantôme" : une ligne existe dans commandes mais sans aucune ligne de détail associée, signe d'une insertion partielle qui a planté en cours de route. GROUP BY + HAVING la détecte en une requête, sur toute la base d'un coup — impossible à repérer en cliquant dans l'interface commande par commande :

GROUP BY / HAVING — commandes sans aucune ligne

SELECT c.id, COUNT(l.id) AS nb_lignes
FROM commandes c
LEFT JOIN lignes_commande l ON l.commande_id = c.id
GROUP BY c.id
HAVING COUNT(l.id) = 0;

Comparer un total affiché à un total recalculé — le cas classique où l'interface montre "Total : 47,50 €" mais où ce chiffre a été mal recalculé après une modification de panier. Une sous-requête compare la valeur stockée à la valeur qu'on recalcule à la volée à partir des lignes :

Sous-requête — total enregistré vs total recalculé

SELECT c.id,
       c.total AS total_enregistre,
       (SELECT SUM(l.quantite * l.prix_unitaire)
        FROM lignes_commande l
        WHERE l.commande_id = c.id) AS total_calcule
FROM commandes c
WHERE c.id = 8823;
-- si total_enregistre ≠ total_calcule, il y a un bug de recalcul côté serveur

Dans les trois cas, la logique QA reste la même que pour un test Playwright : on part de ce que l'utilisateur devrait voir, et on vérifie que la base raconte la même histoire — JOIN pour rassembler les tables liées, GROUP BY/HAVING pour repérer un écart sur un ensemble de lignes, une sous-requête pour comparer une valeur stockée à une valeur recalculée.

Exercice

Niveau 8 · Module 26

Vivre un sprint QA : specs incomplètes, tickets flous, changement de dernière minute

Jusqu'ici, chaque module isole une compétence. En entreprise, elles arrivent toutes en même temps, dans le désordre, avec des informations qui manquent et des priorités qui changent en cours de route. Ce module simule trois jours d'un sprint réel sur NovaCart — pas un exercice de plus, mais l'expérience de devoir avancer sans attendre que tout soit parfaitement clair.

Jour 1 — Une user story qui en dit trop peu

Le Product Owner dépose ceci dans le sprint, sans rien ajouter d'autre :

User story reçue

"En tant que client, je veux filtrer les produits par prix pour trouver plus vite ce qui m'intéresse."

Aucun critère d'acceptation (module 4) n'est fourni. C'est volontaire — c'est le cas le plus fréquent en vrai sprint, pas l'exception.

Jour 2 — Trois tickets Jira, des bugs pas encore confirmés

Le lendemain, trois tickets apparaissent dans le backlog, remontés par le support client. Aucun n'a encore été rejoué par un testeur — c'est justement ta première tâche du jour.

TicketDescription telle que reçue
NOVA-2201"Un client dit que le filtre affiche des articles à 45€ alors qu'il avait mis un maximum de 40€."
NOVA-2202"Le filtre prix fait planter la page de recherche sur mobile, mais seulement parfois."
NOVA-2203"Quand on filtre sur un prix qui ne correspond à aucun article, la page reste blanche au lieu d'afficher un message."

Jour 3 — Le changement de dernière minute

En fin de sprint, le Product Owner annonce en réunion : le champ prix ne sera finalement pas une valeur unique ("filtrer sous 40€") mais une fourchette ("entre 20€ et 40€"), pour coller à ce que font les concurrents. La spécification change, et certains cas de test déjà écrits ne veulent plus rien dire tels quels.

Exercice — MISSION QA : le rapport de sprint

Professionnelle

Rédige un mini rapport de sprint en trois parties, une par jour :

Jour 1 — Liste 5 questions précises à poser au Product Owner avant de pouvoir écrire le moindre cas de test sur cette user story (pense aux bornes, au format, aux cas sans résultat).

Jour 2 — Pour chacun des trois tickets, écris le cas de test qui permettrait de confirmer ou d'infirmer le bug décrit, sans avoir accès à l'application pour vérifier toi-même (tu dois raisonner uniquement à partir du texte du ticket, comme un QA qui reçoit un rapport de support avant de pouvoir le rejouer).

Jour 3 — Parmi les cas de test que tu aurais écrits pour "filtrer sous 40€", lesquels faut-il jeter, lesquels faut-il adapter, et lesquels restent valables tels quels une fois le filtre transformé en fourchette ?

Voir la correction

Jour 1 — Questions attendues : Le prix filtré est-il une borne unique (max) ou une fourchette (min et max) ? Que fait-on si le prix saisi ne correspond à aucun article — message d'erreur ou liste vide ? Le filtre s'applique-t-il au prix affiché TTC ou au prix hors taxes ? Peut-on saisir un prix négatif ou non numérique, et que doit-il se passer ? Le filtre se combine-t-il avec d'autres filtres déjà existants (catégorie, marque), et si oui dans quel ordre ? Ce sont exactement les zones d'ombre qu'une spécification incomplète laisse ouvertes — les découvrir avant d'écrire un cas de test évite de tester la mauvaise chose.

Jour 2 — NOVA-2201 : cas de test "Filtrer avec un maximum de 40€ doit exclure tout article strictement au-dessus de 40€" — si un article à 45€ apparaît, le bug est confirmé ; sinon, il faut demander au client la valeur exacte saisie (peut-être 45€ était en réalité le prix avant une remise appliquée après filtrage). NOVA-2202 : "seulement parfois" est le signal classique d'un bug lié à des données précises ou à un appareil précis (module 21, flaky) — le cas de test doit préciser un modèle de téléphone, une taille d'écran, et un jeu de résultats particulier (ex. plus de 50 articles retournés) avant de pouvoir conclure à un vrai bug plutôt qu'à un incident isolé. NOVA-2203 : cas de test direct — "Filtrer sur un prix ne correspondant à aucun article doit afficher un message explicite, jamais une page blanche" ; ce ticket est le plus simple à confirmer, une page blanche étant un résultat observable sans ambiguïté.

Jour 3 — À jeter : tout cas de test qui suppose un champ unique côté interface (ex. "vérifier qu'un seul champ prix est présent"). À adapter : les cas sur les valeurs limites (ils restent utiles mais doivent désormais s'appliquer aux deux bornes, min et max, plutôt qu'à une seule) et le cas du ticket NOVA-2201 (le "maximum" devient la borne haute de la fourchette). À garder tel quel : le cas du ticket NOVA-2203 (prix sans résultat) reste valable quelle que soit la forme du filtre, et le cas de non-régression sur la combinaison avec d'autres filtres. La bonne pratique ici n'est pas de tout réécrire par précaution, mais d'identifier précisément ce que le changement invalide réellement — un changement de spec, comme un changement de code, mérite son propre petit diagnostic d'impact.

Niveau 8 · Module 27

RGPD et données de test

Tous les exemples de ce cours utilisent test@novacart.fr — jamais une vraie adresse cliente. Ce n'est pas un détail de style, c'est la règle : copier la base de production dans un environnement de test moins protégé est une des façons les plus courantes de créer une fuite de données personnelles, et une infraction au RGPD dès qu'un environnement de test contient des données réelles de clients européens.

Deux techniques à distinguer

TechniquePrincipeRéversible ?
PseudonymisationRemplacer les données identifiantes par un identifiant technique, avec une table de correspondance gardée à partOui, avec la clé
AnonymisationRemplacer définitivement par des données inventées, sans moyen de remonter à la personne réelleNon — c'est le but

Pour la grande majorité des cas de test (module 5), l'anonymisation totale suffit et évite tout risque : la règle de validation d'un mot de passe se teste aussi bien avec un compte entièrement fictif qu'avec un vrai. Une bibliothèque comme Faker (portée dans la plupart des langages) génère en une ligne des jeux de données réalistes mais inventés — noms, adresses, numéros de carte au format valide mais fictif :

fixtures/comptes_test.py

from faker import Faker

fake = Faker("fr_FR")


def generer_compte_test():
    return {
        "email": fake.email(),
        "nom": fake.name(),
        "adresse": fake.address(),

fixtures/comptesTest.ts — équivalent TypeScript

Question à se poser avant d'ouvrir un environnement de test

Si cet environnement était compromis demain, quelles données personnelles réelles seraient exposées ? Si la réponse n'est pas "aucune", il y a un risque de conformité à traiter avant de passer à l'outillage — pas après.

Exercice

Un testeur copie 200 lignes de la table clients de production vers l'environnement de staging pour "avoir des données réalistes". Quel est le problème, et quelle alternative proposer avec les outils de ce module ?

Voir la correction

Le problème : des données personnelles réelles de clients se retrouvent dans un environnement moins protégé — un risque RGPD direct. L'alternative : générer des comptes fictifs mais réalistes avec Faker, comme dans l'exemple du module.

Niveau 9 · Module 29

Sécurité applicative avec OWASP ZAP

Le module 3 citait la sécurité comme famille de test non-fonctionnelle, sans outil. OWASP ZAP (Zed Attack Proxy) comble ce vide : c'est un scanner gratuit qui se place entre le navigateur et NovaCart, observe le trafic, puis envoie automatiquement des variantes suspectes des requêtes pour chercher les failles les plus courantes — celles listées dans l'OWASP Top 10, la référence du secteur (injection, authentification cassée, en-têtes de sécurité manquants…).

Terminal — scan automatisé en ligne de commande

docker run -t zaproxy/zap-stable zap-baseline.py \
  -t https://staging.novacart.exemple \
  -r rapport-zap.html

Sur NovaCart, un scan de base sur /connexion repère par exemple l'absence d'en-tête Content-Security-Policy, ou une page qui accepte une entrée non échappée dans le champ de recherche — des signaux à faire vérifier par un développeur, pas nécessairement des failles confirmées.

Ce que ZAP ne fait pas

Un scan automatique trouve des vulnérabilités techniques génériques. Il ne trouve pas les failles de logique métier — par exemple, un utilisateur qui accède au panier d'un autre en changeant simplement l'identifiant dans l'URL. Ce genre de cas se teste manuellement, avec les techniques du module 5 appliquées à un objectif malveillant plutôt que fonctionnel.

Exercice

Un scan OWASP ZAP ne remonte aucune faille sur /panier, mais un testeur découvre manuellement qu'en changeant l'identifiant dans l'URL il voit le panier d'un autre client. Pourquoi ZAP n'a-t-il rien trouvé ?

Voir la correction

C'est une faille de logique métier (autorisation), pas une vulnérabilité technique générique — exactement ce que ce module signale comme hors du périmètre d'un scanner automatique. Ce genre de cas se teste manuellement.

JWT : ce qu'un testeur QA vérifie sans être cryptographe

Un token JWT (module 11 pour son usage en authentification) encode ses informations en clair, simplement encodées en base64 — pas chiffrées. Un testeur QA n'a pas besoin de casser une signature pour repérer des risques concrets :

Point à vérifierCe que ça révèle
Expiration (exp) présente et raisonnableUn token sans expiration, ou valide 10 ans, reste exploitable indéfiniment s'il fuite
Contenu du payload (décodable sur jwt.io, sans la clé secrète)Un mot de passe ou une donnée sensible ne doit jamais apparaître en clair dans le payload
Un token modifié (payload changé, signature laissée telle quelle) est-il rejeté ?Si l'API accepte quand même le token, la signature n'est pas vérifiée côté serveur — faille critique
Algorithme none accepté ?Une vulnérabilité historique connue : certaines bibliothèques acceptaient un token sans aucune signature si l'en-tête déclarait "alg": "none"

Le deuxième test du tableau se vérifie en quelques lignes, sans outil spécialisé : prendre un token valide, changer un caractère dans le payload décodé, le ré-encoder, et observer si l'API le refuse toujours (comportement attendu) ou l'accepte (faille à signaler immédiatement).

Cookies de session : trois indicateurs à lire dans l'onglet réseau

Un cookie de session mal configuré est aussi risqué qu'un token JWT mal vérifié — et se contrôle en quelques secondes dans les DevTools du navigateur (onglet Application ou Réseau), sans outil supplémentaire :

AttributRôleAbsent = risque
HttpOnlyInterdit l'accès au cookie depuis JavaScriptUn script injecté (XSS) peut voler le cookie de session
SecureN'envoie le cookie que sur une connexion HTTPSLe cookie peut circuler en clair sur une connexion non chiffrée
SameSiteLimite l'envoi du cookie aux requêtes venant du même siteExpose à des attaques CSRF (une autre page déclenche une action au nom de l'utilisateur connecté)

Sur NovaCart, un exemple de payload manuel simple pour vérifier qu'un champ de recherche échappe correctement son entrée : saisir <script>alert(1)</script> dans le champ recherche et observer si le texte s'affiche tel quel (correct) ou si le script s'exécute (faille XSS) — le même réflexe qu'un scan automatique appliqué plus haut, ici fait à la main sur un cas ciblé.

Exercice — MISSION QA : audit d'un cookie de session

Semi-guidée

Voici l'en-tête Set-Cookie renvoyé après connexion sur l'environnement de staging de NovaCart :

Set-Cookie: session=eyJhbGciOi...; Path=/

Identifie ce qui manque, le risque concret associé à chaque absence, et la correction attendue.

Voir la correction

Aucun des trois attributs de sécurité n'est présent :

1. HttpOnly absent — un script malveillant injecté sur la page (via une faille XSS ailleurs sur le site) peut lire ce cookie avec document.cookie et l'exfiltrer. Correction : ajouter HttpOnly.

2. Secure absent — le cookie peut être transmis sur une connexion HTTP non chiffrée si elle existe, exposant la session à une interception réseau. Correction : ajouter Secure (nécessite HTTPS partout, ce qui est déjà le cas en production).

3. SameSite absent — le comportement par défaut varie selon le navigateur ; explicite vaut mieux qu'implicite. Correction : SameSite=Lax pour un site e-commerce classique (protège contre le CSRF tout en gardant les liens externes fonctionnels).

En-tête corrigé attendu : Set-Cookie: session=eyJhbGciOi...; Path=/; HttpOnly; Secure; SameSite=Lax

Niveau 9 · Module 30

Environnements reproductibles avec Docker

"Ça passe sur ma machine mais pas en CI" est un symptôme classique : une version de Node différente, une police système absente, une dépendance installée à la main un jour et oubliée. Docker élimine cette classe entière de problèmes en empaquetant exactement le même environnement, partout.

Dockerfile — Python, pour exécuter les tests Playwright du module 11

FROM mcr.microsoft.com/playwright/python:v1.48.0-jammy

WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .

CMD ["pytest", "--browser", "chromium"]

Dockerfile — TypeScript (équivalent)

FROM mcr.microsoft.com/playwright:v1.48.0-jammy

WORKDIR /app
COPY package*.json .
RUN npm ci
COPY . .

CMD ["npx", "playwright", "test"]

La même image tourne en local (docker build -t novacart-tests . && docker run novacart-tests) et dans le pipeline GitHub Actions du module 14 — plus de surprise entre "chez moi" et "en CI", parce que c'est littéralement le même système de fichiers qui exécute les tests dans les deux cas. Les deux images officielles Microsoft (playwright pour Node, playwright/python pour Python) embarquent déjà les navigateurs et leurs dépendances système — pas besoin de gérer soi-même l'installation de Chromium/Firefox/WebKit dans l'image.

Une fois cette reproductibilité acquise, la question de l'échelle se pose naturellement : faire tourner les tests de charge du module 13 depuis une seule machine locale limite le nombre d'utilisateurs virtuels simulables de façon réaliste. Des VM cloud (AWS, Azure) permettent de lancer ces mêmes conteneurs depuis plusieurs régions à la fois — un sujet d'infrastructure à part entière, qui dépasse ce cours, mais qui repose entièrement sur la reproductibilité que Docker apporte ici.

Exercice

La même image tourne en local et en CI — donc littéralement la même version de navigateur et les mêmes dépendances dans les deux cas. Il ne peut plus y avoir de divergence d'environnement à l'origine du problème.

Une certification qui reste utile en complément : ISTQB Foundation Level

Contrairement au certificat NovaSavo évoqué au tout début de ce parcours, l'ISTQB Foundation Level (CTFL) est la certification la plus reconnue au monde en test logiciel — délivrée par un organisme indépendant, présente dans une bonne partie des offres d'emploi "testeur QA" comme atout, rarement comme prérequis strict. Pour un profil sans diplôme informatique, une certification indépendante et reconnue internationalement peut compenser ce qu'un diplôme classique aurait démontré — elle dit à un recruteur "quelqu'un d'autre que moi a déjà vérifié ce que je sais". Utile en complément d'un portfolio, donc, mais pas un substitut : sans projets concrets à montrer, la certification seule convainc rarement.

Étude de cas — le ticket flou

Un product owner t'écrit : "Le bouton de paiement ne marche pas parfois, peux-tu regarder ?" C'est tout ce que tu as. Que fais-tu avant d'écrire le moindre cas de test ?

Voir la correction

Avant d'écrire quoi que ce soit, on clarifie : "parfois" veut dire quoi — un navigateur en particulier, un compte en particulier, une condition réseau ? On demande l'environnement concerné (module 33 — DEV, recette, prod ?), on essaie de reproduire soi-même avec plusieurs comptes et navigateurs, on regarde les logs ou le monitoring s'ils existent. Le réflexe à éviter : se mettre à écrire des cas de test sur une hypothèse non vérifiée. Une fois le déclencheur identifié (souvent une condition précise : montant à zéro, session expirée, double-clic), le cas de test devient trivial à écrire — le vrai travail était l'investigation, pas l'écriture.

Entretien blanc : structurer une réponse sous pression

La question la plus redoutée n'est pas la plus technique — c'est souvent la plus ouverte, celle où on ne sait pas par où commencer.

Entretien blanc

Le recruteur te dit : "On va tester ta réflexion. Comment testerais-tu la fonctionnalité 'ajouter au panier' d'un site e-commerce ? Tu as deux minutes." Structure une réponse à voix haute avant de regarder la correction.

Voir la correction

Une réponse solide suit un ordre visible, pas une liste de cas au hasard : d'abord le chemin heureux (ajouter un produit disponible, vérifier qu'il apparaît dans le panier avec la bonne quantité et le bon prix) ; puis les cas limites (quantité maximale en stock, produit qui devient indisponible entre l'affichage et le clic, ajout du même produit deux fois) ; puis les cas d'erreur (rupture de stock, utilisateur non connecté selon le site) ; et enfin, si le temps le permet, un mot sur le non-fonctionnel (le panier reste-t-il après rafraîchissement de la page ? après changement d'onglet ?). Dire cet ordre à voix haute — "je vais commencer par le chemin heureux, puis les limites, puis les erreurs" — vaut autant que le contenu : ça montre une méthode, pas une improvisation. C'est exactement la structure des techniques du module 5, appliquée en direct.

Les environnements : de DEV à PROD

Un test ne s'exécute jamais "quelque part au hasard" — il tourne dans un environnement précis, et cet environnement change ce qu'on a le droit d'y faire, qui y intervient, et quels tests y ont du sens. Un testeur qui ne sait pas dans quel environnement il se trouve peut, sans le vouloir, valider un correctif qui n'a jamais tourné sur une configuration proche de la production — ou pire, toucher à de vraies données clients (module 27). Ce module reprend la chaîne Développement → Intégration → Recette → Préproduction → Production, telle qu'elle existe dans la plupart des organisations, avec le rôle précis du QA à chaque étape.

Les deux visions décrivent la même réalité de terrain avec un découpage différent. Deux scénarios pratiques

Scénario 1 — Un bug apparaît en préproduction (lenteur anormale sous charge) alors que tous les tests fonctionnels étaient passés en recette. Est-ce contradictoire ? Non : la recette valide le comportement fonctionnel avec un jeu de données réduit, la préproduction valide la performance avec une configuration et un volume proches du réel — deux environnements, deux objectifs différents, un bug de performance peut très bien être invisible tant qu'on n'a pas testé à l'échelle.

Scénario 2 — Un testeur reçoit une demande urgente : "connecte-toi directement à la base de production pour vérifier ce compte client". C'est exactement la règle non négociable du module 24 : jamais de connexion à la production pour un test, quelle que soit l'urgence — la bonne réponse est de reproduire le cas en recette avec un compte fictif équivalent, ou de faire remonter la vérification à quelqu'un habilité à consulter la production en lecture seule, sans y exécuter de test.

Exercice

Une équipe NovaCart teste une nouvelle fonctionnalité de recherche. Les tests fonctionnels passent tous en recette. Avant la mise en production, quel environnement doit encore valider quoi, et pourquoi ne peut-on pas passer directement de la recette à la production ?

Voir la correction

La préproduction doit encore valider la performance sous charge réaliste et l'absence de régression, dans une configuration identique à la production ("iso-prod") — ce que la recette, avec son jeu de données réduit, ne peut pas garantir. Passer directement de la recette à la production reviendrait à découvrir un problème de charge ou de compatibilité devant les vrais utilisateurs, au pire moment possible.

L'erreur classique

Sur ce genre de page, le réflexe du débutant est d'ajouter time.sleep(3) partout "pour être sûr". C'est fragile (trop court sur une machine lente, trop long partout ailleurs) et ça ralentit toute la suite. Playwright attend déjà automatiquement qu'un élément soit visible, activable, stable — le vrai travail est de choisir le bon sélecteur et, au pire, un timeout explicite comme dans le dernier exemple.

Structurer en Page Object Model, dans les deux langages

Quatre tests plats comme ci-dessus, ça reste lisible. Une vraie suite d'automatisation grandit vite — c'est là que le Page Object Model (module 18) évite que chaque nouveau test réécrive les mêmes sélecteurs. Voici la page d'alertes JS réécrite en objet de page, en Python puis en TypeScript :

pages/alerts_page.py

from playwright.sync_api import Page


class AlertsPage:
    def __init__(self, page: Page):
        self.page = page
        self.result = page.locator("#result")

    def ouvrir(self):
        self.page.goto("https://the-internet.herokuapp.com/javascript_alerts")

    def declencher_alerte_simple(self):
        self.page.once("dialog", lambda dialog: dialog.accept())
        self.page.get_by_role("button", name="Click for JS Alert").click()

import { Page, Locator } from '@playwright/test';

export class AlertsPage {
  readonly page: Page;
  readonly result: Locator;

  constructor(page: Page) {
    this.page = page;
    this.result = page.locator('#result');
  }

  async ouvrir() {
    await this.page.goto('https://the-internet.herokuapp.com/javascript_alerts');
  }

  async declencherAlerteSimple() {
    this.page.once('dialog', dialog => dialog.accept());
    await this.page.getByRole('button', { name: 'Click for JS Alert' }).click();
  }
}

Le pipeline : de git push au rapport

C'est ici que ce projet se distingue des trois précédents : la suite ci-dessus ne vaut rien tant que personne ne l'exécute. Le workflow GitHub Actions (module 14) construit l'image Docker du module 30, y fait tourner les deux suites, et publie le rapport HTML même en cas d'échec — pour que la personne qui review la PR puisse cliquer et voir exactement ce qui a cassé.

.github/workflows/tests.yml

name: Tests NovaCart Portfolio

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  tests:
    runs-on: ubuntu-latest
    container: mcr.microsoft.com/playwright/python:v1.48.0-jammy
    steps:
      - uses: actions/checkout@v4
      - name: Installer les dépendances
        run: pip install -r requirements.txt
      - name: Lancer la suite UI + API
        run: pytest tests/ --html=rapport.html --self-contained-html
      - name: Publier le rapport (même en cas d'échec)
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: rapport-de-tests
          path: rapport.html

Le job tourne dans le conteneur playwright/python du module 30 plutôt que directement sur la machine du runner — même garantie de reproductibilité : ce qui passe en local dans Docker passe en CI, et inversement. Un push qui casse un test bloque la fusion automatiquement (branch protection), et la personne qui a cassé le test peut ouvrir rapport.html directement depuis l'onglet Artifacts, sans relancer quoi que ce soit sur sa machine.

Exercice — MISSION QA : l'audit complet

Voir une correction possible

Bloquants (risque réel) : mot de passe en clair dans le code source (PASSWORD, module 19) ; assert True dans test_recherche qui ne teste littéralement rien (module 23) ; test_2 dépend implicitement de l'état laissé par test_1 — aucun des deux tests n'est autonome (module 19 et 21) ; aucune CI configurée, donc rien ne s'exécute automatiquement à chaque changement (module 14) ; assertions status_code != 500 beaucoup trop permissives, un 401 ou 403 passerait sans être détecté (module 23).

Inconfort, à corriger mais moins urgent : noms de tests non descriptifs (test_1, test_2) qui ne disent rien de ce qu'ils vérifient ; time.sleep() systématique plutôt qu'une attente explicite, source de lenteur et de flakiness (module 21) ; aucune séparation UI/API dans la structure du dépôt (module 19) ; pas de .gitignore visible ; README qui ne documente ni le contexte ni comment lancer réellement la suite.

Neuf problèmes distincts couvrant quatre catégories différentes — un vrai audit professionnel ne se contente jamais de dire "c'est mal écrit", il nomme précisément chaque défaut pour pouvoir le prioriser.
