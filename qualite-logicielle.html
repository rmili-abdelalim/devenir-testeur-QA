Les fondamentaux

Partie 1 · Module 01

Tester, qu'est-ce que ça veut dire

Tester un logiciel, c'est l'exécuter volontairement pour trouver les endroits où il se comporte mal — avant que quelqu'un d'autre ne le découvre en production. Ce n'est pas prouver qu'un programme fonctionne (on ne peut jamais le prouver complètement), c'est réduire le risque de surprise.

Trois mots qu'on confond souvent :

TermeCe que c'est
TestL'activité concrète : exécuter le logiciel, comparer le résultat obtenu au résultat attendu.
QC — Contrôle qualitéL'ensemble des activités qui vérifient que le produit est conforme (dont le test fait partie).
QA — Assurance qualitéL'ensemble des activités qui améliorent le processus de fabrication, pour que les défauts apparaissent moins souvent en amont.

En clair : un testeur QC clique sur le bouton "payer" de NovaCart avec une carte invalide pour voir ce qui se passe. Une démarche QA se demande pourquoi ce cas n'était pas prévu dans les specs, et change le process d'écriture des tickets pour que ça n'arrive plus. Dans la vraie vie, un même poste fait souvent les deux.

Pourquoi ça coûte de ne pas tester

Un bug coûte à peu près 10 fois plus cher à corriger à chaque étape où il n'est pas attrapé : trouvé pendant que le développeur écrit le code, c'est quasi gratuit ; trouvé en recette, ça mobilise un testeur et un aller-retour ; trouvé en production, ça mobilise le support, parfois les clients, parfois la réputation. Ce n'est pas un chiffre magique à retenir par cœur, c'est l'idée à retenir : plus un défaut est détecté tôt, moins il coûte. Toute la partie 2 de ce cours (l'automatisation) n'est qu'une façon de détecter plus tôt et plus souvent.

À retenir

Un test qui ne trouve jamais rien n'est pas forcément un mauvais test — mais un testeur qui ne trouve jamais rien, sur un logiciel qui a des bugs en production, cherche probablement au mauvais endroit. On verra comment mieux choisir où chercher dans le module 5.

Exercice

NovaCart remarque que la moitié des bugs remontés en production concernent des cas jamais prévus dans les tickets, et décide de changer sa façon d'écrire les spécifications pour que ces cas soient pensés en amont. Est-ce une activité de QC ou de QA ? Justifie en une phrase.

Voir la correction

C'est de la QA : on ne corrige pas un défaut sur le produit lui-même (ça, ce serait du QC), on change le processus de fabrication pour que ce type de défaut apparaisse moins souvent — exactement la distinction du tableau plus haut.

Partie 1 · Module 02

Où le test se glisse dans le cycle de dev

Historiquement (modèle en V), on testait à la toute fin : les devs livrent, les testeurs testent, ça arrive une fois. Le problème, c'est que le module 1 vient de le dire — plus on teste tard, plus c'est cher. Le monde a bougé vers deux idées complémentaires :

Shift-left : tester plus tôt

Faire remonter le test vers l'amont : un développeur écrit un test unitaire en même temps que sa fonction, une revue de code cherche les cas oubliés, un analyste écrit les critères d'acceptation avant même que le code existe. Sur NovaCart, ça veut dire : le critère "le champ carte bancaire refuse un numéro de moins de 13 chiffres" est écrit avant que le développeur code le formulaire de paiement, pas après.

Shift-right : apprendre aussi en production

Certains problèmes (charge réelle, comportements d'utilisateurs imprévus, pannes d'infrastructure) ne se voient qu'en conditions réelles. Le monitoring, les tests A/B, les déploiements progressifs (canary releases) sont une forme de test — plus tardive, mais qui complète le reste sans le remplacer.

ContexteRythme du testCe qui change concrètement
Cycle en VUne phase de test, en fin de projetLong feedback loop, bugs chers à corriger
Agile / ScrumÀ chaque sprint (1–2 semaines)Tests écrits avec les user stories, pas après
DevOps / CI-CDÀ chaque commitTests automatisés obligatoires, exécutés en minutes

C'est cette dernière ligne qui motive toute la partie 2 : si les tests s'exécutent à la main, "à chaque commit" est physiquement impossible. L'automatisation n'est pas un luxe, c'est ce qui rend le shift-left tenable.

Exercice

Classe ces trois pratiques dans le bon camp — shift-left ou shift-right : (1) un Product Owner écrit les critères d'acceptation avant que le développement commence, (2) un déploiement progressif limité à 5% des utilisateurs pour observer le comportement réel, (3) une revue de code qui cherche les cas oubliés avant la mise en recette.

Voir la correction

(1) et (3) sont du shift-left — le test remonte avant l'écriture ou juste après le code. (2) est du shift-right — on apprend depuis la production réelle, pas avant.

Partie 1 · Module 03

Les familles de tests

Deux découpages se superposent tout le temps dans le métier — il faut les garder séparés.

Fonctionnel vs non-fonctionnel

Le test fonctionnel vérifie ce que le logiciel fait : "quand j'ajoute un article au panier, le total se met à jour". Le test non-fonctionnel vérifie comment il le fait :

  • Performance — la page panier de NovaCart s'affiche en moins de 2 secondes avec 500 utilisateurs simultanés (module 13)
  • Sécurité — un utilisateur ne peut pas voir le panier d'un autre en modifiant l'URL
  • Utilisabilité — un nouvel utilisateur trouve le bouton "payer" sans aide
  • Compatibilité — le site fonctionne sur Safari mobile comme sur Chrome desktop
  • Accessibilité — le formulaire de paiement est utilisable au clavier et par un lecteur d'écran

Boîte noire, boîte blanche, boîte grise

ApprocheCe que le testeur voitExemple sur NovaCart
Boîte noireSeulement les entrées et les sorties, pas le codeSaisir un code promo et vérifier la réduction affichée
Boîte blancheLe code sourceVérifier que chaque branche if de la fonction de calcul de réduction est exécutée par au moins un test
Boîte griseUn peu des deuxSavoir que la réduction est plafonnée à 50 € en base de données, et tester spécifiquement cette limite depuis l'interface

Dans ce cours, le module 5 (conception de cas de test) est très majoritairement de la boîte noire — c'est ce dont un testeur QA a besoin en premier. Le module 11 (Playwright) reste aussi en boîte noire : on pilote l'interface comme le ferait un utilisateur, sans lire le code de l'application testée.

Exercice

Un testeur vérifie que chaque branche if de la fonction de calcul de réduction de NovaCart est exécutée par au moins un test : boîte noire, blanche ou grise ? Et s'il sait, sans lire le code, que la réduction est plafonnée à 50 € en base de données, et teste spécifiquement cette limite depuis l'interface ?

Voir la correction

La première situation est de la boîte blanche — il regarde le code pour décider quoi tester. La seconde est de la boîte grise : il connaît un détail interne (le plafond en base) mais teste depuis l'interface, sans lire le code.

Partie 1 · Module 04

Les niveaux de test

Un même bug peut être attrapé à plusieurs étages. Sur NovaCart, prenons la fonctionnalité "connexion utilisateur" et suivons-la à travers les quatre niveaux classiques.

NiveauCe qu'on isoleSur NovaCart, concrètementQui l'écrit, en général
UnitaireUne seule fonction, isolée du resteLa fonction validerMotDePasse(mdp) renvoie false pour un mot de passe de 5 caractèresLe développeur
IntégrationDeux composants qui communiquentLe service d'authentification appelle bien le service e-mail pour envoyer un code à deux facteursDéveloppeur ou testeur automaticien
SystèmeL'application entière, de bout en boutUn utilisateur peut se connecter, ajouter un article, payer et recevoir un e-mail de confirmationÉquipe QA
AcceptationLe besoin métier réel, du point de vue clientLe Product Owner valide que le parcours correspond à ce qui a été commandéProduct Owner / client

Un exemple de critère d'acceptation, écrit en Gherkin (le format lisible utilisé par Cucumber, très répandu pour ce niveau) :

Scénario : Connexion avec identifiants valides
  Étant donné que je suis sur la page de connexion de NovaCart
  Quand je saisis un e-mail et un mot de passe valides
  Et que je clique sur "Se connecter"
  Alors je suis redirigé vers mon tableau de bord
  Et je vois mon prénom en haut de la page
Pourquoi ça compte

Plus on descend vers "unitaire", plus un test est rapide à exécuter et facile à isoler quand il échoue — mais moins il prouve que l'expérience utilisateur réelle fonctionne. C'est tout l'objet de la pyramide de tests, module 8.

Exercice

Le service d'authentification de NovaCart plante quand il tente d'appeler le service e-mail pour envoyer un code à deux facteurs — alors que les deux services, testés séparément, fonctionnent très bien. Quel niveau de test aurait dû attraper ce bug avant la mise en production ?

Voir la correction

Le niveau intégration : chaque composant est correct isolément, c'est leur communication qui casse — exactement ce que le test unitaire ne peut pas voir, et que le test système aurait vu bien trop tard.

Partie 1 · Module 05

Concevoir des cas de test

C'est le module que la plupart des cours bâclent — normalement celui qui devrait être le plus concret. Voici quatre techniques, chacune avec un cas de test réel dessus, pas juste la théorie.

1. Partitionnement en classes d'équivalence

Idée : si le programme traite un groupe de valeurs de la même façon, teste une seule valeur du groupe, pas toutes. Sur NovaCart, le champ mot de passe exige entre 8 et 20 caractères.

ClasseExemple de valeurRésultat attendu
Invalide — trop court"abc123"Rejeté
Valide"MotDePasse2026"Accepté
Invalide — trop long"a" × 25Rejeté

Trois cas suffisent à couvrir la règle entière, au lieu de tester 20 mots de passe différents pour rien.

2. Analyse aux valeurs limites

Les bugs adorent se cacher pile sur les frontières des classes ci-dessus — les erreurs de type < au lieu de <= sont le pain quotidien du développeur. On teste donc juste avant, sur, et juste après chaque limite (8 et 20 caractères) :

LongueurPositionRésultat attendu
7Juste sous la limite basseRejeté
8Limite basseAccepté
9Juste au-dessusAccepté
19Juste sous la limite hauteAccepté
20Limite hauteAccepté
21Juste au-dessusRejeté

Ces six cas, combinés aux trois du partitionnement, forment un jeu de tests solide pour une seule règle de validation — et ce sont exactement les cas qu'on automatisera au module 11.

3. Table de décision

Utile quand le résultat dépend de plusieurs conditions combinées. Sur NovaCart : que se passe-t-il à la connexion selon que l'e-mail est valide, le mot de passe correct, et le compte verrouillé (après 5 échecs) ?

E-mail valide ?Mot de passe correct ?Compte verrouillé ?Résultat
OuiOuiNonConnexion réussie
OuiNonNon"Mot de passe incorrect"
Oui—Oui"Compte verrouillé, réessayez dans 15 min"
Non——"Aucun compte associé à cet e-mail"

Chaque ligne de cette table devient un cas de test. C'est aussi le meilleur outil pour repérer les combinaisons que personne n'avait pensé à spécifier (ici : que dit-on si le mot de passe est faux et que le compte est déjà verrouillé ? La table force la question.)

4. Test de transition d'état

Utile quand un objet passe par des états distincts. Le compte NovaCart : Actif → (5 échecs) → Verrouillé → (15 min ou réinitialisation) → Actif. On teste les transitions valides, mais surtout les transitions invalides qui ne devraient pas être possibles : peut-on se connecter alors que le compte est verrouillé ? Le système doit refuser, quel que soit le mot de passe saisi.

Exercice

Le champ "code promo" de NovaCart doit accepter entre 4 et 8 caractères. En reprenant les deux premières techniques de ce module, liste les cas de test à écrire.

Voir la correction

Classes d'équivalence : une valeur invalide trop courte (ex. 3 caractères), une valeur valide (ex. 6 caractères), une valeur invalide trop longue (ex. 10 caractères). Valeurs limites : 3, 4, 5 autour de la borne basse, et 7, 8, 9 autour de la borne haute — six cas au total, sur le même principe que le mot de passe.

Sévérité ≠ priorité

Deux axes qu'on confond souvent en début de carrière :

  • Sévérité — l'impact technique du bug (mineur, majeur, critique, bloquant). Objectif, indépendant du contexte business.
  • Priorité — l'urgence de le corriger, décidée par l'équipe produit (peut dépendre d'une date de lancement, d'un client important, etc.).

Exemple : une faute d'orthographe sur la page d'accueil est sévérité mineure mais peut être priorité haute se déroule un lancement presse le lendemain. À l'inverse, un bug qui plante une fonctionnalité rarement utilisée peut être sévérité critique mais priorité basse si le correctif est complexe et l'usage marginal.

Stratégie et plan de test

Avant d'écrire le premier cas de test, une équipe QA sérieuse répond à quelques questions par écrit — ça évite de tester deux fois la même chose et d'oublier un pan entier de l'application.

Section du planQuestion à laquelle elle répondExemple NovaCart
PérimètreQu'est-ce qui est testé, et surtout qu'est-ce qui ne l'est pas ?Le tunnel d'achat complet. Hors périmètre : le back-office de gestion des stocks
ApprocheManuel, automatisé, ou les deux ? À quels niveaux ?Automatisé pour la régression, manuel/exploratoire pour les nouvelles fonctionnalités
Critères d'entréeQuand peut-on commencer à tester ?L'environnement de staging est déployé et stable
Critères de sortieQuand peut-on dire "c'est testé" ?100% des cas critiques passent, 0 bug bloquant ouvert
RisquesOù sont les zones fragiles ?Le module de paiement, réécrit récemment

Tester en fonction du risque

On n'a jamais le temps de tout tester exhaustivement — le test basé sur les risques consiste à croiser deux facteurs pour décider où investir l'effort : la probabilité qu'un défaut existe (code récent, complexe, souvent modifié) et l'impact s'il survient (le paiement, pas la page "À propos"). Le module de paiement de NovaCart, récemment réécrit, cumule les deux — c'est là que va l'essentiel du budget de test, pas également réparti sur toute l'application.

Exercice

NovaCart a deux zones à tester avant une mise en production, mais pas le temps de tout couvrir : le module de paiement, récemment réécrit, et la page "À propos", inchangée depuis deux ans. Où concentrer l'effort, et pourquoi en termes de probabilité et d'impact ?

Voir la correction

Le module de paiement : probabilité de défaut élevée (code récent, donc moins éprouvé) et impact élevé (bloque toute vente) — les deux facteurs du test basé sur les risques pointent dans la même direction. La page "À propos" cumule au contraire faible probabilité et faible impact.

Partie 2 · Module 08

Pourquoi (et quoi) automatiser

Un test manuel coûte le même temps humain à chaque exécution. Un test automatisé coûte du temps une fois (pour l'écrire), puis quasiment rien à chaque exécution suivante. La bascule vaut le coup pour tout ce qui est répétitif, stable, et important — pas pour tout.

Bon candidat à l'automatisationMauvais candidat
Test de régression exécuté à chaque commitTest exploratoire d'une fonctionnalité tout juste livrée
Parcours critique (connexion, paiement)Détail visuel subjectif ("est-ce que ça a l'air pro ?")
Interface stable depuis plusieurs sprintsÉcran en pleine refonte, qui va encore changer
Calculs avec beaucoup de combinaisons (module 5)Test d'accessibilité fin nécessitant un jugement humain

La pyramide de tests

Le principe : beaucoup de tests unitaires (rapides, bon marché, faciles à isoler), moins de tests d'intégration, encore moins de tests de bout en bout (E2E — lents, plus fragiles, mais qui vérifient le vrai comportement utilisateur). Une variante plus récente et très citée en 2026, la testing trophy de Kent C. Dodds, met l'accent sur les tests d'intégration plutôt que sur les tests unitaires : l'idée est que tester "à peu près comme un utilisateur le ferait" donne plus confiance par test écrit. Dans ce cours, le module 11 (Playwright) se situe justement au niveau intégration/E2E — c'est là que la confiance utilisateur est la plus directe, et c'est pour ça qu'on commence par là niveau outillage.

Exercice

Classe ces quatre tests en bon ou mauvais candidat à l'automatisation : (1) la régression du tunnel d'achat à chaque commit, (2) un détail visuel subjectif sur un écran tout juste redessiné, (3) le calcul de réduction avec de nombreuses combinaisons, (4) un test exploratoire d'une fonctionnalité livrée hier.

Voir la correction

Bons candidats : (1) et (3) — répétitifs, stables ou avec beaucoup de combinaisons. Mauvais candidats : (2) et (4) — un écran encore instable et un jugement subjectif ne se prêtent pas à l'automatisation, exactement le tableau de ce module.

Partie 2 · Module 09

Choisir son langage

Le langage n'a pas besoin d'être ton préféré — il doit surtout coller à celui de l'équipe que tu testes, pour pouvoir lire leur code et parler le même vocabulaire.

LangageÉcosystème de testCourbe d'apprentissageTerrain naturel

Ce cours utilise Python pour la partie pratique — un choix assumé, pas un choix par défaut. TypeScript reste légèrement plus demandé dans les offres "QA automation" pures (détail au module 27), mais Python a deux avantages qui comptent davantage ici : pas besoin de mener deux apprentissages de front en parallèle (Python d'un côté, JavaScript/TypeScript de l'autre), et une compétence Python solide ouvre aussi vers la data, les scripts et l'IA. Playwright supporte Python nativement, à parité de fonctionnalités avec sa version TypeScript — ce n'est pas un choix de repli, c'est un vrai choix professionnel.

Exercice

Un testeur rejoint une équipe déjà 100% Java, avec Selenium et REST Assured en place depuis des années. Quel langage a le plus de sens pour lui, même si Python lui semble plus simple à apprendre ? Pourquoi ?

Voir la correction

Java — le principe de ce module est de coller au langage de l'équipe qu'on rejoint pour pouvoir lire son code et parler le même vocabulaire, pas de choisir le langage le plus confortable pour soi.

Pourquoi Selenium a-t-il vieilli ? Techniquement il fonctionne toujours, mais il pilote le navigateur via un protocole plus lent et plus sujet aux "tests fragiles" (flaky tests) qui échouent aléatoirement sans changement du logiciel testé — la cause n°1 de démotivation chez les testeurs, exactement ce que tu décrivais. Recommandation de ce cours

Playwright par défaut pour tout nouveau projet en 2026 — c'est ce qu'on installe au module suivant. Cypress reste un bon choix si une équipe JS/TS valorise surtout son expérience développeur au quotidien. Selenium garde un intérêt réel pour le test mobile natif via Appium, ou sur des systèmes legacy déjà bâtis dessus — ce n'est pas mort, c'est juste rarement le bon point de départ aujourd'hui.

Exercice

Une entreprise fait tourner depuis cinq ans une suite de tests mobiles natifs avec Selenium/WebDriver via Appium, stable et fiable. Faut-il migrer immédiatement vers Playwright parce que c'est l'outil recommandé par ce cours ?

Voir la correction

Non — ce module recommande Playwright par défaut pour les nouveaux projets, mais note explicitement que Selenium garde un intérêt réel pour le test mobile natif via Appium. Migrer une suite stable sans problème identifié serait du temps perdu, pas un progrès.

Partie 2 · Module 11

Playwright en pratique

On automatise maintenant exactement les cas de test écrits au module 5 (connexion NovaCart), avec Playwright piloté en Python via pytest — l'intégration officielle et la plus utilisée côté Python. Installation d'abord :

Terminal

python -m venv venv
source venv/bin/activate        # sous Windows : venv\Scripts\activate
pip install pytest-playwright
playwright install

Pas de fichier de config généré automatiquement comme en TypeScript — on crée simplement un dossier tests/ avec des fichiers test_*.py, que pytest détecte tout seul. Voici le premier vrai fichier de test, qui automatise trois cas du module 5 (mot de passe valide, trop court, compte verrouillé) :

tests/test_connexion.py

import re
from playwright.sync_api import Page, expect


def test_tc_conn_003_identifiants_valides_redirigent(page: Page):
    """TC-CONN-003 — identifiants valides redirigent vers le tableau de bord"""
    page.goto("https://novacart.exemple/connexion")
    page.get_by_label("E-mail").fill("test@novacart.fr")
    page.get_by_label("Mot de passe").fill("MotDePasse2026")
    page.get_by_role("button", name="Se connecter").click()

    expect(page).to_have_url(re.compile(r".*tableau-de-bord"))
    expect(page.get_by_text("Bonjour")).to_be_visible()


def test_tc_conn_014_mot_de_passe_de_7_caracteres_est_rejete(page: Page):
    """TC-CONN-014 — mot de passe de 7 caractères est rejeté"""
    page.goto("https://novacart.exemple/connexion")
    page.get_by_label("E-mail").fill("test@novacart.fr")
    page.get_by_label("Mot de passe").fill("abc1234")  # 7 caractères
    page.get_by_role("button", name="Se connecter").click()

    expect(page.get_by_text("au moins 8 caractères")).to_be_visible()
    expect(page).to_have_url(re.compile(r".*connexion"))  # pas redirigé


def test_tc_conn_021_compte_verrouille_refuse_meme_bon_mot_de_passe(page: Page):
    """TC-CONN-021 — compte verrouillé refuse même un bon mot de passe"""
    page.goto("https://novacart.exemple/connexion")
    page.get_by_label("E-mail").fill("verrouille@novacart.fr")
    page.get_by_label("Mot de passe").fill("BonMotDePasse1")
    page.get_by_role("button", name="Se connecter").click()

    expect(page.get_by_text("Compte verrouillé")).to_be_visible()

Terminal — exécuter les tests

pytest --browser chromium -v
pytest --browser chromium --tracing on   # garde une trace rejouable de chaque test

La commande --tracing on enregistre le déroulé complet (captures d'écran, réseau, DOM) de chaque test dans un fichier .zip, rejouable avec playwright show-trace trace.zip — l'équivalent Python du rapport HTML intégré côté TypeScript.

Trois choix qui évitent les tests fragiles

  • Sélectionner par rôle et par label (get_by_role, get_by_label) plutôt que par classe CSS — un changement de style ne casse pas le test, contrairement à un sélecteur du type .btn-primary-v2.
  • Ne jamais ajouter de time.sleep() fixe. Playwright attend automatiquement qu'un élément soit visible et stable avant d'agir — c'est la principale raison pour laquelle il est plus fiable que Selenium par défaut.
  • Un test, un comportement. Le nom de la fonction (test_tc_conn_014_...) reprend l'ID du cas de test écrit au module 6 — quand ça échoue en CI, on sait immédiatement quel cas métier est cassé, pas juste "un test sur 14 a échoué".
Et si l'équipe travaille en TypeScript ?

La logique de ce module — sélecteurs par rôle, pas de sleep, un ID de cas de test par nom de test — est strictement identique en TypeScript, seule la syntaxe change. Si un projet l'impose, tu sauras déjà quoi faire : il ne restera qu'à changer de dialecte.

Tester une API

Tout ne se teste pas par l'interface. Tester directement l'API de NovaCart est plus rapide et plus stable — pas de navigateur à démarrer, pas de CSS à charger.

Pour débuter : Postman

Interface graphique, aucune ligne de code nécessaire. On envoie une requête, on écrit une assertion dans l'onglet "Tests" — à noter, ces scripts sont toujours en JavaScript, quel que soit ton langage principal : c'est une particularité de l'outil, pas un choix à faire :

Postman — onglet Tests, sur POST /api/connexion

pm.test("Statut 200 pour identifiants valides", () => {
    pm.response.to.have.status(200);
});

pm.test("La réponse contient un token", () => {
    const body = pm.response.json();
    pm.expect(body).to.have.property('token');
});

Postman est le chemin le plus rapide pour vérifier une API à la main ou la documenter en équipe — mais dès qu'il faut faire tourner ça automatiquement en CI, on bascule vers du code.

En projet réel : Playwright (API testing)

Playwright ne teste pas que des pages web — son objet page.request teste aussi des API directement, dans le même fichier que les tests E2E du module 11, avec les mêmes fixtures pytest :

tests/test_api_connexion.py

from playwright.sync_api import Page


def test_connexion_renvoie_un_token_pour_un_compte_valide(page: Page):

        "email": "test@novacart.fr",
        "motDePasse": "MotDePasse2026",
    })

    assert reponse.status == 200
    corps = reponse.json()
    assert "token" in corps


def test_connexion_renvoie_401_pour_un_mauvais_mot_de_passe(page: Page):

        "email": "test@novacart.fr",

Partie 2 · Module 13

Tests de charge avec k6

Un test fonctionnel vérifie qu'une requête réussit. Un test de charge vérifie que ça tient quand des milliers de requêtes arrivent en même temps — k6 est aujourd'hui l'outil de référence pour ça, construit spécifiquement pour ce cas d'usage (contrairement à JMeter, plus ancien et plus lourd à configurer, encore utilisé mais de moins en moins recommandé pour un nouveau projet). Précision utile : les scripts k6 s'écrivent toujours en JavaScript, même si le reste de ta suite est en Python comme dans ce cours — c'est propre à l'outil, pas une incohérence.

charge-connexion.js

import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  vus: 50,           // 50 utilisateurs virtuels simultanés
  duration: '30s',
};

export default function () {
  const reponse = http.post('https://novacart.exemple/api/connexion', JSON.stringify({
    email: 'test@novacart.fr',
    motDePasse: 'MotDePasse2026',
  }), { headers: { 'Content-Type': 'application/json' } });

  check(reponse, {
    'statut est 200': (r) => r.status === 200,
    'répond en moins de 500ms': (r) => r.timings.duration < 500,
  });

  sleep(1);
}

Terminal

k6 run charge-connexion.js

k6 sort un rapport avec les métriques qui comptent vraiment sous charge : le p95 (95% des requêtes répondent plus vite que ce chiffre — plus parlant qu'une moyenne, que quelques requêtes très lentes peuvent fausser), et le taux d'erreur. C'est la combinaison "Playwright pour le fonctionnel/E2E, k6 pour la charge" qui domine chez les équipes JS/TS en 2026.

Partie 2 · Module 14

Brancher les tests en CI/CD

Un test qui ne s'exécute que quand quelqu'un pense à le lancer à la main finit par ne plus s'exécuter du tout. L'objectif du module 2 (shift-left) se concrétise ici : les tests tournent tout seuls à chaque push, et bloquent la mise en production si l'un d'eux échoue.

.github/workflows/tests.yml

name: Tests NovaCart

on:
  push:
    branches: [main, develop]
  pull_request:

jobs:
  e2e:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - run: pip install -r requirements.txt
      - run: playwright install --with-deps
      - run: pytest --browser chromium --tracing retain-on-failure
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: traces-playwright
          path: test-results/

Trois détails qui changent tout au quotidien : le job échoue (donc bloque la pull request) si un seul test échoue ; --tracing retain-on-failure (module 11) ne garde une trace rejouable que pour les tests qui ont raté, pas besoin de fouiller dans des centaines de traces inutiles ; et ça tourne sur chaque pull request, pas seulement sur main — donc le bug est visible avant la fusion, pas après.

Exercice

L'équipe veut aussi que le pipeline tourne automatiquement chaque nuit à 2h du matin, même sans commit, pour détecter une régression liée à une API externe. Quelle ligne ajouter au fichier YAML de ce module ?

Voir la correction 
on:
  push:
    branches: [main, develop]
  pull_request:
  schedule:
    - cron: '0 2 * * *'

Le déclencheur schedule avec une expression cron fait tourner le job à heure fixe, indépendamment de toute activité sur le dépôt.

L'IA dans la QA en 2026

À traiter avec le même recul que le reste de ce cours : ce que l'IA fait réellement bien aujourd'hui, sans survente.

Usage réel en 2026Ce que ça change concrètement
Génération de cas de test initiauxÀ partir d'une user story, un outil IA propose une première liste de cas — un point de départ à revoir avec les techniques du module 5, pas un livrable final
Sélecteurs auto-réparantsSi un bouton change de position ou de classe CSS, certains frameworks ajustent le sélecteur automatiquement plutôt que de faire échouer le test — réduit les faux positifs, source n°1 de fatigue chez les équipes QA

Le garde-fou à garder

Un test généré par IA reste un test que tu dois comprendre et pouvoir justifier — s'il échoue en CI, c'est toi qui le débogueras, pas l'IA qui l'a écrit. La tendance qui se confirme en 2026 n'est pas "l'IA remplace le testeur", c'est une collaboration où l'humain garde les cas complexes, l'UX et le jugement, et délègue les tâches répétitives.

Partie 2 · Module 16

Projet : ta première suite

Le module qui rassemble tout. Choisis une fonctionnalité réelle — d'une appli que tu utilises, ou continue avec NovaCart — et déroule ces cinq étapes dans l'ordre :

  1. Écris un mini plan de test (module 7) : périmètre en une phrase, 2–3 risques identifiés.
  2. Conçois 6 à 10 cas de test (module 5) en combinant au moins deux techniques — par exemple partitionnement + valeurs limites sur un champ de formulaire.
  3. Formalise-les avec le gabarit du module 6, ID inclus.
  4. Automatise-en trois avec Playwright (module 11) — commence par le cas nominal (le chemin qui marche), puis un cas d'erreur, puis un cas limite.
  5. Branche-les en CI (module 14) avec le fichier GitHub Actions fourni, adapté à ton dépôt.
Comment savoir que c'est réussi

Tes trois tests automatisés passent en local avec npx playwright test, et ils tournent aussi tout seuls dans l'onglet "Actions" de ton dépôt GitHub après un git push. Si un test échoue volontairement (change une valeur attendue pour le vérifier), la pull request doit s'afficher en rouge — sinon la CI n'est pas vraiment branchée.

Exercice

Avant de considérer ton mini-projet terminé : as-tu automatisé au moins un cas nominal (qui marche) ET un cas d'erreur (qui échoue volontairement) — pas seulement deux variantes qui passent toutes les deux ?

Voir la correction

Si tu n'as que des cas nominaux, ta suite ne prouve que ce qui marche déjà. Le vrai test de robustesse vient des cas d'erreur et des cas limites (module 5) — reviens en ajouter au moins un avant de considérer le projet terminé.

Partie 3 · Module 17

Git pour testeurs

Dès que le module 11 a produit un fichier tests/connexion.spec.ts, il vit dans un dépôt Git — comme le code de l'application. Un testeur qui ne sait pas versionner son propre code de test finit par écraser le travail d'un collègue ou par perdre le sien.

Le trajet minimal à connaître

CommandeÀ quoi elle sert
git clone <url>Récupérer le dépôt NovaCart en local, une seule fois
git checkout -b tests/paiementCréer une branche dédiée avant d'ajouter des tests — jamais directement sur main
git add tests/paiement.spec.tsSélectionner précisément ce qu'on va enregistrer
git commit -m "..."Enregistrer un instantané, avec un message qui dit pourquoi, pas juste "ajout tests"
git push -u origin tests/paiementEnvoyer la branche sur GitHub

Depuis GitHub, on ouvre une pull request — c'est exactement ce qui déclenche le pipeline du module 14 : la CI exécute les nouveaux tests avant que quiconque approuve la fusion. Si deux testeurs modifient tests/connexion.spec.ts en parallèle sur des branches séparées, Git signale un conflit à la fusion plutôt que d'écraser silencieusement le travail de l'un des deux — c'est précisément l'intérêt de ne jamais travailler directement sur main.

Réflexe à prendre

Un fichier .gitignore à la racine du projet doit exclure venv/, __pycache__/, .pytest_cache/ et test-results/ — ce sont des dossiers régénérés à chaque exécution, qui n'ont rien à faire dans l'historique du dépôt.

Exercice

Deux testeurs créent chacun une branche à partir de main pour ajouter des tests dans le même fichier tests/connexion.spec.ts. Que se passe-t-il quand le second essaie de fusionner sa branche après le premier ?

Voir la correction

Git signale un conflit à la fusion plutôt que d'écraser silencieusement le travail du premier. Le second doit ouvrir le fichier, choisir quelles lignes garder des deux versions, puis valider la résolution avant de pouvoir fusionner — jamais forcer un écrasement.

Partie 3 · Module 18

Le Page Object Model

Les tests du module 11 fonctionnent très bien à trois. À trente, un problème apparaît : le sélecteur du champ "Mot de passe" est répété dans quinze fichiers, et le jour où le design change ce champ, il faut corriger quinze fichiers à la main. Le Page Object Model (POM) résout exactement ça.

Le principe : une classe par page, qui regroupe les sélecteurs et les actions possibles sur cette page. Les tests appellent des méthodes qui ont un sens métier, jamais un sélecteur brut.

pages/login_page.py

from playwright.sync_api import Page, expect


class LoginPage:
    def __init__(self, page: Page):
        self.page = page

    def goto(self):
        self.page.goto("https://novacart.exemple/connexion")

    def se_connecter(self, email: str, mot_de_passe: str):
        self.page.get_by_label("E-mail").fill(email)
        self.page.get_by_label("Mot de passe").fill(mot_de_passe)
        self.page.get_by_role("button", name="Se connecter").click()

    def attendre_erreur(self, message: str):
        expect(self.page.get_by_text(message)).to_be_visible()

Le test du module 11 devient plus court, et surtout plus stable :

tests/test_connexion.py — réécrit avec le Page Object

from playwright.sync_api import Page
from pages.login_page import LoginPage


def test_tc_conn_014_mot_de_passe_de_7_caracteres_est_rejete(page: Page):
    connexion = LoginPage(page)
    connexion.goto()
    connexion.se_connecter("test@novacart.fr", "abc1234")
    connexion.attendre_erreur("au moins 8 caractères")

Le gain se voit le jour où le champ change d'identifiant : une seule ligne à corriger, dans login_page.py — tous les tests qui l'utilisent redeviennent verts sans y être touchés.

Partie 3 · Module 19

BDD avec pytest-bdd

Le module 4 a introduit le format Gherkin comme façon lisible d'écrire un critère d'acceptation. pytest-bdd va plus loin : ce même texte devient exécutable, sans le retaper en code — chaque ligne du scénario est reliée à une fonction Python par une "step definition", et ça s'exécute avec le même pytest que le module 11 (contrairement à Cucumber, qui demande son propre runner en JavaScript).

features/connexion.feature

Fonctionnalité : Connexion à NovaCart

  Scénario : Mot de passe trop court refusé
    Étant donné que je suis sur la page de connexion
    Quand je saisis l'e-mail "test@novacart.fr" et le mot de passe "abc1234"
    Alors je vois le message "au moins 8 caractères"

tests/test_connexion_bdd.py

from pytest_bdd import scenarios, given, when, then, parsers
from playwright.sync_api import expect

scenarios("connexion.feature")


@given("que je suis sur la page de connexion")
def aller_sur_la_page_de_connexion(page):
    page.goto("https://novacart.exemple/connexion")


@when(parsers.parse('je saisis l\'e-mail "{email}" et le mot de passe "{mot_de_passe}"'))
def saisir_les_identifiants(page, email, mot_de_passe):
    page.get_by_label("E-mail").fill(email)
    page.get_by_label("Mot de passe").fill(mot_de_passe)
    page.get_by_role("button", name="Se connecter").click()


@then(parsers.parse('je vois le message "{message}"'))
def verifier_le_message(page, message):
    expect(page.get_by_text(message)).to_be_visible()

L'intérêt réel n'est pas technique, il est humain : un Product Owner qui ne lit pas Python peut lire et même corriger le fichier .feature, et vérifier lui-même que le scénario décrit bien la règle métier voulue — les "step definitions" ne changent quasiment jamais une fois écrites, seuls les scénarios en langage naturel bougent au fil des besoins. La fixture page utilisée ici est exactement celle de pytest-playwright, module 11 — les deux outils cohabitent dans le même projet.

Ne pas sur-utiliser

Le BDD ajoute une couche (fichier .feature + steps) qui a un coût de maintenance. S'il n'y a personne côté métier qui lit réellement ces scénarios, les tests Playwright directs du module 11 sont plus simples et tout aussi valables — le BDD est un outil de collaboration, pas une obligation technique.

SQL — vérifier ce qui se passe côté base

Un test comme celui du module 11 vérifie ce que voit l'utilisateur. Mais un bug classique se cache exactement là où personne ne regarde : l'interface affiche "Article ajouté au panier", alors qu'en base la ligne n'a pas été insérée, ou l'a été avec la mauvaise quantité. Sans requête SQL, ce bug est invisible depuis le navigateur.

Vérification manuelle, en base de test

SELECT article_id, quantite
FROM panier
WHERE utilisateur_id = 4471
ORDER BY ajoute_le DESC
LIMIT 1;

On peut aussi faire de cette requête une assertion automatisée, en complément d'un test Playwright — pas à sa place, en plus :

tests/test_panier.py — extrait

import os
import psycopg2
from playwright.sync_api import Page


def test_ajouter_article_cree_bien_une_ligne_en_base(page: Page):
    # ... actions dans l'interface (module 11) ...

    connexion = psycopg2.connect(os.environ["DATABASE_URL_TEST"])
    curseur = connexion.cursor()
    curseur.execute(
        "SELECT quantite FROM panier WHERE utilisateur_id = %s",
        (4471,)

    resultat = curseur.fetchone()

Règle non négociable

Cette connexion pointe vers une base de test, jamais vers la production — un test qui écrit ou lit dans la vraie base de NovaCart est une porte ouverte à la fois vers des données corrompues et, comme le rappelle le module 22, vers une fuite de données personnelles réelles.

Partie 3 · Module 21

Suivre un bug de bout en bout avec Jira

Le gabarit de rapport de bug du module 6 doit vivre quelque part — Jira (ou Trello pour des équipes plus légères) est l'outil le plus répandu pour ça. Ce qui compte n'est pas de connaître tous les boutons de l'interface, mais de comprendre le cycle de vie d'un ticket, parce que le rôle du testeur change à chaque étape.

StatutRôle du testeur
NouveauVient de créer le ticket avec le gabarit du module 6 — titre, sévérité, étapes de reproduction
À trierL'équipe assigne la priorité (module 6 : sévérité ≠ priorité) et une personne
En coursLe développeur corrige — le testeur n'intervient plus, sauf si on lui demande une précision
En revueLe correctif est prêt, généralement associé à une pull request (module 17) dont la CI (module 14) doit être verte
À vérifierLe testeur rejoue le cas de test d'origine — ne jamais fermer un ticket sur la seule parole du développeur
FerméReproduit avant, non reproduit après : seul un testeur qui a vérifié peut clôturer

Une pratique qui se généralise en 2026 : lier le ticket Jira directement à la pull request et au test automatisé qui couvre ce bug (souvent le même ID que le cas de test — TC-CONN-014 pointe vers NOVA-1842) pour qu'on puisse remonter d'un test qui échoue en CI jusqu'au ticket qui explique pourquoi ce cas existe.

Exercice

Voir la correction

Aucun testeur n'a rejoué le cas de test d'origine — le ticket se ferme sur la seule parole du développeur. Le risque : un bug "corrigé" qui ne l'est pas vraiment repart directement en production, sans filet.

Partie 3 · Module 22

RGPD et données de test

Tous les exemples de ce cours utilisent test@novacart.fr — jamais une vraie adresse cliente. Ce n'est pas un détail de style, c'est la règle : copier la base de production dans un environnement de test moins protégé est une des façons les plus courantes de créer une fuite de données personnelles, et une infraction au RGPD dès qu'un environnement de test contient des données réelles de clients européens.

Deux techniques à distinguer

TechniquePrincipeRéversible ?
PseudonymisationRemplacer les données identifiantes par un identifiant technique, avec une table de correspondance gardée à partOui, avec la clé
AnonymisationRemplacer définitivement par des données inventées, sans moyen de remonter à la personne réelleNon — c'est le but

Pour la grande majorité des cas de test (module 5), l'anonymisation totale suffit et évite tout risque : la règle de validation d'un mot de passe se teste aussi bien avec un compte entièrement fictif qu'avec un vrai. Une bibliothèque comme Faker (portée dans la plupart des langages, dont Python) génère en une ligne des jeux de données réalistes mais inventés — noms, adresses, numéros de carte au format valide mais fictif :

fixtures/comptes_test.py

from faker import Faker

fake = Faker("fr_FR")


def generer_compte_test():
    return {
        "email": fake.email(),
        "nom": fake.name(),
        "adresse": fake.address(),
    }
Question à se poser avant d'ouvrir un environnement de test

Si cet environnement était compromis demain, quelles données personnelles réelles seraient exposées ? Si la réponse n'est pas "aucune", il y a un risque de conformité à traiter avant de passer à l'outillage — pas après.

Exercice

Un testeur copie 200 lignes de la table clients de production vers l'environnement de staging pour "avoir des données réalistes". Quel est le problème, et quelle alternative proposer avec les outils de ce module ?

Voir la correction

Le problème : des données personnelles réelles de clients se retrouvent dans un environnement moins protégé — un risque RGPD direct. L'alternative : générer des comptes fictifs mais réalistes avec Faker, comme dans l'exemple du module.

Partie 3 · Module 23

Automatiser le mobile avec Appium

Playwright (module 11) pilote un navigateur. Le jour où NovaCart sort une vraie application mobile native (pas juste son site consulté sur téléphone), Playwright ne peut plus rien faire — il faut Appium, qui parle aux applications iOS et Android installées sur un appareil ou un émulateur.

La logique reste la même que tout ce qu'on a vu : trouver un élément, agir dessus, vérifier un résultat. Seuls les sélecteurs changent — on cible par identifiant d'accessibilité plutôt que par label HTML :

tests/test_connexion_mobile.py (structure simplifiée)

from appium.webdriver.common.appiumby import AppiumBy

champ_email = driver.find_element(AppiumBy.ACCESSIBILITY_ID, "champ-email")
champ_email.send_keys("test@novacart.fr")

champ_mdp = driver.find_element(AppiumBy.ACCESSIBILITY_ID, "champ-mot-de-passe")
champ_mdp.send_keys("MotDePasse2026")

bouton_connexion = driver.find_element(AppiumBy.ACCESSIBILITY_ID, "bouton-se-connecter")

Ces identifiants (~champ-email) doivent être ajoutés par les développeurs mobile dans le code de l'application — contrairement au web, on ne peut pas s'appuyer sur du texte visible aussi facilement. C'est une conversation à avoir tôt avec l'équipe mobile, pas une contrainte que le testeur découvre après coup.

Exercice

L'application mobile NovaCart n'a aucun identifiant d'accessibilité sur son bouton de connexion. Qui doit l'ajouter, et pourquoi le testeur ne peut-il pas simplement "trouver le bouton" comme il le ferait sur le web ?

Voir la correction

Les développeurs mobile doivent l'ajouter dans le code de l'application. Contrairement au web, il n'y a pas de texte ou de DOM aussi facilement exploitable — sans identifiant explicite, Appium n'a rien de fiable à cibler.

Partie 3 · Module 24

Sécurité applicative avec OWASP ZAP

Le module 3 citait la sécurité comme famille de test non-fonctionnelle, sans outil. OWASP ZAP (Zed Attack Proxy) comble ce vide : c'est un scanner gratuit qui se place entre le navigateur et NovaCart, observe le trafic, puis envoie automatiquement des variantes suspectes des requêtes pour chercher les failles les plus courantes — celles listées dans l'OWASP Top 10, la référence du secteur (injection, authentification cassée, en-têtes de sécurité manquants…).

Terminal — scan automatisé en ligne de commande

docker run -t zaproxy/zap-stable zap-baseline.py \
  -t https://staging.novacart.exemple \
  -r rapport-zap.html

Sur NovaCart, un scan de base sur /connexion repère par exemple l'absence d'en-tête Content-Security-Policy, ou une page qui accepte une entrée non échappée dans le champ de recherche — des signaux à faire vérifier par un développeur, pas nécessairement des failles confirmées.

Ce que ZAP ne fait pas

Un scan automatique trouve des vulnérabilités techniques génériques. Il ne trouve pas les failles de logique métier — par exemple, un utilisateur qui accède au panier d'un autre en changeant simplement l'identifiant dans l'URL. Ce genre de cas se teste manuellement, avec les techniques du module 5 appliquées à un objectif malveillant plutôt que fonctionnel.

Exercice

Un scan OWASP ZAP ne remonte aucune faille sur /panier, mais un testeur découvre manuellement qu'en changeant l'identifiant dans l'URL il voit le panier d'un autre client. Pourquoi ZAP n'a-t-il rien trouvé ?

Voir la correction

C'est une faille de logique métier (autorisation), pas une vulnérabilité technique générique — exactement ce que ce module signale comme hors du périmètre d'un scanner automatique. Ce genre de cas se teste manuellement.

Partie 3 · Module 25

Environnements reproductibles avec Docker

"Ça passe sur ma machine mais pas en CI" est un symptôme classique : une version de Node différente, une police système absente, une dépendance installée à la main un jour et oubliée. Docker élimine cette classe entière de problèmes en empaquetant exactement le même environnement, partout.

Dockerfile — pour exécuter les tests Playwright du module 11

FROM mcr.microsoft.com/playwright/python:v1.48.0-jammy

WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .

CMD ["pytest", "--browser", "chromium"]

La même image tourne en local (docker build -t novacart-tests . && docker run novacart-tests) et dans le pipeline GitHub Actions du module 14 — plus de surprise entre "chez moi" et "en CI", parce que c'est littéralement le même système de fichiers qui exécute les tests dans les deux cas.

Une fois cette reproductibilité acquise, la question de l'échelle se pose naturellement : faire tourner les tests de charge du module 13 depuis une seule machine locale limite le nombre d'utilisateurs virtuels simulables de façon réaliste. Des VM cloud (AWS, Azure) permettent de lancer ces mêmes conteneurs depuis plusieurs régions à la fois — un sujet d'infrastructure à part entière, qui dépasse ce cours, mais qui repose entièrement sur la reproductibilité que Docker apporte ici.

Exercice

Un test passe en local mais échoue en CI avec une erreur liée à une version de navigateur différente. En quoi Docker empêche-t-il ce problème de se reproduire ?

Voir la correction

La même image tourne en local et en CI — donc littéralement la même version de navigateur et les mêmes dépendances dans les deux cas. Il ne peut plus y avoir de divergence d'environnement à l'origine du problème.

La certification qui pèse le plus : ISTQB Foundation Level
