Introduction

Pourquoi ce rappel, même pour un testeur

Tu ne vas pas devenir développeur front-end — mais HTML et CSS te servent tous les jours en tant que testeur QA, même sans les écrire :

  • Lire le DOM pour écrire un sélecteur Playwright fiable (button.submit-btn, [data-testid="login"]) plutôt qu'un sélecteur fragile.
  • Rédiger un bug report précis : « le bouton a un padding incohérent » est plus utile pour un dev que « c'est moche ».
  • Comprendre le responsive pour savoir pourquoi un test passe sur desktop mais casse sur mobile.
  • Construire ton propre portfolio — la page qui présente ton projet livret-mission et ta candidature QA aux recruteurs.
Ce cours suppose que tu as déjà vu HTML/CSS une fois (même vaguement). On ne repart pas de zéro : on consolide, avec la pratique.
Partie 1 / 3

Les bases HTML

La structure et le contenu d'une page.

Module 1

Structure d'une page HTML

Une page HTML a toujours le même squelette : <!doctype html> indique la version, <head> contient les métadonnées (titre, encodage, liens CSS), <body> contient ce qui s'affiche.

<!doctype html>
<html lang="fr">
  <head>
    <meta charset="utf-8">
    <title>Ma page</title>
  </head>
  <body>
    <h1>Bonjour</h1>
  </body>
</html>

Les balises sémantiques

Plutôt que d'empiler des <div> partout, HTML5 propose des balises qui décrivent le rôle du contenu : <header>, <nav>, <main>, <section>, <article>, <footer>. C'est important pour l'accessibilité (lecteurs d'écran) et pour le SEO — et ça rend tes sélecteurs de test plus lisibles.

Module 2

Texte, liens et images

Les balises de texte les plus courantes : <p>, <h1>…<h6>, <strong> (important), <em> (emphase). Un lien : <a href="...">. Une image : <img src="..." alt="...">.

L'attribut alt n'est pas optionnel. Il décrit l'image pour les lecteurs d'écran et s'affiche si l'image ne charge pas. En test, une image sans alt est un vrai bug d'accessibilité à signaler.

Module 3

Listes, tableaux et formulaires

Listes : <ul> (à puces) ou <ol> (numérotée), avec des <li> à l'intérieur. Tableaux : <table>, <tr> (ligne), <th> (en-tête), <td> (cellule).

Les formulaires — essentiels en test

Un formulaire est probablement la chose que tu testeras le plus souvent : champs, validations, soumission. Chaque champ mérite un <label> lié par for/id — sans ça, un lecteur d'écran (et parfois un sélecteur de test) ne sait pas à quoi correspond le champ.

<form>
  <label for="email">Email</label>
  <input type="email" id="email" name="email" required>
  <button type="submit">Envoyer</button>
</form>

Module 4

Sélecteurs et cascade

CSS applique des styles via des sélecteurs : p (toutes les balises p), .carte (classe), #titre (id unique). Quand plusieurs règles s'appliquent au même élément, la plus spécifique gagne — d'où le nom « cascade ».

Ordre de spécificité (du plus faible au plus fort) : élément → classe → id → style inline. En pratique, privilégie les classes : elles sont réutilisables et faciles à cibler en test.

Module 5

Le box model

Chaque élément HTML est une boîte : content (le contenu), padding (l'espace intérieur), border (la bordure), margin (l'espace extérieur). Ajoute box-sizing: border-box pour que width inclue le padding et la bordure — sinon les tailles deviennent vite imprévisibles.

CSS
Exercice — retire box-sizing: border-box

Supprime la ligne *{ box-sizing:border-box; } et relance. Observe : la boîte devient plus large que 200px, car le padding et la bordure s'ajoutent désormais à la largeur. C'est exactement le genre de détail qu'un testeur repère en comparant une maquette au rendu réel.

Module 6

Flexbox

Flexbox est l'outil principal pour aligner des éléments sur une ligne ou une colonne. display:flex sur un parent active flexbox pour ses enfants directs. justify-content gère l'axe principal (horizontal par défaut), align-items l'axe secondaire, gap l'espacement entre éléments.

Exercice — passe en colonne

Ajoute flex-direction: column; à .barre et change justify-content en flex-start. Observe comment les cartes s'empilent verticalement au lieu de s'aligner horizontalement.

Module 7

Responsive & media queries

Une @media query applique des styles seulement si une condition est vraie (le plus souvent, une largeur d'écran). L'approche recommandée est mobile-first : on écrit les styles de base pour mobile, puis on ajoute des règles pour les écrans plus larges avec min-width.

.grille{ display:grid; grid-template-columns:1fr; }

@media (min-width: 640px) {
  .grille{ grid-template-columns:1fr 1fr; }
}
Redimensionne la fenêtre de l'aperçu ci-dessous (ou regarde-la sur ton téléphone) pour voir la mise en page changer selon la largeur.

Pour aller plus loin (pas indispensable pour débuter) : les container queries (@container) adaptent un composant à la taille de son conteneur plutôt qu'à l'écran entier, le nesting CSS natif permet d'imbriquer des règles comme en Sass, et :has() permet de styler un parent selon ses enfants. Ce sont des standards modernes largement supportés en 2026, bons à connaître pour ne pas être surpris en lisant du code récent.
Bonus · Module 7 bis

Le design system

Un design system est un ensemble cohérent de règles et de composants réutilisables — couleurs, typographies, espacements, boutons, cartes, états (survol, focus, désactivé, erreur) — que design et développement partagent pour garder une interface cohérente sur tout un produit. Techniquement, il repose souvent sur des design tokens : des valeurs nommées (une couleur, un espacement) définies une seule fois et réutilisées partout, au lieu d'être copiées-collées dans chaque composant.

Tu en utilises déjà un sans le savoir : regarde le haut du CSS de cette page — --bg, --accent, --border… ce sont des design tokens sous forme de variables CSS. Chaque bouton, chaque carte de ce cours les réutilise plutôt que de redéfinir ses propres couleurs. C'est un mini design system.

Pourquoi ça concerne un testeur

Tu ne construis pas le design system, mais tu vérifies qu'il est bien respecté :

  • Deux boutons "primaires" sur deux pages différentes ont-ils exactement la même couleur, le même arrondi, le même espacement ?
  • Un composant a-t-il bien tous ses états prévus — hover, focus, disabled, erreur — ou seulement l'état par défaut ?
  • Le contraste texte/fond reste-t-il suffisant dans chaque état, y compris en thème sombre ?
  • Un changement de token (par exemple la couleur de marque) se répercute-t-il bien partout, sans qu'un composant isolé garde l'ancienne couleur en dur ?
HTML
CSS
Exercice — change un seul token

Change uniquement la valeur de --token-couleur (par exemple en #1E5A96) et relance. Observe : le bouton primaire, la bordure du bouton secondaire et la carte changent tous ensemble, parce qu'ils pointent vers le même token. C'est exactement ce que tu vérifierais en test : si un seul de ces trois éléments n'avait pas bougé, ce serait un bug de cohérence avec le design system — un cas fréquent en test visuel.

Module 8

Cahier des charges du projet

Le projet : une page de présentation personnelle — une seule page HTML/CSS que tu pourras publier et mettre en lien dans tes candidatures. Elle montre à un recruteur que tu sais construire une page propre, structurée et responsive — utile pour un profil QA qui doit comprendre ce qu'il teste.

User stories

  • En tant que visiteur, je vois immédiatement qui tu es et ce que tu vises (reconversion QA) en haut de page.
  • En tant que visiteur, je peux lire une courte présentation de ton parcours.
  • En tant que visiteur, je vois tes compétences clés (Python, Playwright, SQL, Git…) présentées clairement.
  • En tant que visiteur, je peux voir ton projet phare (le livret de mission) avec un lien vers son code.
  • En tant que visiteur, je peux te contacter (email ou LinkedIn) facilement.
  • En tant que visiteur sur mobile, la page reste lisible et bien mise en page.
C'est la même logique de user stories que dans le cours Agile & Scrum — la « Definition of Done » ici, c'est : structure sémantique correcte, aucun alt manquant, responsive testé, liens fonctionnels.

Module 10

Finitions et publication

Avant de publier, une petite checklist qualité — le réflexe testeur appliqué à ton propre travail :

  • Tous les <img> ont un alt pertinent.
  • Les liens (href="#") pointent vers de vraies adresses (GitHub, LinkedIn, mailto:).
  • La page reste lisible à 375px de large (mobile) et à 1440px (desktop).
  • Un seul <h1> par page ; la hiérarchie h1 → h2 → h3 est respectée.
  • Le contraste texte/fond est suffisant (texte blanc sur orange foncé : ok ; texte gris clair sur blanc : à éviter).

Publier la page

Le plus simple : reprends le fichier HTML final, crée un dépôt GitHub (comme vu dans le cours GitHub pour la QA), puis active GitHub Pages dans les paramètres du dépôt (Settings → Pages → Deploy from branch). Ta page devient accessible via une URL publique en quelques minutes — c'est ce lien que tu mets dans tes candidatures et sur ton CV.

Projet livrable : une page HTML/CSS complète, responsive, publiée sur GitHub Pages, avec ton vrai profil et un lien vers ton projet livret-mission. C'est un deuxième élément de portfolio, complémentaire à l'application JavaScript du cours JS Moderne.
