PARTIE 1

Au-delà de REST

Deux modules pour comprendre pourquoi REST, malgré sa domination, ne suffit plus partout — et où GraphQL et gRPC prennent le relais.

Partie 1 · Module 01

Les limites de REST

REST reste, de loin, le style d'API le plus répandu — et rien dans ce cours ne remet ça en cause. Mais deux limites concrètes ont poussé certaines équipes vers d'autres approches, et un testeur doit savoir les reconnaître.

Over-fetching et under-fetching

Sur NovaCart, l'endpoint REST GET /articles/42 renvoie tout l'objet article — nom, prix, stock, description, dimensions — même si l'écran mobile n'a besoin que du nom et du prix. C'est de l'over-fetching : plus de données transférées que nécessaire. À l'inverse, afficher une commande avec le nom de chaque article demande souvent plusieurs appels successifs (la commande, puis chaque article un par un) — c'est de l'under-fetching, qui multiplie les allers-retours réseau.

Le problème du contrat entre microservices

Quand des dizaines de microservices communiquent entre eux en interne (pas exposés aux utilisateurs finaux), la flexibilité de REST devient parfois un défaut : sans schéma strict, une légère divergence entre ce qu'un service envoie et ce qu'un autre attend passe facilement inaperçue jusqu'en production. C'est exactement le problème que gRPC (partie 3) a été conçu pour résoudre.

Exercice

La page de liste des commandes NovaCart n'affiche que le numéro de commande et son statut, mais l'API REST actuelle renvoie l'objet commande complet (client, articles, adresses, montants). De quel problème s'agit-il, et quelle famille d'API le résout structurellement ?

Voir la correction

C'est de l'over-fetching — bien plus de données que nécessaire sont transférées pour cet écran. GraphQL (partie 2) résout structurellement ce problème : le client précise exactement les champs qu'il veut, rien de plus.

Partie 1 · Module 02

Panorama des protocoles en 2026

Les trois familles coexistent — le choix dépend du contexte, pas d'une mode. En 2026, REST reste dominant pour les API publiques, GraphQL s'est stabilisé sur les applications avec des interfaces riches et changeantes (mobile, dashboards), et gRPC s'est généralisé dans les communications internes entre microservices, notamment quand la performance et la validation stricte comptent.

RESTGraphQLgRPC

Lisible dans un navigateur ?OuiOui (via un client dédié)Non, nécessite un outil dédié

Pour toi en tant que testeur, la bonne nouvelle : les principes de fond du test d'API — vérifier les cas nominaux, les cas d'erreur, les valeurs limites, l'authentification — restent identiques d'un protocole à l'autre. Ce qui change, ce sont les outils et la façon de formuler la requête, pas la logique de test elle-même.

Exercice

Une équipe construit une application mobile NovaCart où chaque écran affiche des combinaisons différentes de données (parfois juste le prix, parfois toute la fiche produit). Quel protocole conviendrait le mieux, et pourquoi ?

Voir la correction

GraphQL — sa capacité à laisser chaque écran demander exactement les champs dont il a besoin correspond précisément à ce besoin de combinaisons variées, sans multiplier les endpoints REST spécifiques à chaque écran.

PARTIE 2

GraphQL

Quatre modules pour comprendre et tester une API GraphQL — le protocole le plus susceptible d'apparaître rapidement dans une offre d'emploi QA en 2026.

Partie 2 · Module 03

Les bases : schéma, queries, mutations

Une API GraphQL expose un schéma unique et fortement typé, qui décrit précisément toutes les données disponibles et leurs relations — un vrai contrat, contrairement à une API REST où la structure exacte des réponses n'est documentée qu'à part (Swagger/OpenAPI, souvent).

Extrait du schéma NovaCart (langage SDL de GraphQL)

type Article {
  id: ID!
  nom: String!
  prix: Float!
  stock: Int!
}

type Query {
  article(id: ID!): Article
  articles(stockMin: Int): [Article!]!
}

type Mutation {
  ajouterAuPanier(articleId: ID!, quantite: Int!): Panier!
}

Le ! signifie "non-nullable" — le schéma garantit qu'un champ marqué ainsi ne sera jamais absent. Deux opérations principales : une query lit des données (l'équivalent d'un GET), une mutation en modifie (l'équivalent d'un POST/PUT/DELETE). Une troisième existe, la subscription, pour recevoir des mises à jour en temps réel — moins fréquente, on ne s'y attarde pas ici.

Exercice

Dans le schéma ci-dessus, la mutation ajouterAuPanier peut-elle être appelée sans préciser de quantité ? Justifie à partir du schéma.

Voir la correction

Non. quantite: Int! — le ! rend ce paramètre obligatoire. Une requête qui omet quantite sera rejetée par le serveur GraphQL avant même d'atteindre la logique métier, avec une erreur de validation de schéma.

Partie 2 · Module 04

Interroger une API GraphQL

Toutes les requêtes GraphQL passent par un seul endpoint (souvent /graphql), en POST, quel que soit le type d'opération — une différence fondamentale avec REST où chaque ressource a sa propre URL.

Une query qui ne demande que ce dont on a besoin

query {
  article(id: "42") {
    nom
    prix
  }
}

Envoyée en Python avec requests

import requests

query = """
query {
  article(id: "42") {
    nom
    prix
  }
}
"""

response = requests.post(
    "https://api.novacart.fr/graphql",
    json={"query": query}
)
data = response.json()["data"]["article"]
assert data["nom"] == "Casque audio"

Remarque la structure de la réponse : les données utiles sont toujours nichées sous une clé "data", elle-même sous une clé correspondant au nom du champ demandé (article) — une convention fixe, quel que soit le schéma.

Exercice

Écris la query GraphQL qui récupère le nom et le stock de tous les articles ayant un stock supérieur à 10 (en te basant sur le schéma du module 3).

Voir la correction 
query {
  articles(stockMin: 11) {
    nom
    stock
  }
}
Partie 2 · Module 05

Tester une API GraphQL

Le piège n°1 pour un testeur habitué à REST : en GraphQL, le code de statut HTTP est presque toujours 200, même en cas d'erreur métier ou de validation. Vérifier uniquement response.status_code == 200 ne prouve donc absolument rien — il faut inspecter le corps de la réponse.

Une requête invalide reste en HTTP 200

{
  "errors": [
    {
      "message": "Article introuvable",
      "path": ["article"]
    }
  ],
  "data": {
    "article": null
  }
}
response = requests.post(url, json={"query": query})
assert response.status_code == 200          # presque toujours vrai, n'apporte rien
body = response.json()
assert "errors" not in body, body.get("errors")   # le vrai test
assert body["data"]["article"] is not None

L'introspection

GraphQL permet d'interroger le schéma lui-même via une requête spéciale (__schema) — très utile pour un testeur qui découvre une API : au lieu de chercher une documentation externe parfois obsolète, on demande directement à l'API de décrire tous ses types et champs disponibles. Des outils comme Postman ou GraphiQL exploitent cette introspection pour offrir de l'auto-complétion.

Point de vigilance sécurité

L'introspection, pratique en développement, expose la structure complète de l'API — y compris des champs qui ne devraient pas être visibles publiquement. En production, elle est généralement désactivée ; vérifier qu'elle l'est bien fait partie d'une checklist de sécurité API basique.

Exercice

Un test vérifie uniquement assert response.status_code == 200 sur un appel GraphQL. Explique pourquoi ce test peut passer au vert alors que la requête a en réalité échoué, et corrige-le.

Voir la correction

En GraphQL, une erreur métier ou de validation renvoie généralement quand même un HTTP 200, avec le détail de l'erreur dans une clé "errors" du corps JSON. Le test doit inspecter ce corps : assert "errors" not in response.json(), en plus (ou à la place) de la vérification du code HTTP.

Partie 2 · Module 06

Cas limites pour un testeur

Trois pièges spécifiques à GraphQL qu'un testeur expérimenté sait chercher, au-delà du fonctionnement nominal.

Le problème N+1

Une query qui demande une liste de commandes, et pour chacune le nom du client, peut déclencher — côté serveur, invisible pour toi en tant que consommateur de l'API — une requête base de données par commande en plus de la requête initiale. Sur 100 commandes, ça fait 101 requêtes SQL au lieu d'une jointure bien pensée. En tant que testeur, ce n'est pas à toi de corriger ce problème technique, mais un test de performance ciblé sur une requête GraphQL imbriquée (nested query) permet souvent de le détecter avant qu'il ne devienne critique en production.

Les autorisations au niveau du champ

Contrairement à REST où un endpoint entier est protégé ou non, GraphQL permet une autorisation beaucoup plus fine : un utilisateur peut avoir le droit de voir article.nom mais pas article.margeInterne, dans la même requête. Un testeur doit donc vérifier les autorisations champ par champ, pas seulement au niveau de l'opération globale — une requête utilisateur standard qui demanderait un champ réservé aux admins doit échouer proprement sur ce champ précis, sans faire échouer toute la requête si d'autres champs demandés sont légitimes.

La profondeur des requêtes (query depth)

Rien n'empêche, en théorie, une query GraphQL malicieuse d'imbriquer des relations sur une profondeur énorme (commandes → client → autres commandes → autres clients → ...) pour surcharger le serveur. Une bonne API limite cette profondeur — un test de sécurité API consiste justement à vérifier qu'une requête excessivement profonde est bien rejetée plutôt qu'exécutée.

Exercice

Un utilisateur standard envoie une query demandant à la fois article.nom (public) et article.margeInterne (réservé aux admins). Quel comportement attends-tu d'une API GraphQL bien conçue ?

Voir la correction

La réponse doit contenir nom normalement dans data, et une entrée dans errors spécifique au champ margeInterne (accès refusé), sans faire échouer toute la requête. C'est l'autorisation au niveau du champ, une spécificité à tester en GraphQL qui n'a pas d'équivalent direct en REST.

PARTIE 3

gRPC

Trois modules pour un protocole moins visible côté utilisateur final, mais omniprésent dans les architectures en microservices — et donc régulièrement présent en entretien technique dès qu'une entreprise a une architecture un peu avancée.

Partie 3 · Module 07

Les bases : protobuf et HTTP/2

gRPC (Google Remote Procedure Call) définit ses contrats dans des fichiers .proto, en Protocol Buffers — un format binaire compact, plus rapide à transmettre et à parser qu'un JSON texte, mais illisible sans outil dédié.

Extrait d'un fichier catalogue.proto pour NovaCart

service NovaCartService {
  rpc ObtenirArticle (ArticleRequest) returns (Article);
  rpc ListerArticles (ListeRequest) returns (stream Article);
}

message ArticleRequest {
  string id = 1;
}

message Article {
  string id = 1;
  string nom = 2;
  float prix = 3;
  int32 stock = 4;
}

À partir de ce fichier .proto, un outil (protoc) génère automatiquement le code client et serveur dans le langage voulu (Python inclus) — c'est ce contrat strict et généré qui élimine la classe entière de bugs "le client envoie un champ que le serveur n'attend pas".

Quatre types d'appels

TypePrincipe
UnaryUne requête, une réponse — l'équivalent classique d'un appel REST
Server streamingUne requête, un flux de réponses successives
Client streamingUn flux de requêtes, une réponse finale
BidirectionnelFlux dans les deux sens, en parallèle
Exercice

Dans le fichier .proto ci-dessus, quel appel serait le plus adapté pour lister progressivement 10 000 articles sans tout charger en mémoire d'un coup ?

Voir la correction

ListerArticles, déjà défini avec stream Article — un server streaming : une seule requête envoyée, puis les articles arrivent progressivement au fil de l'eau plutôt que dans une seule réponse massive.

Partie 3 · Module 08

Outils pour tester une API gRPC

Un navigateur ou un simple curl ne suffisent pas pour du gRPC — le format binaire et HTTP/2 demandent des outils dédiés.

OutilUsage
grpcurlL'équivalent de curl pour gRPC, en ligne de commande — le plus simple pour explorer rapidement un service
PostmanSupporte gRPC nativement depuis plusieurs années — pratique si tu es déjà à l'aise avec son interface pour REST
grpcio (Python)La librairie officielle pour écrire des clients/tests gRPC directement en Python

Explorer un service avec grpcurl

grpcurl -plaintext localhost:50051 list
grpcurl -plaintext -d '{"id": "42"}' \
  localhost:50051 catalogue.NovaCartService/ObtenirArticle

Sans réflexion serveur activée (grpc reflection), grpcurl a besoin du fichier .proto en local pour connaître la structure du service — un détail à vérifier avant de se lancer.

Exercice

Pourquoi curl seul ne peut-il pas tester efficacement un service gRPC, contrairement à une API REST ?

Voir la correction

gRPC encode ses messages en Protocol Buffers, un format binaire, sur HTTP/2 — curl est conçu pour du texte lisible sur HTTP/1.1 classique. Il faut un outil qui comprend le format protobuf et sait sérialiser/désérialiser les messages selon le contrat .proto, comme grpcurl.

Partie 3 · Module 09

Écrire un test gRPC en Python

Une fois le code généré à partir du fichier .proto (via protoc), écrire un test gRPC en Python ressemble beaucoup à un test d'API classique — la différence se joue surtout dans la préparation du canal de communication.

import grpc
import pytest
import catalogue_pb2
import catalogue_pb2_grpc

@pytest.fixture
def stub():
    channel = grpc.insecure_channel("localhost:50051")
    return catalogue_pb2_grpc.NovaCartServiceStub(channel)

def test_obtenir_article_existant(stub):
    requete = catalogue_pb2.ArticleRequest(id="42")
    reponse = stub.ObtenirArticle(requete)
    assert reponse.nom == "Casque audio"
    assert reponse.prix > 0

def test_article_introuvable_leve_une_erreur(stub):
    requete = catalogue_pb2.ArticleRequest(id="id-inexistant")
    with pytest.raises(grpc.RpcError) as exc_info:
        stub.ObtenirArticle(requete)
    assert exc_info.value.code() == grpc.StatusCode.NOT_FOUND

Remarque la gestion des erreurs : gRPC a son propre jeu de codes de statut (NOT_FOUND, INVALID_ARGUMENT, UNAUTHENTICATED...), l'équivalent des codes HTTP en REST mais spécifique au protocole — à connaître pour écrire des assertions précises plutôt que de se contenter d'attraper une exception générique.

Exercice

Écris un test qui vérifie qu'appeler ObtenirArticle sans fournir d'id (chaîne vide) lève une erreur gRPC de type INVALID_ARGUMENT.

Voir la correction 
def test_id_vide_leve_invalid_argument(stub):
    requete = catalogue_pb2.ArticleRequest(id="")
    with pytest.raises(grpc.RpcError) as exc_info:
        stub.ObtenirArticle(requete)
    assert exc_info.value.code() == grpc.StatusCode.INVALID_ARGUMENT
PARTIE 4

Contrats, mocks, sécurité

Trois modules transversaux, valables quel que soit le protocole — ce qui distingue un testeur API rigoureux d'un testeur qui teste "au cas par cas".

Partie 4 · Module 10

REST Assured et son équivalent Python

REST Assured est une librairie Java extrêmement répandue pour tester des API REST avec une syntaxe fluide et lisible — tu la verras citée dans énormément d'offres d'emploi QA, même si tu travailles en Python. Il est utile de savoir la reconnaître, sans avoir besoin de l'apprendre en profondeur.

À quoi ressemble REST Assured (Java) — pour la reconnaître, pas pour l'écrire

given()
    .header("Content-Type", "application/json")
.when()
    .get("/articles/42")
.then()
    .statusCode(200)
    .body("nom", equalTo("Casque audio"));

L'équivalent en Python, avec requests et pytest, exprime exactement la même logique — donner/quand/vérifier — avec une syntaxe différente :

response = requests.get(f"{BASE_URL}/articles/42")
assert response.status_code == 200
assert response.json()["nom"] == "Casque audio"

Le test de contrat (contract testing)

Au-delà de vérifier une réponse précise, le test de contrat vérifie que la structure d'une réponse respecte un schéma défini — utile pour détecter automatiquement qu'un champ a disparu ou changé de type, même sans connaître à l'avance la valeur exacte attendue. En Python, la librairie schemathesis génère automatiquement des tests à partir d'une spécification OpenAPI/Swagger existante :

import schemathesis

schema = schemathesis.from_uri("https://api.novacart.fr/openapi.json")

@schema.parametrize()
def test_respecte_le_contrat(case):
    case.call_and_validate()

Cette seule fonction génère et exécute automatiquement des dizaines de cas de test, dérivés directement de la spécification OpenAPI — un gain de temps considérable comparé à écrire chaque cas à la main, particulièrement adapté pour vérifier qu'une API respecte son propre contrat après chaque déploiement.

Exercice

Une offre d'emploi mentionne "expérience avec REST Assured" mais tu ne connais que Python. Comment présenter honnêtement cette compétence en entretien ?

Voir la correction

Expliquer que la logique de test (given/when/then, vérification du statut et du corps de la réponse) est la même quel que soit l'outil, que tu la pratiques en Python avec requests/pytest, et que la syntaxe Java de REST Assured se lirait sans difficulté majeure — sans prétendre l'avoir pratiquée si ce n'est pas le cas. C'est exactement l'esprit du module 27 du cours QA : ne jamais bluffer sur une compétence non maîtrisée.

Partie 4 · Module 11

Mocker une API

Un mock d'API simule les réponses d'un vrai service, sans l'appeler réellement — utile quand le vrai service n'existe pas encore, est instable, coûte de l'argent à chaque appel (une API de paiement tierce, par exemple), ou quand on veut forcer un scénario d'erreur précis, difficile à provoquer sur le vrai système.

OutilPrincipe
WireMockServeur de mock configurable par règles (stubs), très utilisé en Java mais utilisable depuis n'importe quel langage via HTTP
PrismGénère un serveur de mock directement à partir d'une spécification OpenAPI existante
responses / pytest-httpserver (Python)Mock léger directement dans le code de test Python, sans serveur externe à lancer

Mocker l'API de paiement tierce avec la librairie responses

import responses
import requests

@responses.activate
def test_paiement_refuse_est_gere_correctement():
    responses.add(
        responses.POST,
        "https://paiement-externe.fr/api/charge",
        json={"status": "refused", "reason": "carte expirée"},
        status=402,
    )
    reponse = requests.post("https://paiement-externe.fr/api/charge", json={})
    assert reponse.status_code == 402
    assert reponse.json()["reason"] == "carte expirée"

Ce test vérifie que le code NovaCart gère bien un refus de paiement — sans jamais appeler la vraie API tierce, sans dépendre de sa disponibilité, et de façon totalement reproductible à chaque exécution.

Exercice

Pourquoi est-il risqué de tester le cas "l'API de paiement externe est indisponible" uniquement contre le vrai service tiers, plutôt qu'avec un mock ?

Voir la correction

On ne peut généralement pas provoquer une vraie panne d'un service tiers à volonté — le test serait au mieux non reproductible, au pire impossible à exécuter. Un mock permet de simuler cette panne de façon déterministe, à chaque exécution, sans dépendre de la disponibilité réelle du tiers ni risquer un vrai paiement de test.

Partie 4 · Module 12

Tester l'authentification OAuth2/JWT

La quasi-totalité des API professionnelles protègent leurs endpoints avec un jeton — un testeur doit savoir vérifier non seulement le cas nominal (jeton valide), mais surtout les cas d'échec, souvent négligés en développement.

JWT, en bref

Un JWT (JSON Web Token) est une chaîne encodée en trois parties (en-tête, données, signature) qui prouve l'identité et les droits d'un utilisateur, sans que le serveur ait besoin de vérifier une session en base à chaque requête — la signature suffit à garantir que le jeton n'a pas été altéré.

Cas à tester systématiquement sur un endpoint protégé

CasRésultat attendu
Aucun jeton fourni401 Unauthorized
Jeton expiré401 Unauthorized, message explicite
Jeton malformé (signature invalide)401 Unauthorized
Jeton valide, mais droits insuffisants (scope manquant)403 Forbidden
Jeton valide, droits suffisants200 OK, accès accordé
def test_endpoint_protege_sans_jeton_renvoie_401():
    response = requests.get(f"{BASE_URL}/commandes/mine")
    assert response.status_code == 401

def test_endpoint_protege_avec_jeton_expire_renvoie_401(jeton_expire):
    headers = {"Authorization": f"Bearer {jeton_expire}"}
    response = requests.get(f"{BASE_URL}/commandes/mine", headers=headers)
    assert response.status_code == 401
Distinction à ne pas confondre

401 Unauthorized signifie "je ne sais pas qui tu es" (pas de jeton, ou jeton invalide) ; 403 Forbidden signifie "je sais qui tu es, mais tu n'as pas le droit" (jeton valide, mais scope ou rôle insuffisant). Une API qui renvoie 401 au lieu de 403 (ou l'inverse) a un bug d'autorisation qu'un testeur doit repérer et signaler précisément.

Exercice

Un endpoint DELETE /articles/42 réservé aux administrateurs renvoie 401 quand un utilisateur normal, correctement authentifié, tente d'y accéder. Ce comportement est-il correct ?

Voir la correction

Non. L'utilisateur est authentifié (le serveur sait qui il est) mais n'a pas les droits suffisants — la réponse correcte est 403 Forbidden, pas 401. Renvoyer 401 ici est un bug d'autorisation à signaler.

Partie 5 · Module 13

L'API testing sur le marché en 2026

Le test d'API REST (Postman, requests) reste, de très loin, la compétence attendue en priorité — c'est ce que couvre déjà le cours QA, et c'est suffisant pour la grande majorité des postes juniors. GraphQL et gRPC, en revanche, fonctionnent comme des signaux de différenciation : peu de candidats juniors les mentionnent, ce qui les rend disproportionnellement remarqués sur un CV, même sans expérience professionnelle dessus.

Niveau attendu d'un juniorCe qui te distingue
Tester une API REST avec PostmanSavoir expliquer la différence de test entre REST et GraphQL (statut HTTP toujours 200)
Vérifier un code de statut HTTPDistinguer précisément 401 et 403, et savoir pourquoi ça compte
Avoir déjà entendu "microservices"Savoir ce qu'est gRPC et pourquoi on l'utilise en interne plutôt que REST
Écrire un test d'API au cas par casConnaître le principe du test de contrat (schemathesis, OpenAPI) pour générer des tests automatiquement
Pour l'entretien

Tu n'as pas besoin d'avoir travaillé en entreprise sur GraphQL ou gRPC pour en parler intelligemment : explique que tu connais les principes et les pièges spécifiques à chaque protocole (statut HTTP GraphQL, contrat strict gRPC), que tu saurais rapidement devenir opérationnel dessus vu la proximité avec ce que tu pratiques déjà en REST — une réponse honnête et solide, dans l'esprit du module 27 du cours QA.

Exercice

En entretien, on te demande : "Avez-vous déjà testé du GraphQL ?" Tu ne l'as pratiqué que dans ce cours, jamais en entreprise. Prépare une réponse honnête et valorisante.
