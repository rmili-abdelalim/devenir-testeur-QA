PARTIE 1

Interroger une base

Sept modules pour lire une base de données couramment — poser une question et obtenir la bonne réponse, sans détour.

Partie 1 · Module 01

Ce qu'est une base relationnelle

Une base de données relationnelle range l'information dans des tables — comme des feuilles de tableur, mais reliées entre elles plutôt qu'isolées. Chaque table a des colonnes (les champs : email, prix, date...) et des lignes (les enregistrements : un utilisateur, un article, une commande).

Ce qui distingue une vraie base de données d'un simple tableur, c'est la capacité à relier les tables entre elles sans dupliquer l'information. Sur NovaCart, une commande n'a pas besoin de recopier l'e-mail du client : elle stocke juste son id dans la colonne utilisateur_id, et on va chercher le reste dans la table utilisateurs au moment de la requête (module 6, les jointures).

Le vocabulaire de base

TermeCe que c'estExemple NovaCart
TableUne collection d'enregistrements de même structurearticles
ColonneUn champ, avec un type de donnée fixeprix (nombre)
LigneUn enregistrement précisL'article "Casque audio"
Clé primaireLa colonne qui identifie chaque ligne de façon uniquearticles.id
Clé étrangèreUne colonne qui pointe vers la clé primaire d'une autre tablecommandes.utilisateur_id

Le langage qu'on utilise pour parler à ce type de base s'appelle SQL (Structured Query Language) — le même vocabulaire, à quelques détails près, fonctionne sur PostgreSQL, MySQL, SQL Server ou SQLite. C'est justement ce qui rend le SQL rentable à apprendre une fois : le module 17 reviendra sur ces différences, mais elles sont mineures comparées à ce qui est commun partout.

Exercice

Dans le schéma NovaCart en haut de page, quelle table utiliserais-tu pour savoir combien d'unités d'un article donné sont encore disponibles à la vente ?

Voir la correction

La table articles, colonne stock — c'est elle qui porte cette information, pas lignes_commande qui ne fait que retracer ce qui a déjà été vendu.

Partie 1 · Module 02

SELECT, WHERE, ORDER BY

Trois mots-clés suffisent à répondre à la majorité des questions qu'on se pose sur une base. SELECT choisit les colonnes à afficher, FROM la table à interroger, WHERE filtre les lignes.

Tous les articles à moins de 30 €

SELECT nom, prix
FROM articles
WHERE prix < 30;

SELECT * renvoie toutes les colonnes — pratique pour explorer, à éviter en production une fois qu'on sait précisément ce qu'on cherche, pour ne pas ramener des colonnes inutiles.

Les commandes d'un utilisateur précis, triées de la plus récente à la plus ancienne

SELECT id, statut, cree_le
FROM commandes
WHERE utilisateur_id = 4471
ORDER BY cree_le DESC;

ORDER BY trie le résultat — ASC (croissant, par défaut) ou DESC (décroissant). Sans lui, l'ordre des lignes renvoyées n'est pas garanti, même si la base semble toujours répondre dans le même ordre par habitude.

Exercice

Écris la requête qui affiche le nom et le stock de tous les articles dont le stock est inférieur à 5, triés du plus faible stock au plus élevé.

Voir la correction 
SELECT nom, stock
FROM articles
WHERE stock < 5
ORDER BY stock ASC;
Partie 1 · Module 03

Filtrer et gérer les NULL

WHERE accepte bien plus que le simple =. Voici les opérateurs qu'on utilise vraiment au quotidien :

OpérateurUsageExemple
=, <>, <, >, <=, >=Comparaison classiqueprix >= 20
IN (...)Appartient à une listestatut IN ('payee', 'expediee')
BETWEEN ... AND ...Dans un intervalle (bornes incluses)prix BETWEEN 10 AND 50
LIKEMotif texte — % = n'importe quelle suite de caractèresemail LIKE '%@novacart.fr'
AND / OR / NOTCombiner plusieurs conditionsprix > 20 AND stock > 0

Le piège des valeurs NULL

NULL représente une valeur absente — pas zéro, pas une chaîne vide, littéralement "on ne sait pas". C'est la source de bugs la plus fréquente pour qui découvre le SQL : WHERE colonne = NULL ne renvoie jamais rien, même sur une ligne où la colonne est vide, parce que NULL n'est égal à rien, pas même à lui-même.

Trouver les commandes sans statut renseigné

SELECT id
FROM commandes
WHERE statut IS NULL;   -- pas "= NULL"
Pour un testeur, ce piège compte double

Une requête de vérification qui utilise = NULL par erreur ne plante pas — elle renvoie juste zéro résultat, silencieusement, et fait croire qu'un problème n'existe pas. Toujours vérifier IS NULL / IS NOT NULL quand une colonne peut être vide.

Exercice

Écris la requête qui trouve tous les utilisateurs dont l'e-mail se termine par "@novacart.fr" ET qui n'ont jamais passé de commande avec le statut "annulee".

Voir la correction

Sans jointure, on ne peut pas encore exclure "jamais annulé" proprement (ça viendra au module 7 avec les sous-requêtes) — mais la partie filtre sur l'e-mail s'écrit :

SELECT *
FROM utilisateurs
WHERE email LIKE '%@novacart.fr';
Partie 1 · Module 04

Trier, dédupliquer, limiter

DISTINCT retire les doublons du résultat, LIMIT plafonne le nombre de lignes renvoyées, OFFSET saute les N premières — utile pour paginer.

Tous les statuts de commande différents qui existent réellement en base

SELECT DISTINCT statut
FROM commandes;

Les 5 articles les plus chers

SELECT nom, prix
FROM articles
ORDER BY prix DESC
LIMIT 5;

La page 2 d'une liste de 20 commandes par page

SELECT id, statut, cree_le
FROM commandes
ORDER BY cree_le DESC
LIMIT 20 OFFSET 20;
Utile pour un testeur

SELECT DISTINCT statut FROM commandes est souvent la première requête à lancer sur une table inconnue : elle révèle en une ligne toutes les valeurs réellement utilisées — parfois plus nombreuses que ce que la documentation officielle prévoyait, ce qui est déjà en soi une découverte utile.

Exercice

Écris la requête qui affiche les 3 articles avec le stock le plus faible, sans doublon de nom.

Voir la correction 
SELECT DISTINCT nom, stock
FROM articles
ORDER BY stock ASC
LIMIT 3;
Partie 1 · Module 05

Agréger avec GROUP BY

Les fonctions d'agrégation résument plusieurs lignes en une seule valeur : COUNT compte, SUM additionne, AVG fait la moyenne, MIN/MAX trouvent les extrêmes. GROUP BY les applique par groupe plutôt que sur toute la table.

Nombre de commandes par statut

SELECT statut, COUNT(*) AS nombre
FROM commandes
GROUP BY statut;

Chiffre d'affaires total par utilisateur, du plus gros au plus petit

SELECT utilisateur_id, SUM(quantite * prix_unitaire) AS total_depense
FROM lignes_commande lc
JOIN commandes c ON c.id = lc.commande_id
GROUP BY utilisateur_id
ORDER BY total_depense DESC;

Une règle stricte à retenir : dans une requête avec GROUP BY, toute colonne du SELECT qui n'est pas dans une fonction d'agrégation doit apparaître dans le GROUP BY — sinon la base ne sait pas quelle valeur choisir parmi les lignes du groupe.

Filtrer après agrégation : HAVING

WHERE filtre les lignes avant le regroupement ; HAVING filtre les groupes après. On ne peut pas écrire WHERE COUNT(*) > 5 — COUNT(*) n'existe pas encore au moment où WHERE s'applique.

Les utilisateurs ayant passé plus de 3 commandes

SELECT utilisateur_id, COUNT(*) AS nb_commandes
FROM commandes
GROUP BY utilisateur_id
HAVING COUNT(*) > 3;
Exercice

Écris la requête qui affiche, pour chaque article, le nombre total d'unités vendues (toutes commandes confondues) — uniquement pour les articles vendus plus de 10 fois au total.

Voir la correction 
SELECT article_id, SUM(quantite) AS total_vendu
FROM lignes_commande
GROUP BY article_id
HAVING SUM(quantite) > 10;
Partie 1 · Module 06

Les jointures

Une jointure combine des lignes de plusieurs tables selon une condition — typiquement une clé étrangère qui pointe vers une clé primaire. C'est la notion qui rend une base relationnelle réellement utile : sans elle, on serait coincé à interroger une table à la fois.

INNER JOIN — seulement ce qui correspond des deux côtés

Le nom de l'article pour chaque ligne de commande

SELECT lc.quantite, a.nom, a.prix
FROM lignes_commande lc
INNER JOIN articles a ON a.id = lc.article_id;

LEFT JOIN — tout de la table de gauche, même sans correspondance

Tous les utilisateurs, avec leur nombre de commandes (0 pour ceux qui n'en ont jamais passé)

SELECT u.email, COUNT(c.id) AS nb_commandes
FROM utilisateurs u
LEFT JOIN commandes c ON c.utilisateur_id = u.id
GROUP BY u.email;

Avec un INNER JOIN ici, les utilisateurs sans commande auraient disparu du résultat — c'est l'erreur la plus fréquente en QA : une requête de vérification qui utilise le mauvais type de jointure et masque silencieusement une catégorie entière de cas.

TypeRenvoie
INNER JOINSeulement les lignes qui correspondent des deux côtés
LEFT JOINToutes les lignes de gauche, complétées par NULL si rien ne correspond à droite
RIGHT JOINL'inverse du LEFT JOIN — rarement utilisé, on préfère inverser l'ordre des tables et faire un LEFT
FULL JOINToutes les lignes des deux côtés, correspondance ou non

Self-join — une table jointe à elle-même

Utile par exemple pour comparer deux commandes du même utilisateur : on joint la table commandes à elle-même via utilisateur_id, en donnant un alias différent à chaque copie (c1, c2) pour que la base sache laquelle est laquelle.

Exercice

Écris la requête qui liste tous les articles qui n'ont jamais été commandés — leur nom doit apparaître même s'ils n'ont aucune ligne dans lignes_commande.

Voir la correction 
SELECT a.nom
FROM articles a
LEFT JOIN lignes_commande lc ON lc.article_id = a.id
WHERE lc.id IS NULL;

Le LEFT JOIN garde tous les articles, et le WHERE lc.id IS NULL ne garde que ceux pour qui la jointure n'a rien trouvé à droite.

Partie 1 · Module 07

Sous-requêtes et CTE

Une sous-requête est une requête imbriquée dans une autre — utile quand on a besoin d'un résultat intermédiaire avant de pouvoir poser la vraie question.

Les articles plus chers que la moyenne

SELECT nom, prix
FROM articles
WHERE prix > (SELECT AVG(prix) FROM articles);

Les utilisateurs qui ont au moins une commande annulée

SELECT email
FROM utilisateurs
WHERE id IN (
    SELECT utilisateur_id FROM commandes WHERE statut = 'annulee'
);

CTE — nommer une étape pour la rendre lisible

Une CTE (Common Table Expression, introduite par WITH) donne un nom à une sous-requête, comme une variable temporaire. Le résultat est identique à une sous-requête imbriquée, mais la requête se lit de haut en bas plutôt que de l'intérieur vers l'extérieur — c'est ce que l'article cité au module 22 appelle "l'organisation des requêtes", une compétence à part entière une fois qu'on dépasse les cas simples.

La même question sur les gros dépensiers, réécrite avec une CTE

WITH depenses_par_utilisateur AS (
    SELECT c.utilisateur_id, SUM(lc.quantite * lc.prix_unitaire) AS total
    FROM lignes_commande lc
    JOIN commandes c ON c.id = lc.commande_id
    GROUP BY c.utilisateur_id
)
SELECT u.email, d.total
FROM depenses_par_utilisateur d
JOIN utilisateurs u ON u.id = d.utilisateur_id
WHERE d.total > 500
ORDER BY d.total DESC;

Une CTE peut aussi référencer plusieurs blocs WITH chaînés — pratique pour découper une requête complexe en étapes qu'on peut relire et tester une par une.

Exercice

Réécris avec une CTE : trouve les articles dont le stock est inférieur à la quantité moyenne commandée par ligne de commande (colonne quantite de lignes_commande).

Voir la correction 
WITH quantite_moyenne AS (
    SELECT AVG(quantite) AS moyenne
    FROM lignes_commande
)
SELECT a.nom, a.stock
FROM articles a, quantite_moyenne q
WHERE a.stock < q.moyenne;

Modéliser et modifier

Quatre modules pour comprendre comment une base est construite, et comment la modifier sans la casser.

Partie 2 · Module 08

Modéliser : clés et normalisation

Pourquoi NovaCart a-t-elle cinq tables séparées plutôt qu'une seule grande table "tout" avec toutes les colonnes ? Réponse : la normalisation — organiser les données pour qu'une même information ne soit jamais stockée à deux endroits différents.

Si le nom et le prix de chaque article étaient recopiés dans chaque ligne de commande, changer le prix d'un article obligerait à mettre à jour des milliers de lignes historiques — et en oublier une seule créerait une incohérence invisible. En stockant seulement article_id dans lignes_commande, le prix vit à un seul endroit : la table articles.

Nuance importante

En réalité, lignes_commande stocke bien prix_unitaire en plus de article_id — volontairement dénormalisé, pour garder une trace du prix payé au moment de l'achat, même si l'article change de prix plus tard. Une bonne modélisation n'est pas "toujours normaliser à fond", c'est choisir en connaissance de cause où la duplication est un bug et où elle est une fonctionnalité.

Les formes normales, en une phrase chacune

FormeRègle
1NFChaque cellule contient une seule valeur — jamais une liste dans une colonne
2NFChaque colonne dépend de la clé primaire entière, pas d'une partie seulement
3NFAucune colonne ne dépend d'une autre colonne non-clé — pas de dépendance transitive

En pratique, un testeur n'a pas besoin de réciter ces règles — mais reconnaître qu'une table est mal modélisée (des colonnes répétées, des listes cachées dans un champ texte) aide à comprendre pourquoi certains bugs de cohérence de données apparaissent régulièrement dans une application.

Exercice

Une table commandes_v2 imaginaire stocke une colonne articles_achetes contenant la chaîne de texte "3,7,12" (des identifiants d'articles séparés par des virgules). Quelle règle de normalisation viole-t-elle, et quel problème concret ça pose pour écrire une requête ?

Voir la correction

Ça viole la 1NF : une cellule contient plusieurs valeurs. Concrètement, impossible d'écrire un WHERE simple pour "trouver toutes les commandes contenant l'article 7" — il faudrait du traitement de texte fragile au lieu d'une jointure propre comme sur lignes_commande.

Partie 2 · Module 09

Contraintes d'intégrité

Une contrainte empêche la base d'accepter une donnée incohérente — la première ligne de défense, bien avant qu'un test ne la découvre.

La table articles, avec ses contraintes

CREATE TABLE articles (
    id SERIAL PRIMARY KEY,
    nom TEXT NOT NULL,
    prix NUMERIC(10,2) NOT NULL CHECK (prix >= 0),
    stock INTEGER NOT NULL DEFAULT 0 CHECK (stock >= 0)
);
ContrainteCe qu'elle empêche
NOT NULLUne valeur manquante sur cette colonne
UNIQUEDeux lignes avec la même valeur (ex. deux comptes avec le même e-mail)
CHECKUne valeur qui ne respecte pas une règle métier (ex. un prix négatif)
DEFAULTUne colonne vide à l'insertion — lui donne une valeur par défaut
FOREIGN KEYUne clé étrangère qui pointe vers une ligne qui n'existe pas

La clé étrangère entre commandes et utilisateurs

ALTER TABLE commandes
ADD CONSTRAINT fk_utilisateur
FOREIGN KEY (utilisateur_id) REFERENCES utilisateurs(id);
Pourquoi ça intéresse un testeur

Une contrainte violée en base renvoie une erreur immédiate et bloquante — c'est souvent la première ligne de défense contre un bug qu'un test applicatif n'a pas pensé à couvrir. Un bon réflexe en investigation de bug : vérifier si la contrainte qui aurait dû empêcher une donnée absurde existe réellement en base, ou si elle n'est appliquée que côté interface (et donc contournable).

Exercice

Écris la contrainte qui empêche deux utilisateurs d'avoir la même adresse e-mail dans la table utilisateurs.

Voir la correction 
ALTER TABLE utilisateurs
ADD CONSTRAINT email_unique UNIQUE (email);
Partie 2 · Module 10

INSERT, UPDATE, DELETE

Trois commandes modifient les données — et contrairement à SELECT, une erreur ici change vraiment la base. La règle d'or : toujours écrire et vérifier le WHERE d'un UPDATE ou d'un DELETE avant d'exécuter, jamais après.

Ajouter un nouvel article

INSERT INTO articles (nom, prix, stock)
VALUES ('Clavier mécanique', 79.90, 25);

Mettre à jour le stock après une vente

UPDATE articles
SET stock = stock - 1
WHERE id = 12;

Supprimer une commande annulée depuis plus d'un an

DELETE FROM commandes
WHERE statut = 'annulee'
AND cree_le < NOW() - INTERVAL '1 year';
Le piège le plus dangereux du SQL

Un UPDATE ou un DELETE sans WHERE s'applique à toutes les lignes de la table, sans confirmation. Sur un environnement de test comme sur un environnement de production, c'est l'erreur qui a le plus détruit de données dans l'histoire du SQL. Réflexe à prendre : écrire d'abord la requête en SELECT avec le même WHERE, vérifier qu'elle ne renvoie que les lignes voulues, puis seulement transformer en UPDATE/DELETE.

Exercice

Écris la requête SELECT de vérification qu'il faudrait lancer avant d'exécuter ce DELETE, pour être sûr de ne pas supprimer trop de lignes : DELETE FROM panier WHERE utilisateur_id = 4471;

Voir la correction 
SELECT * FROM panier WHERE utilisateur_id = 4471;

Si le nombre de lignes renvoyées correspond à ce qu'on attend (le panier d'un seul utilisateur), le DELETE avec le même WHERE est sûr à exécuter.

Partie 2 · Module 11

Transactions et ACID

Une transaction regroupe plusieurs modifications en un seul bloc qui réussit ou échoue entièrement — jamais à moitié. Sur NovaCart, valider une commande implique au moins deux opérations : créer la ligne dans commandes, et décrémenter le stock dans articles. Si la seconde échoue après que la première ait réussi, on se retrouve avec une commande fantôme sans stock décrémenté — exactement le genre de bug de cohérence qu'une transaction empêche.

Une transaction qui garantit la cohérence

BEGIN;

INSERT INTO commandes (utilisateur_id, statut) VALUES (4471, 'payee');
UPDATE articles SET stock = stock - 1 WHERE id = 12;

COMMIT;  -- ou ROLLBACK; en cas d'erreur, pour tout annuler

ACID, en une phrase chacune

PropriétéCe qu'elle garantit
AtomicitéTout ou rien — pas d'état intermédiaire visible
CohérenceLa base respecte toujours ses contraintes (module 9), avant et après
IsolationDeux transactions simultanées ne se marchent pas dessus
DurabilitéUne fois validée (COMMIT), la modification survit même à une panne

Le module 21 (bases de test) réutilise directement l'atomicité : ouvrir une transaction avant un test et faire un ROLLBACK à la fin est l'une des façons les plus propres de garder une base de test toujours dans le même état de départ.

Exercice

Deux utilisateurs achètent en même temps le dernier exemplaire en stock (stock = 1) d'un même article, sans transaction ni verrou. Quel problème concret l'isolation est censée empêcher ici ?

Voir la correction

Sans isolation correcte, les deux requêtes peuvent lire stock = 1 en même temps, chacune décrémenter à 0 puis valider — résultat : deux commandes payées pour un seul article en stock. C'est une condition de course (race condition), et c'est exactement ce que des transactions bien isolées empêchent.

PARTIE 3

SQL avancé

Six modules qui font la différence entre "je sais écrire une requête" et "je sais écrire la requête qu'un senior écrirait" — exactement ce que le module 22 identifie comme la vraie césure du marché en 2026.

Partie 3 · Module 12

Fonctions fenêtrées

Une fonction fenêtrée calcule une valeur sur un groupe de lignes sans les fusionner en une seule, contrairement à GROUP BY — chaque ligne garde son identité, avec une colonne calculée en plus.

Classer les articles du plus cher au moins cher, sans fusionner de lignes

SELECT nom, prix,
    ROW_NUMBER() OVER (ORDER BY prix DESC) AS rang
FROM articles;

Le classement des dépenses par utilisateur, catégorie par catégorie

SELECT utilisateur_id, categorie, total_depense,
    RANK() OVER (PARTITION BY categorie ORDER BY total_depense DESC) AS rang_categorie
FROM depenses_par_categorie;

PARTITION BY recrée des groupes, comme GROUP BY, mais le calcul reste attaché à chaque ligne individuelle plutôt que de les fusionner — rang_categorie repart à 1 pour chaque nouvelle catégorie.

FonctionCe qu'elle fait
ROW_NUMBER()Numérote les lignes, sans égalité possible
RANK()Classe, avec des ex-æquo qui sautent des rangs (1, 2, 2, 4)
LAG() / LEAD()Regarde la ligne précédente / suivante — utile pour comparer une commande à la précédente du même utilisateur
Exercice

Écris la requête qui affiche, pour chaque commande d'un utilisateur, le montant de sa commande précédente (chronologiquement) — NULL si c'est sa première.

Voir la correction 
SELECT utilisateur_id, id, cree_le,
    LAG(id) OVER (PARTITION BY utilisateur_id ORDER BY cree_le) AS commande_precedente
FROM commandes;
Partie 3 · Module 13

UNION, INTERSECT, EXCEPT

Ces opérateurs combinent le résultat de deux requêtes ayant le même nombre de colonnes, dans le même ordre de type — utile pour comparer deux ensembles plutôt que joindre deux tables.

OpérateurRenvoie
UNIONToutes les lignes des deux requêtes, doublons retirés
UNION ALLPareil, mais garde les doublons — plus rapide si on sait qu'il n'y en a pas
INTERSECTSeulement les lignes présentes dans les deux résultats
EXCEPTLes lignes du premier résultat absentes du second

Les utilisateurs qui ont un panier actif mais aucune commande "payee" — un bon indicateur d'abandon de panier

SELECT DISTINCT utilisateur_id FROM panier
EXCEPT
SELECT utilisateur_id FROM commandes WHERE statut = 'payee';
Exercice

Écris la requête qui trouve les utilisateurs ayant à la fois une commande "payee" ET une commande "annulee" — deux comportements qui coexistent.

Voir la correction 
SELECT utilisateur_id FROM commandes WHERE statut = 'payee'
INTERSECT
SELECT utilisateur_id FROM commandes WHERE statut = 'annulee';
Partie 3 · Module 14

Index et performance

Sans index, chercher une ligne dans une table revient à lire toutes les lignes une par une — un "scan complet". Un index est une structure annexe qui permet de sauter directement aux bonnes lignes, comme l'index d'un livre plutôt que de le lire page par page.

Accélérer les recherches par e-mail (déjà rapide si UNIQUE, mais explicite ici)

CREATE INDEX idx_utilisateurs_email ON utilisateurs(email);

EXPLAIN — voir ce que la base fait vraiment

EXPLAIN affiche le plan d'exécution choisi par la base pour une requête — sans l'exécuter (EXPLAIN ANALYZE l'exécute et donne les temps réels).

EXPLAIN ANALYZE
SELECT * FROM commandes WHERE utilisateur_id = 4471;

Un plan qui affiche Seq Scan (balayage complet) sur une grande table alors qu'un index existe sur la colonne filtrée est un signal à investiguer — soit l'index n'est pas utilisé pour une bonne raison technique, soit il manque.

Un index n'est pas gratuit

Chaque index accélère les lectures mais ralentit les écritures (INSERT/UPDATE/DELETE), puisque l'index doit lui aussi être mis à jour. Empiler des index "au cas où" sur une table très écrite peut dégrader les performances plutôt que les améliorer — la modélisation (module 8) et l'usage réel de la table guident la décision, pas une règle automatique.

Exercice

Une requête WHERE statut = 'payee' sur la table commandes (des millions de lignes) est lente. La colonne statut ne prend que 4 valeurs possibles. Un index dessus est-il forcément une bonne idée ?

Voir la correction

Pas nécessairement — avec seulement 4 valeurs possibles réparties sur des millions de lignes, chaque valeur représente une part énorme de la table, et un index apporte peu par rapport à un scan complet (la base doit de toute façon lire une grande partie des pages). Un index composite incluant statut avec une autre colonne plus sélective, ou une réflexion sur le partitionnement de la table, serait souvent plus efficace.

Partie 3 · Module 15

Vues et procédures stockées

Une vue est une requête sauvegardée sous un nom, qu'on interroge ensuite comme une table normale — pratique pour ne pas réécrire dix fois la même jointure complexe.

Une vue qui simplifie l'accès au chiffre d'affaires par utilisateur

CREATE VIEW ca_par_utilisateur AS
SELECT c.utilisateur_id, SUM(lc.quantite * lc.prix_unitaire) AS total
FROM lignes_commande lc
JOIN commandes c ON c.id = lc.commande_id
WHERE c.statut = 'payee'
GROUP BY c.utilisateur_id;

-- s'utilise ensuite comme une table :
SELECT * FROM ca_par_utilisateur WHERE total > 1000;

Une vue ne stocke pas de données elle-même — elle réexécute sa requête à chaque interrogation. Une vue matérialisée (MATERIALIZED VIEW) fait l'inverse : elle stocke un résultat figé, à rafraîchir explicitement, utile quand la requête sous-jacente est coûteuse et n'a pas besoin d'être à la seconde près.

Procédures stockées et triggers, en bref

Une procédure stockée encapsule de la logique directement dans la base (calculs, boucles, conditions), appelable par son nom. Un trigger déclenche automatiquement une action quand un événement survient (avant/après un INSERT, par exemple, pour maintenir un historique). Les deux sont puissants mais rendent la logique métier plus difficile à tester et à versionner qu'un simple code applicatif — à connaître de nom pour ne pas être surpris en les rencontrant, sans forcément en écrire au quotidien.

Exercice

Pourquoi une vue matérialisée peut-elle induire un testeur en erreur s'il ne sait pas qu'elle existe ?

Voir la correction

Parce qu'elle peut afficher des données obsolètes — un testeur qui modifie une donnée source puis interroge la vue matérialisée sans rafraîchissement peut croire à un bug alors que la donnée source est correcte, seule la vue n'a pas encore été mise à jour.

Partie 3 · Module 16

Dates, texte et JSON

Trois familles de fonctions reviennent sans cesse dans les requêtes du quotidien.

Dates et heures

-- Commandes des 30 derniers jours
SELECT * FROM commandes WHERE cree_le > NOW() - INTERVAL '30 days';

-- Nombre de commandes par mois
SELECT DATE_TRUNC('month', cree_le) AS mois, COUNT(*)
FROM commandes
GROUP BY mois
ORDER BY mois;

Texte

-- Normaliser la casse avant de comparer
SELECT * FROM utilisateurs WHERE LOWER(email) = LOWER('Test@NovaCart.fr');

-- Concaténer prénom et nom
SELECT CONCAT(prenom, ' ', nom) AS nom_complet FROM utilisateurs;

JSON — de plus en plus courant en 2026

PostgreSQL stocke nativement des données JSON dans une colonne (type JSONB), pratique pour des attributs variables sans créer une colonne par cas (par exemple, les caractéristiques techniques différentes d'une catégorie d'article à l'autre).

-- Une colonne 'caracteristiques' au format JSONB sur articles
SELECT nom, caracteristiques->>'couleur' AS couleur
FROM articles
WHERE caracteristiques->>'garantie_mois' = '24';
Pourquoi le JSON compte pour un testeur en 2026

De plus en plus d'applications mélangent tables relationnelles classiques et colonnes JSON pour les données peu structurées. Savoir interroger une colonne JSONB directement en SQL évite de devoir tout extraire côté application juste pour vérifier une valeur — un gain de temps réel en investigation de bug.

Partie 4 · Module 18

Vérifier l'intégrité des données derrière l'interface

Le module 20 du cours QA a déjà montré le principe : l'interface peut afficher un succès alors que la base ne reflète pas ce succès. Ici, on va plus loin — comment structurer ces vérifications pour qu'elles couvrent vraiment ce qui compte.

Trois familles de vérifications à automatiser

FamilleExemple
ExistenceLa ligne attendue existe-t-elle après l'action ? (module 20 du cours QA)
CohérenceLe total affiché correspond-il à la somme réelle des lignes en base ?
AbsenceUne ligne supprimée a-t-elle vraiment disparu partout — y compris dans les tables liées ?

Vérifier la cohérence : le total affiché doit égaler la somme réelle

SELECT c.id,
    (SELECT SUM(quantite * prix_unitaire) FROM lignes_commande WHERE commande_id = c.id) AS total_calcule
FROM commandes c
WHERE c.id = 8842;

Vérifier l'absence après suppression d'un compte : aucune trace ne doit rester

SELECT
    (SELECT COUNT(*) FROM panier WHERE utilisateur_id = 4471) AS panier_restant,
    (SELECT COUNT(*) FROM commandes WHERE utilisateur_id = 4471) AS commandes_restantes;
-- les deux doivent valoir 0, ou suivre la politique de conservation définie (RGPD, module 22 du cours QA)
Exercice

Écris la requête qui vérifie que le stock d'un article (id 12) correspond bien à : stock initial connu (100) moins la somme de toutes les quantités vendues pour cet article.

Voir la correction 
SELECT a.stock AS stock_actuel,
    100 - COALESCE(SUM(lc.quantite), 0) AS stock_attendu
FROM articles a
LEFT JOIN lignes_commande lc ON lc.article_id = a.id
WHERE a.id = 12
GROUP BY a.stock;

COALESCE remplace un NULL (aucune vente) par 0, pour que le calcul reste correct même sans aucune ligne de commande.

Partie 4 · Module 19

Générer et nettoyer des données de test

Le module 22 du cours QA a introduit Faker pour générer des comptes fictifs réalistes. Ici, on regarde comment insérer ces jeux de données en masse, et surtout comment les nettoyer proprement après usage.

Insérer 500 comptes de test générés avec Faker (Python), en une seule requête

INSERT INTO utilisateurs (email, mot_de_passe_hash, cree_le)
VALUES
    ('test001@novacart.fr', '...', NOW()),
    ('test002@novacart.fr', '...', NOW()),
    -- ... générées par le script Faker du module 22 du cours QA
    ('test500@novacart.fr', '...', NOW());

Nettoyer sans casser les autres données

Un jeu de données de test qui s'accumule sans être nettoyé finit par fausser des statistiques, ralentir des requêtes, ou pire, se mélanger avec de vraies données lors d'un export. La convention la plus simple : préfixer systématiquement les données de test (test%@novacart.fr) pour pouvoir les cibler sans ambiguïté.

-- Nettoyage ciblé, jamais un DELETE FROM utilisateurs; sans WHERE
DELETE FROM utilisateurs
WHERE email LIKE 'test%@novacart.fr'
AND cree_le < NOW() - INTERVAL '7 days';
Attention à l'ordre de suppression

Supprimer un utilisateur avant ses commandes viole la contrainte de clé étrangère du module 9 (ou pire, la contourne silencieusement si elle n'est pas configurée). L'ordre correct : supprimer d'abord les lignes des tables dépendantes (lignes_commande, puis commandes, puis panier), et remonter jusqu'à utilisateurs en dernier — ou utiliser ON DELETE CASCADE sur la contrainte, en toute connaissance de cause.

Exercice

Écris, dans le bon ordre, les requêtes DELETE nécessaires pour supprimer proprement toutes les traces d'un utilisateur de test (id 9001) dans lignes_commande, commandes, panier, puis utilisateurs.

Voir la correction

DELETE FROM panier WHERE utilisateur_id = 9001;

SQL dans une suite pytest

On relie maintenant tout ce module au cours QA : comment appeler du SQL proprement depuis une suite de tests Playwright/pytest, sans dupliquer la logique de connexion dans chaque fichier de test.

Une fixture pytest réutilisable pour la connexion à la base de test

import os
import psycopg2
import pytest


@pytest.fixture
def db_connexion():
    connexion = psycopg2.connect(os.environ["DATABASE_URL_TEST"])
    yield connexion
    connexion.close()

tests/test_panier.py — réutilise la fixture

def test_ajouter_article_cree_bien_une_ligne_en_base(page, db_connexion):
    # ... actions dans l'interface (module 11 du cours QA) ...

Partie 4 · Module 21

Stratégies de bases de test

Trois approches courantes pour garder une base de test dans un état prévisible entre deux exécutions — chacune avec un compromis différent.

StratégiePrincipeAvantageLimite
Base dédiée par environnementUne base de test isolée, jamais touchée par la productionSimple à mettre en placePeut dériver de la structure réelle de prod si mal maintenue
Transaction annulée (rollback)Chaque test ouvre une transaction (module 11) et l'annule à la fin, quel que soit le résultatBase toujours propre, rapideNe fonctionne pas pour les tests qui vérifient un vrai COMMIT (ex. envoi d'e-mail déclenché après validation)
Snapshot / seedUn script réinitialise la base à un état connu avant chaque campagneReproductible, proche d'un vrai jeu de donnéesPlus lent, à réserver aux tests système (module 4 du cours QA), pas à chaque test unitaire

Le pattern rollback, appliqué en pytest

@pytest.fixture
def db_connexion_transaction():
    connexion = psycopg2.connect(os.environ["DATABASE_URL_TEST"])
    connexion.autocommit = False
    yield connexion
    connexion.rollback()   # annule tout ce que le test a modifié
    connexion.close()
Comment choisir

Pour la majorité des tests d'intégration (module 4 du cours QA), le rollback est le meilleur rapport rapidité/fiabilité. Réserve les snapshots aux scénarios de bout en bout où l'état exact de départ fait partie du test lui-même — pas par défaut, seulement quand c'est justifié.

Exercice

Un test vérifie qu'un e-mail de confirmation part bien après le paiement d'une commande — le service d'envoi d'e-mail se déclenche uniquement après un COMMIT réel en base. La stratégie rollback convient-elle ici ?

Voir la correction

Non — un rollback annule la transaction avant qu'elle ne devienne visible, donc le déclencheur d'e-mail (qui réagit à un COMMIT réel) ne se déclenchera jamais dans ce scénario. Une base dédiée ou un snapshot, avec un vrai nettoyage après coup, est plus adapté ici.
